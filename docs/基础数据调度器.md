# 基础数据调度器

基础数据调度器负责按频率编排 A 股和数字货币的基础数据采集。它只复用 `scripts/data/collect_base_data.py`，不做因子计算、初筛、评分、Agent 分析或交易执行。

在私人金融助手架构中，它是事实输入前置层，负责把上游 `AssetUniverse`、行情、财务、资金流、事件和风险数据稳定落库，供后续持仓监控、观察池触发、推荐决策和复盘使用。

## 1. 推荐链路中的位置

```text
数据同步配置
 -> 基础数据调度器
 -> raw_records / assets / asset_profiles / asset_provider_mappings / asset_universes / asset_universe_members
 -> asset_status_snapshots / realtime_quote_snapshots
 -> market_bars / fundamental_snapshots / capital_flow_snapshots / event_records / risk_findings
 -> 因子 / 信号 / 风险更新
 -> TriggerService 判断
 -> 上层 Agent 调度金融团队 Workflow
```

`assets` 是稳定身份主表，高频变化的名称补全、Provider 代码映射、交易状态和实时行情分别写入 `asset_profiles`、`asset_provider_mappings`、`asset_status_snapshots` 和 `realtime_quote_snapshots`。采集器使用 `ensure_asset()` 创建缺失资产，存在时不更新主表行，用来降低并发调度下 PostgreSQL `assets` 行锁死锁概率。`universe_refresh` 中的指数、行业、概念、热榜和涨停池成员关系只写入 `asset_universes` / `asset_universe_members`，不再写入 `asset_profiles`；候选池种子补齐的 Provider 映射统一使用 `akshare:universe_seed`，具体来源保存在 `payload.universe_source`。

## 2. 配置怎么填

不要手写股票代码，也不要把“候选池”理解成推荐结果。第一版配置只关心四件事：

1. 选哪个预设。
2. 哪些市场启用。
3. 每个市场启用哪些数据包。
4. 每类任务的刷新间隔和补采窗口。

A 股的 `universe_refresh` 不是单标的示例任务，而是先拉目录，再按目录自动展开：

- 指数目录 -> 指数成分种子池。
- 行业目录 -> 行业成分种子池。
- 概念目录 -> 概念成分种子池。
- 资金流榜 -> 资金流候选种子。

导出到底层调度计划时会带上 `index_catalog_limit`、`industry_catalog_limit`、`concept_catalog_limit` 和 `catalog_member_limit`。这几个字段为 `0` 表示不截断目录或目录成员，适合全面采集；它们不再使用 `batch_size` 作为总量上限。

可以先导出默认模板，再修改：

```powershell
python -m finance_agent.cli data config init --output data_sync_config.json
python -m finance_agent.cli data config preview --config-file data_sync_config.json
python -m finance_agent.cli data config export --config-file data_sync_config.json --output base_data_scheduler.json
```

无参数初始化默认使用 `personal-ashare`，只启用 A 股和基金。数字货币保持独立配置，只有显式传入 `--preset crypto-comprehensive` 或手工选择 crypto 市场时才会进入调度计划；旧的 `personal-comprehensive` 仍保留四市场兼容行为。

### 2.1 配置字段说明

- `preset`：预设模式，例如 `personal-ashare`、`personal-comprehensive`、`ashare-comprehensive`、`crypto-comprehensive`、`lightweight`。
- `markets`：启用的市场，只能是 `ashare`、`fund`、`crypto_spot`、`crypto_future`。
- `universe_sources`：上游候选池来源，例如 A 股全 A、指数成分、行业成分、概念成分、资金流榜、人气榜、涨停池；数字货币只有 Binance 交易对池。
- `data_packages`：实际要拉的数据包，例如 K 线、实时行情、财务、估值、资金流、新闻公告、风险情绪、衍生品快照。
- `interval_seconds`：每类任务的刷新间隔。
- `lookback_days` / `lookback_hours`：补采窗口。
- `batch_size`：按标的补采时的单批标的数量，不是本次任务的资产总上限。K 线、A 股基本面/估值、数字货币合约衍生品会自动展开资产池，并在一次调度任务内按 `batch_size` 分批循环，直到本次待补股票或交易对跑完。
- `limit`：单个 Provider 调用内部的记录窗口或调度摘要上限，不能用来表示“本轮只采多少只股票”。逐标的任务会从库内完整资产池展开。
- `source_limit`：仅供人工诊断或临时限流使用的列表来源上限。调度计划默认不写入该字段，因此资金流、新闻公告、风险情绪等列表型来源默认完整刷新，不受 `batch_size` 截断。
- `catalog_member_limit`：A 股指数、行业、概念目录下成分采集上限，默认 `0` 表示不截断。
- A 股 `risk_sentiment_refresh` 在调度执行时会生成“运行日向前 14 天”的 `risk_start/risk_end`，避免沿用采集脚本样例日期；显式配置这两个字段时按历史回补日期原样执行。

## 3. 候选池和基础池的区别

- `基础池` 不是“已经进入推荐结果的股票/币种列表”，它只是系统采集和过滤的底层输入范围。
- `候选池来源/种子池` 是上游数据源直接给出的范围，比如全 A、指数成分、行业成分、概念成分、资金流榜、人气榜、涨停池、Binance 交易对池。
- `AssetUniverse` 才是系统整理后的推荐输入。
- Agent 分析后的结果应该叫推荐榜、观察池或回避池，不应该再叫候选池。

## 4. A 股和数字货币的边界

- A 股和数字货币共用同一套配置模型、调度器和采集入口。
- 但两条链路必须分别运行、分别排序、分别输出。
- `mixed` 不能作为候选池或推荐运行的市场，只能保留在少量历史兼容场景里。

## 5. 运行方式

### 5.1 生成配置和调度计划

打印当前计划，不触发采集：

```powershell
python scripts/data/run_base_data_scheduler.py --print-plan
```

输出默认调度模板：

```powershell
python scripts/data/run_base_data_scheduler.py --dump-default-config
```

按配置执行启用任务：

```powershell
python scripts/data/run_base_data_scheduler.py --config base_data_scheduler.json --run-once
```

只做 dry-run：

```powershell
python scripts/data/run_base_data_scheduler.py --config base_data_scheduler.json --run-once --dry-run
```

### 5.2 常驻运行

本地常驻运行可以直接使用 `--loop`。建议显式指定状态文件和事件日志文件，方便后续前端、监控脚本或系统服务读取。

```powershell
python scripts/data/run_base_data_scheduler.py `
  --config base_data_scheduler.json `
  --loop `
  --status-file runtime/base_data_scheduler/status.json `
  --event-log-file runtime/base_data_scheduler/events.jsonl
```

生产部署时建议先用 `--dry-run --max-cycles 1` 验证配置：

```powershell
python scripts/data/run_base_data_scheduler.py `
  --config base_data_scheduler.json `
  --loop `
  --dry-run `
  --max-cycles 1 `
  --status-file runtime/base_data_scheduler/status.json `
  --event-log-file runtime/base_data_scheduler/events.jsonl
```

### 5.3 健康检查

调度器运行时会写入状态文件。外部进程可以用健康检查命令读取该文件：

```powershell
python scripts/data/run_base_data_scheduler.py `
  --health-check `
  --status-file runtime/base_data_scheduler/status.json `
  --health-max-age-seconds 300
```

退出码约定：

- `0`：健康。
- `2`：状态文件缺失、过期、格式错误或最后任务失败。

状态文件核心字段：

- `updated_at`：最近心跳更新时间。
- `state`：`running`、`completed`、`interrupted`、`disabled` 等。
- `last_job`：最后执行的任务。
- `last_job_status`：`planned`、`executed`、`failed`。
- `last_error`：最后错误信息。
- `health_stale_seconds`：状态过期阈值。

### 5.4 日志和重试

`--event-log-file` 会写入 JSONL 结构化事件，当前包括：

- `scheduler_start`
- `job_start`
- `job_error`
- `job_retry`
- `job_success`
- `job_planned`
- `scheduler_stop`

调度计划支持以下全局字段：

- `max_job_retries`：单个任务失败后的最大重试次数，默认 `2`。
- `retry_backoff_seconds`：失败重试等待秒数，默认 `30`。
- `health_stale_seconds`：健康检查心跳过期阈值，默认 `300`。

任务失败不会直接让整个调度器崩溃。调度器会记录失败摘要，继续进入后续任务或下一轮调度。Provider 级别的任务锁和熔断仍由 `collect_base_data.py` 负责。

### 5.5 全量和增量策略

默认 `personal-ashare` 只导出 A 股、基金及其分析/维护任务。2026-07-15 真实 `--print-plan` 共 37 项、启用 33 项，crypto 任务为 0；一次性 `--run-once --dry-run` 为 `completed`、无错误。显式 `personal-comprehensive` 继续保留完整四市场任务，显式 `crypto-comprehensive` 继续独立导出数字货币任务。

完整预设可覆盖以下任务类型：

- A 股全量 Universe：`ashare.universe.all`，默认每日刷新。全 A 资产列表和指数/行业/概念目录默认完整展开，不受 `batch_size` 截断。
- A 股 K 线增量补采：`ashare.bars.1d`，默认每小时。每次触发会按 K 线覆盖缺口、采集水位和失败重试时间筛选待补资产，并按 `batch_size` 分批跑完整个待补集合。
- A 股基本面/估值：`ashare.fundamentals`，默认每 12 小时。每次触发会按完整 A 股资产池分批刷新个股财务指标和估值，业绩报表、股息率仍按市场级接口执行一次。
- A 股资金流：`ashare.capital_flow`，默认每 30 分钟。资金流榜属于列表型来源，默认不按 `batch_size` 截断。
- A 股新闻公告：`ashare.events`，默认每 5 分钟。个股新闻只覆盖观察池、最新非回避推荐和默认标的等重点资产，默认最多 `priority_symbol_limit=batch_size` 只；公告按市场级列表刷新，默认不按 `batch_size` 截断来源记录。
- A 股风险情绪：`ashare.risk_sentiment`，默认每 5 分钟。停牌、人气榜、涨停池、龙虎榜、大宗交易和两融数据属于列表型来源，默认不按 `batch_size` 截断。
- 数字货币现货 Universe：`crypto_spot.universe.binance`，默认每小时。Binance 交易对完整写入资产池，不受 `batch_size` 截断。
- 数字货币现货 K 线：`crypto_spot.bars.1h`，默认每 5 分钟。每次触发会按覆盖缺口排序交易对，并按 `batch_size` 分批跑完当前资产池。
- 数字货币合约 Universe：`crypto_future.universe.binance`，默认每小时。Binance 合约交易对完整写入资产池，不受 `batch_size` 截断。
- 数字货币合约 K 线：`crypto_future.bars.1h`，默认每 5 分钟。每次触发会按覆盖缺口排序交易对，并按 `batch_size` 分批跑完当前资产池。
- 数字货币合约衍生品：`crypto_future.derivatives`，默认每 5 分钟。每次触发会按完整合约资产池分批刷新资金费率、未平仓量和多空比。

可以通过 `data_sync_config.json` 中的 `interval_seconds`、`batch_size`、`lookback_days` 和 `lookback_hours` 调整频率、单批标的数量和增量补采窗口。导出的 `ashare.events.params.priority_symbol_limit` 用于控制逐股新闻覆盖的重点标的数量。

按标的增量任务遵循统一顺序：

```text
刷新完整上游 Universe
 -> 写入 assets / asset_universes / asset_universe_members
 -> 从库内资产池读取本轮待补标的
 -> 按覆盖缺口、成功水位和失败重试时间排序分批
 -> 每批执行采集并提交
 -> 本轮资产池跑完后任务结束
```

如果增量任务启动时发现库内资产池为空或明显像旧的截断池，会先自动执行一次完整 Universe 刷新，再继续本轮分批补采。

列表型来源遵循不同顺序：

```text
按接口自身支持的范围完整刷新
 -> 标准化写入资金流、事件、风险、候选池种子等表
 -> 原文补全等慢操作不阻塞主事件入库
 -> 只有显式传入 source_limit 时才临时截断
```

因此，`batch_size=200` 不表示资金流、人气榜、公告或风险列表只同步 200 条；它只控制需要逐标的循环的任务单批处理多少个标的。

### 5.6 采集水位、失败退避和限流

- `data_sync_watermarks` 记录每个资产、数据域、周期和逻辑 Provider 的采集水位。A 股 K 线成功后以 `market_bars` 表内最新 K 线时间更新 `watermark_at`。
- K 线出现 `curl(56)`、超时、远端断连等失败时，任务仍继续处理同批其他标的，并写入 `next_retry_at`。下一轮筛选会跳过仍处于冷却期的标的。
- `raw_records` 继续保存 Provider 原始响应和错误审计；水位表只负责调度选择和失败恢复，不替代原始记录。
- 采集入口使用进程内 `SourceRateLimiter` 按数据源限流。默认对 `stock_zh_a_hist_tx`、`stock_news_em`、`stock_notice_report` 和 `ccxt_binance_fetch_ohlcv` 分别限制并发和最小请求间隔，避免并发批次把单一上游接口打满。

通用化改造后，水位不再只服务 K 线补采，而是作为所有可 item 化任务的断点续跑依据。当前已接入的逻辑如下：

| 数据域 | 任务 | `data_domain` | `provider` / 逻辑来源 | `asset_id` 粒度 |
| --- | --- | --- | --- | --- |
| A 股日 K | `ashare.bars.1d` / `ashare.bars.1d.bootstrap` / `midday_partial` / `close_final` / `revision` | `market_bars` | `akshare:stock_zh_a_hist_tx` | 单股票，例如 `ashare:600519` |
| A 股基本面 | `ashare.fundamentals` | `fundamentals` | `stock_financial_analysis_indicator_em` | 单股票 |
| A 股估值 | `ashare.fundamentals` | `valuation` | `stock_value_em` | 单股票 |
| A 股资金流 | `ashare.capital_flow` | `capital_flow` | `stock_individual_fund_flow_rank` | 榜单逻辑 item 或单股票补缺 |
| A 股新闻正文 | `ashare.news_articles` | `events` | 新闻 URL 正文补全 Provider | 单新闻 URL 逻辑 item |
| A 股风险情绪 | `ashare.risk_sentiment` | `risk_sentiment` | `stock_zh_a_stop_em`、`stock_hot_rank_em`、`stock_zt_pool_em`、`stock_lhb_detail_em`、`stock_dzjy_mrmx`、`stock_margin_sse`、`stock_margin_szse` | 单风险源逻辑 item |
| Crypto K 线 | `crypto_spot.bars.1h` / `crypto_future.bars.1h` | `market_bars` | `ccxt_binance_fetch_ohlcv` | 单交易对，例如 `crypto_spot:BTCUSDT` |
| Crypto 衍生品 | `crypto_future.derivatives` | `derivatives` | `binance_derivative_snapshot` | 单合约交易对 |

水位表的 `status` 表示该 item 在该数据域最近一次采集状态，`watermark_at` 表示成功推进到的数据时间，`next_retry_at` 表示失败冷却期。任务启动时会同时参考事实表覆盖度和水位表，跳过已经完整覆盖或仍处于冷却期的 item；Redis 进度丢失时，也可以通过这些持久化水位恢复下一轮待处理集合。

调度器、资源池、任务 worker 与 SourceGate 是四层不同控制：

- `max_concurrent_jobs` 是调度器全局总闸门，限制同时运行多少个 job。
- `resource_pools` / `job.resource_pool` 是调度层资源隔离，限制同类重任务、实时任务、正文补抓、Agent 消费等各自最多并行多少个 job；资源池额度可在数据同步配置页单独保存，运行中的 loop 会在下一轮选 job 前热加载调度 JSON。
- `max_workers` 是当前任务内部消费 item 队列的 worker 数，页面保存后会在下一只 item 提交前重新读取。
- `rate_policies` 是源级有效并发和请求间隔，SourceGate 在每次取令牌前按最新策略刷新，worker 或资源池额度增大都不会绕过源级限制。
- Provider 失败后会更新源状态快照，前端可看到全局任务并发、资源池占用、任务 worker、源有效并发、退避状态和熔断剩余时间。
- A 股 K 线 Provider 链为 Eastmoney Direct -> Tencent Direct -> AKShare wrapper；基本面、估值、新闻正文、风险源和 Crypto 衍生品按各自输出结构配置独立 Provider 或逻辑来源，不伪造等价 fallback。

### 5.7 生产化补采和候选池策略工具

数据层生产化增强已经接入 `finance-agent data production` 命令组。它不直接联网拉新数据，而是把健康检查、交易日历和候选池策略转成可执行计划：

```powershell
python scripts/data/check_base_data_health.py > base_data_health.json
python -m finance_agent.cli data production backfill-plan --health-file base_data_health.json
```

当前 `backfill-plan` 会根据 `market_calendars`、`market_bars`、资金流、基本面、事件、风险和数字货币衍生品缺口生成调度任务。`market_bars` 缺口会同时生成 A 股、数字货币现货和数字货币合约补采任务，避免只补 A 股、不补 Binance 行情。

候选池策略也已提供 CLI：

```powershell
python -m finance_agent.cli data production merge-universe `
  --target-universe-id universe:merged:ashare:daily `
  --name 每日A股综合候选池 `
  --source-universe-ids universe:flow,universe:hot `
  --source-weights "{\"universe:flow\":2.0,\"universe:hot\":1.0}"

python -m finance_agent.cli data production rebuild-avoid-pool `
  --universe-id universe:avoid:ashare `
  --name A股回避池 `
  --market ashare
```

- `merge-universe`：只允许合并同市场候选池，按来源权重和成员排名去重排序。
- `rebuild-avoid-pool`：根据资产交易状态、ST/风险警示名称和 `risk_findings` 高风险记录生成回避池。
- 回避池成员写入时使用 `included=false`，用于后续推荐和 Agent 决策前置回避，而不是推荐结果。

## 7. 推荐流水线写库闸门

`recommendation_pipeline` 不再在基础数据不完整时硬跑完整推荐链路。调度参数会传入以下门槛：

- A 股：`min_bars=60`、`min_indicator_coverage_ratio=0.7`、`min_factor_coverage_ratio=0.5`、`min_available_factor_groups=3`
- 数字货币现货：`min_bars=120`、`min_indicator_coverage_ratio=0.85`、`min_factor_coverage_ratio=0.6`、`min_available_factor_groups=2`
- 数字货币合约：`min_bars=120`、`min_indicator_coverage_ratio=0.85`、`min_factor_coverage_ratio=0.6`、`min_available_factor_groups=3`

执行顺序为：

```text
候选池成员
 -> IndicatorService 计算指标覆盖率
 -> 覆盖率达标后，仅对已有指标快照的标的运行 FactorService
 -> 因子覆盖率达标后，才进入 Screening / Scoring / Signal / Recommendation
```

这样低覆盖的候选池会在日志和返回摘要中显示 `indicator_coverage` 或 `factor_coverage`，但不会继续写入大量 `unavailable` / `partial` 的 `factor_frames`、`signal_snapshots` 和推荐结果。

## 8. 新闻事件链路

当前 A 股新闻链路拆成四个调度任务：

- `ashare.events`：盘中高频任务，默认每 5 分钟运行一次。逐股新闻只采集事件重点池、用户观察池、系统研究池、技术初筛池和最近推荐中的可交易主板标的，参数为 `news_scope=priority`。
- `ashare.events.full`：盘后全量补采任务，交易日 18:20 运行。逐股新闻从可交易 A 股主板资产池展开，参数为 `news_scope=full_tradeable`，按 `batch_size` 分批执行，但不把 `batch_size` 当作总量上限。
- `ashare.news_articles`：新闻正文补抓任务，在 `ashare.events` 或 `ashare.events.full` 成功后触发，单独使用 `article_enrichment` 资源池和 `stock_news_article` 源级限频。
- `ashare.news_retention`：过期新闻/公告事件清理任务，每天 19:10 后台执行，参数为 `sync_task_type=event_article_retention`、`article_retention_days=90`，使用 `maintenance` 资源池，并与新闻采集共享 `ashare.event_records` 互斥键。

新闻数据当前按三层保存：

- `event_records`：清洗后的事件事实表。个股新闻写入 `event_type=news`，公告写入公告类事件；字段包括 `event_id`、`asset_id`、`symbol`、`market`、`title`、`summary`、`url`、`published_at`、`collected_at` 和 `payload`。正文补抓成功后，会把 `payload.article.full_text`、抓取状态、正文长度、来源摘录和 `raw_record_id` 回填到对应新闻事件。
- `evidence`：供推荐、因子和 Agent 读取的证据索引。新闻和公告会同步写入证据项，正文补抓后也会按 `event_id` 回填 `payload.article`。
- `raw_records`：Provider 原始响应审计表。`stock_news_em`、`stock_notice_report`、`stock_news_article` 的成功和失败都会归档；相同 Provider、endpoint、request hash、content hash、status 会通过唯一索引精确去重。

时效性上，推荐和因子链路不要求新闻永久等权使用。事件因子通过 `published_at` 或 `collected_at` 做时间衰减，越新的新闻权重越高；盘中高频任务负责发现重点资产的新事件，盘后全量任务负责补齐当天可交易主板资产新闻。

新闻时效已经按“热窗口保留”和“原始审计保留”分层处理：

- Agent 上下文和因子计算默认只读取最近 90 天事件，避免长期无新消息的标的把旧新闻继续当成当前信号。
- `event_records` / `evidence` 中的新闻和公告默认只保留 90 天热窗口，过期后删除整行，避免时效事件长期膨胀。
- `EventRepository.delete_expired_article_events()` 会删除过期新闻/公告事件和证据整行，但保留 `raw_records` 原始审计。
- `ashare.news_retention` 已接入基础数据调度器，后台定时调用上述清理能力，不触发新闻抓取、不清理 `raw_records`。
- `raw_records` 继续作为 Provider 原始响应审计表，当前不自动删除。后续如库体积压力明显，再增加按月份归档或冷存储流程，不建议直接无备份删除。
