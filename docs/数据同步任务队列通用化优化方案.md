# 数据同步任务队列通用化优化方案

## 1. 背景

10 年 A 股日 K 初始化任务已经验证了一套较完整的批量采集模型：资产池展开、按覆盖度筛选待同步标的、任务内 worker 并发、源级限流、Provider 降级、失败水位记录、进度可视化、暂停取消和失败重跑。

当前其他数据任务仍然偏“调度任务直接调用采集函数”的模式。它们虽然已经有 `batch_size`、`max_workers` 和部分 `rate_policies`，但在断点续跑、失败隔离、Provider 降级、进度细粒度和热配置方面还不够统一。因此，本方案目标是把 10 年 K 线任务的成熟设计抽象为通用数据同步执行框架，让 A 股基本面、资金流、新闻事件、风险情绪、Crypto K 线和衍生品等任务都能复用同一套执行语义。

## 2. 目标

1. 统一任务执行模型：所有批量采集任务都按“任务运行 + item 队列 + worker 池 + Provider 链 + 水位记录”执行。
2. 保持任务可恢复：任务取消、后端重启或数据源失败后，下一次运行能按水位和覆盖度继续，不重复扫完整市场。
3. 分离任务并发和源并发：页面配置的任务 worker 是队列消费并发；实际外部请求还必须经过源级限流。
4. 降低数据源压力：失败时进入退避、熔断或降级，不让多个 worker 同时猛打同一数据源。
5. 保持前端可观测：每个任务展示总数、已完成、失败、处理中、剩余、吞吐量、源状态、最近日志和失败原因。
6. 不破坏事实表设计：运行态进度和短期日志放 Redis；事实数据、水位和失败摘要继续写数据库。

## 3. 非目标

1. 不把所有实时日志长期写入 PostgreSQL。
2. 不要求所有数据域都必须有等价备用源；没有等价源时，记录该数据域缺失，而不是伪造 fallback。
3. 不把盘中看盘功能交给日 K 任务；盘中行情仍由实时行情快照负责。
4. 不在第一阶段重写所有 Provider；先抽象执行框架，再逐类迁移。

## 4. 10 年 K 线任务已验证能力

| 能力 | 当前 10 年 K 线表现 | 通用化后的要求 |
|---|---|---|
| 待处理 item 生成 | 从资产池读取主板股票，按 K 线覆盖度和水位筛选 | 每个数据域定义自己的 item 生成器 |
| 断点续跑 | 已有完整 10 年覆盖的标的跳过 | 通过 coverage + watermark 跳过已完成 item |
| 任务 worker | `max_workers=8` 消费标的队列 | 每个任务单独配置 worker，可热读取 |
| 源级限流 | 数据源有单独 `rate_policies` | 所有外部源必须经过 SourceGate |
| Provider 降级 | Eastmoney Direct -> Tencent Direct -> AKShare wrapper | 每个 data_domain 配置 source chain |
| 失败处理 | 单标的失败不阻断整批，写水位和 raw record | 单 item 失败不拖垮任务 |
| 失败重跑 | 失败项可后续手动重跑 | 所有可 item 化任务支持失败项重跑 |
| 进度展示 | 展示批次、完成数、失败数、吞吐量 | 所有任务采用同一进度协议 |

## 5. 通用执行模型

### 5.1 核心概念

| 概念 | 说明 |
|---|---|
| TaskDefinition | 来自调度配置的任务定义，包括 `job_name`、`sync_task_type`、`batch_size`、`max_workers`、`sources`、`lookback` 等 |
| TaskRun | 一次任务运行实例，负责进度、日志、取消、暂停和运行统计 |
| TaskItem | 一个可独立处理的同步单元，如一个股票的 K 线、一个股票的基本面、一个新闻 URL、一个交易对的 1h K 线 |
| ItemSelector | 根据资产池、覆盖度、水位和失败冷却生成待处理 item |
| WorkerPool | 按任务 worker 数从 item 队列取任务执行 |
| SourceGate | 按数据源控制有效并发、最小请求间隔、退避和熔断 |
| ProviderChain | 同一 item 的 Provider 尝试链，支持主源、备用源和 wrapper 兜底 |
| Watermark | 记录 item 在某个 data_domain/provider/timeframe 上的成功、失败、下次重试时间和错误摘要 |
| ProgressRecorder | 把任务、阶段、item、日志、吞吐量和源状态写入 Redis |

### 5.2 执行流程

```text
读取 TaskDefinition
  -> ItemSelector 生成待处理 item
  -> 跳过已完整覆盖 / 未到重试时间 / 已暂停任务
  -> WorkerPool 消费 item
  -> SourceGate 获取源令牌
  -> ProviderChain 逐源请求
  -> Normalizer 标准化
  -> 批量写入事实表
  -> 更新 Watermark
  -> 写入 ProgressRecorder
  -> 汇总 TaskRun 结果
```

### 5.3 运行态存储边界

| 数据 | 存储位置 | 原因 |
|---|---|---|
| 任务总进度、阶段进度、实时日志、吞吐量 | Redis | 运行态数据，过期即可 |
| 失败原因摘要、下次重试时间、最新成功水位 | PostgreSQL `data_sync_watermarks` | 断点续跑和重跑需要持久化 |
| 原始响应和失败 payload | `raw_records` | 审计和排查需要 |
| 标准事实数据 | PostgreSQL / TimescaleDB | 业务消费 |
| 长期任务历史 | 后续可选 `data_sync_task_runs` | MVP 阶段不强制 |

## 6. 并发策略

### 6.1 四层并发

| 层级 | 控制对象 | 配置来源 | 说明 |
|---|---|---|---|
| 调度器并发 | 同时运行多少个 job | `max_concurrent_jobs` | 当前为 4 |
| 资源池并发 | 同一类 job 最多同时运行多少个 | `resource_pools` + job `resource_pool` | 隔离实时、重采集、正文补抓、Agent、分析和维护任务 |
| 任务 worker | 一个 job 内同时处理多少 item | job `params.max_workers` | 页面配置项，尽量热生效 |
| 源有效并发 | 同一个数据源同时多少请求 | `rate_policies` | 不随 worker 线性放大 |

默认资源池如下：

| 资源池 | 默认并发 | 适用任务 |
|---|---:|---|
| `realtime` | 1 | 盘中行情、盘中触发器、轻量风险情绪 |
| `collection_heavy` | 2 | K 线、基本面、资金流、新闻列表、风险源采集 |
| `article_enrichment` | 1 | 新闻正文二次补抓 |
| `analytics` | 1 | 技术初筛、候选池合并、推荐计算、质量检查 |
| `agent` | 1 | Agent 消费、高风险复核 |
| `maintenance` | 1 | 回测、复盘、低频维护 |
| `default` | 跟随全局上限 | 兼容未显式分类的旧任务 |

### 6.2 热配置规则

1. `max_workers`：下一次提交 item 前读取，尽量做到当前任务热生效。
2. `batch_size`：下一批 item 生成前读取。
3. `limit`：对“本次最多处理多少 item”生效，当前任务运行中可以在下一批次边界生效。
4. `resource_pools`：可在数据同步配置页逐个资源池调整；保存后写入调度 JSON，调度器下一轮选 job 前按文件变更热加载；正在运行的 job 不会被强制中断。
5. `rate_policies`：SourceGate 每次取令牌前读取或定期刷新，避免重启才能降速。

### 6.3 推荐默认值

| 任务类型 | 任务 worker | 源有效并发 | 最小间隔 | 说明 |
|---|---:|---:|---:|---|
| A 股日 K | 4 到 8 | 1 到 2 | 0.5s 到 1s | 已验证可批量运行，但需要源级退避 |
| A 股实时行情 | 1 | 1 | 30s | 优先全市场 snapshot，不按单股逐个请求 |
| A 股基本面/估值 | 2 到 4 | 1 | 1s 到 3s | 数据源重，失败时降级为因子缺失 |
| A 股资金流 | 2 到 4 | 1 到 2 | 1s 到 3s | 可按榜单/标的增量 |
| 新闻列表 | 2 到 4 | 1 到 2 | 2s 到 5s | 关注实时性，但避免全市场正文抓取 |
| 新闻正文 | 1 到 2 | 1 | 5s 到 10s | 二次抓正文，失败后延迟补抓 |
| 风险情绪 | 2 到 4 | 1 到 2 | 1s 到 5s | 多源组合，单源失败只影响该风险组 |
| Crypto K 线 | 4 | 3 | 0.05s 到 0.2s | 交易所 API 相对稳定，但仍需限频 |

## 7. 降级策略

### 7.1 降级类型

| 类型 | 场景 | 处理方式 |
|---|---|---|
| 等价源降级 | K 线、部分板块成员、部分行情接口 | 主源失败后切备用源，输出同一结构 |
| 部分数据降级 | 基本面、估值、风险、事件 | 缺哪组记录哪组，不让整任务失败 |
| 延迟补全 | 新闻正文、公告详情 | 先保存列表和摘要，正文失败后标记待补 |
| 跳过降级 | 数据源熔断或未到重试时间 | 本轮跳过 item，等待下轮或手动重跑 |
| 推荐层降级 | 因子组缺失 | 记录缺失组、降低置信度，不输出伪完整结论 |

### 7.2 ProviderChain 规则

每个 `sync_task_type` 需要声明：

```text
data_domain
  -> preferred_sources
  -> fallback_sources
  -> normalizer
  -> watermark_provider
  -> failure_policy
```

示例：

```text
market_bars.ashare.1d
  -> eastmoney:direct:kline
  -> tencent:direct:kline
  -> akshare:stock_zh_a_hist
  -> normalize_market_bars
  -> provider=akshare:stock_zh_a_hist_tx
  -> 失败写 watermark，不阻断整批
```

## 8. 各数据域改造方案

### 8.1 A 股日 K 任务

适用任务：

- `ashare.bars.1d.midday_partial`
- `ashare.bars.1d.close_final`
- `ashare.bars.1d.revision`
- `ashare.bars.1d.bootstrap`

要求：

1. 全部复用 K 线 item selector。
2. 全部复用 Eastmoney -> Tencent -> AKShare 的 ProviderChain。
3. 按 `is_closed` 和 `status` 区分 partial/final/revision。
4. `bootstrap` 不自动重试，日常任务保留失败冷却和后续补漏。

### 8.2 A 股基本面与估值

适用任务：

- `ashare.fundamentals`

要求：

1. item 粒度为单股票或单报告期股票。
2. 成功写 `fundamental_snapshots` 和 valuation 相关表。
3. 单股票失败写 `data_sync_watermarks`，不让整批失败。
4. 没有等价备用源时，不强行切源；在因子层标记 `fundamental/valuation` 缺失。
5. 支持 `only_failed_or_stale`，避免每 12 小时重复扫完整资产池。

### 8.3 A 股资金流

适用任务：

- `ashare.capital_flow`

要求：

1. item 粒度优先为榜单批次，其次为单股票补缺。
2. 资金流源失败时只影响 `capital_flow` 因子组。
3. 失败写水位，后续按冷却补跑。
4. 资金流归一化必须继续过滤非 6 位股票代码和非主板个股。

### 8.4 新闻、公告和正文补全

适用任务：

- `ashare.events`
- `ashare.news_articles`

要求：

1. 新闻列表和正文补全拆开。
2. 新闻列表写事件记录、来源、标题、摘要、链接和发布时间。
3. 正文补全 item 粒度为新闻 URL。
4. 正文失败不影响新闻列表入库，只标记待补全。
5. 正文抓取严格低并发，防止被新闻站点拒绝。
6. 新闻保留策略由事件数据生命周期单独控制，过旧新闻可清洗归档。

### 8.5 风险情绪

适用任务：

- `ashare.risk_sentiment`

要求：

1. ST、热榜、涨停池、龙虎榜、大宗交易、融资融券等源拆成子阶段。
2. 单子阶段失败不让整个风险任务失败。
3. 每个风险源写独立 watermark。
4. 推荐层读取时按风险组缺失降级。

### 8.6 Crypto K 线与衍生品

适用任务：

- `crypto_future.bars.1h`
- `crypto_spot.bars.1h`
- `crypto_future.derivatives`

要求：

1. 复用 item 队列模型。
2. `ccxt_fetch_ohlcv` 和 Binance native 源走统一 SourceGate。
3. 交易对级失败不影响其他交易对。
4. 7x24 市场使用自己的 stale 规则，不套 A 股交易日历。

| 区域 | 字段 |

| 任务列表 | 任务名、状态、整体进度、worker、源有效并发、失败数、剩余数 |

| 控制 | 保存配置、保存并执行、暂停、继续、取消、失败项重跑 |

## 10. API 设计

### 10.1 查询任务定义

```http
GET /api/data/scheduler/jobs
```

返回调度配置、任务参数、运行期控制参数、源级限流策略。

### 10.2 更新单任务配置

```http
PUT /api/data/scheduler/jobs/{job_name}
```

支持更新：

- `enabled`
- `limit`
- `batch_size`
- `max_workers`
- `schedule_type`
- `run_at`
- `rate_policy_overrides`

### 10.3 执行单任务

```http
POST /api/data/scheduler/jobs/{job_name}/run
```

只启动一个手工任务实例，并使用原子锁防止重复启动。

### 10.4 控制任务

```http
POST /api/data/scheduler/jobs/{job_name}/pause
POST /api/data/scheduler/jobs/{job_name}/resume
POST /api/data/scheduler/jobs/{job_name}/cancel
POST /api/data/scheduler/jobs/{job_name}/rerun-failed
```

### 10.5 查询进度

```http
GET /api/data/scheduler/progress
GET /api/data/scheduler/jobs/{job_name}/progress
```

返回 Redis 中的运行态快照。

## 11. 测试策略

| 类型 | 重点 |
|---|---|
| 单元测试 | item selector、水位判断、ProviderChain 降级、SourceGate 限流 |
| 集成测试 | 单任务小批量真实运行、失败不阻断、断点续跑 |
| 回归测试 | K 线 full/bootstrap、midday、close_final、revision 均不退化 |
| 前端测试 | 任务状态一致性、失败原因弹窗、配置保存与执行 |
| 压力验证 | worker 从 1/2/4/8 梯度测试，观察失败率和吞吐量 |

## 12. 实施顺序

1. 抽象通用 `TaskItem`、`TaskRun`、`ProviderAttempt` 和 `ProviderChain` 数据结构。
2. 先把 A 股日常 K 线任务迁移到与 10 年 K 线一致的执行模型。
3. 为基本面、资金流、事件、风险补齐 watermark 和 item 级失败记录。
4. 为新闻正文补全任务接入低并发 URL item 队列。
5. 统一前端展示字段：任务 worker、源有效并发、吞吐量、失败原因和重跑入口。
6. 为 Crypto K 线和衍生品接入相同的 item 队列与 SourceGate。
7. 清理旧的直接批处理分支，只保留兼容入口。

## 13. 风险与约束

1. 数据源没有公开 SLA，限频必须保守。
2. 不同数据域不能共享完全相同的 fallback，必须按输出结构匹配。
3. 任务运行态放 Redis，Redis 清空后仍要能通过数据库 watermarks 恢复。
4. 页面热配置应在 item 边界生效，不强行中断正在请求的外部接口。
5. 推荐层必须显式消费缺失因子组，不能把缺数据误判为低风险。
