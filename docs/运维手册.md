# 运维手册

> 适用范围：本手册覆盖 finance-agent 的本机常驻调度器、API 服务、Docker 调度器模板、数据健康检查和缺口补采流程。当前 API 没有认证层，默认只允许绑定 `127.0.0.1`；如需局域网访问，必须先接入反向代理与鉴权，不得直接暴露。

## 1. 日常巡检

### 1.1 调度器心跳

基础数据调度器常驻运行时应显式写入状态文件和事件日志：

```powershell
.\.venv\Scripts\python.exe scripts\data\run_base_data_scheduler.py `
  --loop `
  --status-file runtime/base_data_scheduler/status.json `
  --event-log-file runtime/base_data_scheduler/events.jsonl
```

健康检查命令：

```powershell
.\.venv\Scripts\python.exe scripts\data\run_base_data_scheduler.py `
  --health-check `
  --status-file runtime/base_data_scheduler/status.json `
  --health-max-age-seconds 300
```

判断规则：

- 退出码 `0`：状态文件存在，`updated_at` 未过期，最近任务没有最终失败。
- 退出码 `2`：状态文件缺失、过期、格式错误，或最近任务失败。
- `runtime/base_data_scheduler/status.json` 用于判断常驻进程是否还活着。
- `runtime/base_data_scheduler/events.jsonl` 用于追踪最近任务开始、成功、失败、重试和停止事件。

### 1.2 数据健康

每日或每次大批同步后运行：

```powershell
.\.venv\Scripts\python.exe scripts\data\check_base_data_health.py --cache-backend redis > runtime/base_data_health.json
```

重点看这些字段：

- 关键事实表数量是否明显异常。
- 最近 Provider 状态是否连续失败。
- Redis 中是否存在源熔断状态。
- `backfill_jobs` 是否生成了缺口补采任务。
- A 股、基金、Crypto 的行情覆盖是否落后。

## 2. 常驻部署

### 2.0 数据库连接池

API、MCP 服务和基础数据调度器都会复用同一进程内的 SQLAlchemy Engine/sessionmaker。默认连接池偏保守，避免长进程反复创建 Engine 后堆积 PostgreSQL idle backend：

- `FINANCE_AGENT_DB_POOL_SIZE`：常驻连接池大小，默认 `10`。
- `FINANCE_AGENT_DB_MAX_OVERFLOW`：短时溢出连接数，默认 `20`。
- `FINANCE_AGENT_DB_POOL_TIMEOUT_SECONDS`：等待连接超时时间，默认 `30` 秒。
- `FINANCE_AGENT_DB_POOL_RECYCLE_SECONDS`：连接回收时间，默认 `1800` 秒。

本地开发如只启动单个 API 或调度器，保持默认即可。真实并发压测前可以按服务进程数估算：`单进程最大连接 = pool_size + max_overflow`，当前默认单进程最大为 `30`。根目录 `docker-compose.yml` 已把本地 TimescaleDB `max_connections` 提高到 `300`，总连接数仍应预留迁移、手工查询和监控连接余量。

### 2.1 Windows 任务计划

推荐在 Windows 生产机使用任务计划注册常驻任务：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\windows\register_scheduler_task.ps1 -WhatIf
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\windows\register_api_task.ps1 -WhatIf
```

确认参数无误后去掉 `-WhatIf` 执行。API 服务模板默认监听 `127.0.0.1:8000`，不要改成 `0.0.0.0` 后直接暴露。

卸载任务：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\windows\unregister_tasks.ps1 -WhatIf
```

### 2.2 Docker

Docker 模板用于部署调度器，不包含数据库和 Redis：

```powershell
docker build -f deploy/docker/Dockerfile.scheduler -t finance-agent-scheduler:local .
docker compose -f deploy/docker/compose.scheduler.yml up -d
```

运行前确认环境变量：

- `FINANCE_AGENT_DATABASE_URL`：PostgreSQL / TimescaleDB 连接串。
- `FINANCE_AGENT_REDIS_URL`：Redis 连接串。
- `FINANCE_AGENT_CACHE_BACKEND`：生产建议使用 `redis`。

compose 会把宿主机 `runtime/` 挂载到容器 `/app/runtime`，因此状态文件、事件日志和 Cookie secret 都会保留在本机运行目录。

## 3. 常见故障

### 3.1 Redis 断连

现象：

- 任务监控页没有实时进度。
- Provider 熔断状态无法展示。
- 调度器仍可能继续跑，但进度快照不可用。

处理：

1. 检查 `FINANCE_AGENT_REDIS_URL` 是否正确。
2. 确认 Redis 服务可达。
3. 重新运行健康检查，确认 `cache_backend` 不再降级。
4. 如果 Redis 恢复后页面仍旧显示旧状态，刷新任务或等待下一次任务启动覆盖 Redis 进度。

### 3.2 源熔断

现象：

- 事件日志出现「Provider 熔断中，跳过本次采集」。
- `check_base_data_health.py` 输出中 Provider 状态连续失败。
- 单个数据源失败，但同一任务内其他源或其他标的仍继续处理。

处理：

1. 不要立即提高并发或频率。
2. 查看 `runtime/base_data_scheduler/events.jsonl` 中最近失败的 Provider、symbol 和错误摘要。
3. 等待熔断冷却结束，或在页面上对失败任务执行重跑。
4. 如果是同一源长时间失败，先降任务 worker，再排查网络、DNS、代理和上游接口。

### 3.3 Cookie 过期

东方财富 Cookie 默认自动保活，代码入口为 `ensure_eastmoney_cookie()`；强制刷新会调用 `refresh_eastmoney_cookie_file()` 并写入 `runtime/secrets/eastmoney_cookie.json`。

诊断命令：

```powershell
.\.venv\Scripts\python.exe -c "from finance_agent.data.providers.eastmoney_curl import ensure_eastmoney_cookie; print(ensure_eastmoney_cookie(force=True))"
```

相关环境变量：

- `FINANCE_AGENT_EASTMONEY_COOKIE`：手工指定 Cookie，优先级最高。
- `FINANCE_AGENT_EASTMONEY_COOKIE_FILE`：Cookie 文件路径，默认 `runtime/secrets/eastmoney_cookie.json`。
- `FINANCE_AGENT_EASTMONEY_COOKIE_AUTO_REFRESH`：设为 `0`、`false`、`no` 或 `off` 时禁用自动刷新。
- `FINANCE_AGENT_EASTMONEY_COOKIE_MAX_AGE_SECONDS`：Cookie 文件最大年龄，默认 12 小时。

如果自动刷新失败，先确认 Playwright / Edge / Chrome 可用，再手动访问东方财富页面验证网络。

### 3.4 任务卡住或无日志

处理顺序：

1. 查看 `runtime/base_data_scheduler/status.json` 的 `updated_at` 是否仍在更新。
2. 查看 `runtime/base_data_scheduler/events.jsonl` 是否还有 `job_start` / `job_success` / `job_error`。
3. 在任务监控页点击取消；如果页面提示没有找到任务，再检查后端父进程和采集子进程是否仍存在。
4. 重启前先确认没有重复的调度器实例，避免两个常驻进程同时采同一批数据。

### 3.5 PostgreSQL idle 连接堆积

现象：

- 健康检查或任务执行报 `too many clients already`。
- `pg_stat_activity` 中同一 `usename` 出现大量 `idle` 连接。

处理：

1. 先确认是否有重复的 API、MCP、调度器或 PyCharm 运行配置。
2. 用数据库侧查询统计连接状态：

```sql
SELECT state, count(*)
FROM pg_stat_activity
WHERE usename = 'finance_agent'
GROUP BY state
ORDER BY state;
```

3. 如只是历史遗留空闲连接，可在确认没有任务正在使用后由管理员终止 idle backend。
4. 新版连接层默认复用 Engine 并限制连接池；如果仍继续增长，优先检查是否有多进程重复启动，而不是提高 `max_connections`。

## 4. 数据缺口补采

推荐流程：

```powershell
.\.venv\Scripts\python.exe scripts\data\check_base_data_health.py --cache-backend redis > runtime/base_data_health.json
.\.venv\Scripts\python.exe -m finance_agent.cli data production backfill-plan --health-file runtime/base_data_health.json
```

`backfill_jobs` 会根据交易日历、K 线、资金流、基本面、事件、风险和 Crypto 衍生品缺口生成补采任务。执行前应先检查：

- 是否只补当前需要的市场。
- `batch_size` 是否适合当前源限流。
- 是否会与正在运行的常驻调度器重复。
- 是否有失败水位仍在冷却期。

上面的模块命令对应 CLI 语义为 `finance-agent data production backfill-plan`。

如果只想手工补单个任务，优先用页面「保存并执行」或调度器 `--run-once`，不要直接绕过水位表批量重刷。

## 5. 升级流程

1. 停止 Windows 任务计划或 Docker 调度器。
2. 确认没有采集子进程残留。
3. 拉取代码并安装依赖。
4. 执行数据库迁移：

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

5. 运行最小健康检查：

```powershell
.\.venv\Scripts\python.exe scripts\data\run_base_data_scheduler.py --print-plan
.\.venv\Scripts\python.exe scripts\data\check_base_data_health.py --cache-backend redis
```

6. 启动调度器和 API 服务。
7. 观察 `runtime/base_data_scheduler/status.json` 和 `runtime/base_data_scheduler/events.jsonl` 至少一个任务周期。

## 6. 安全约束

- 不提交 `.env`、`runtime/`、Cookie 文件、数据库密码或真实 API key。
- API 默认只绑定本机；没有鉴权前不得直接暴露到局域网或公网。
- Docker / Windows 模板中的连接串只能使用占位符或环境变量。
- 真实模型 API key 只允许放在本机环境变量或 secret 管理系统中。
