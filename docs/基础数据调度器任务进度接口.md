# 基础数据调度器任务进度接口

本文档定义 Web 任务监控页使用的运行态进度接口。任务进度、实时日志和吞吐指标只写入 Redis，不写入 PostgreSQL。业务数据结果仍写入标准数据表。

## 设计目标

- 前端可以展示每个调度任务的整体进度、阶段进度、剩余数量、失败数量和最近处理日志。
- 进度数据生命周期与任务频率同步：下一轮同名任务开始时清理上一轮运行态数据，同时设置 Redis TTL 作为兜底。
- Redis 不可用时不阻塞采集任务，接口返回降级状态，前端展示配置队列和健康提示。
- 不解析 `process.log` 作为结构化数据源；日志文件只用于人工排障。

## Redis Key

每次任务运行生成一个 `run_id`，推荐格式为 `{job_name}:{yyyymmddTHHMMSS}:{short_hash}`。

```text
base_data:task:{job_name}:current
base_data:task:{job_name}:run:{run_id}:snapshot
base_data:task:{job_name}:run:{run_id}:events
base_data:task:active
```

- `current`：字符串，指向当前 run_id。
- `snapshot`：JSON，当前任务进度快照。
- `events`：Redis List，最近进度事件，最多保留 200 条。
- `active`：JSON 或集合，当前仍在运行/最近完成的任务索引。

## TTL 策略

同名任务启动时：

1. 读取 `base_data:task:{job_name}:current`。
2. 如果存在旧 run_id，删除旧 `snapshot` 和 `events`。
3. 写入新 run_id 和初始快照。

同时设置 TTL：

```text
ttl_seconds = max(interval_seconds + grace_seconds, min_ttl_seconds)
grace_seconds = 1800
min_ttl_seconds = 900
```

例如：

- `ashare.events`：5 分钟频率，TTL 15 分钟。
- `ashare.bars.1d`：1 小时频率，TTL 90 分钟。
- `ashare.fundamentals`：12 小时频率，TTL 12.5 小时。

## 事件结构

```json
{
  "event_type": "symbol_completed",
  "job_name": "ashare.bars.1d",
  "run_id": "ashare.bars.1d:20260603T153012:8f3a",
  "stage_key": "sync_market_bars",
  "symbol": "600519",
  "name": "贵州茅台",
  "status": "completed",
  "batch_index": 18,
  "batch_count": 27,
  "item_count": 180,
  "retry_count": 0,
  "retry_after_seconds": null,
  "next_retry_at": null,
  "provider_key": "akshare:stock_zh_a_hist_tx",
  "error_category": null,
  "error_message": null,
  "created_at": "2026-06-03T15:35:12+08:00"
}
```

当单标的采集失败且已写入水位延迟重试时，`symbol_failed` 事件会额外带上：

- `retry_after_seconds`：本次失败后建议等待多久再重试。
- `next_retry_at`：下一次允许重试的绝对时间。
- `provider_key`：触发失败的数据源或逻辑 Provider。
- `error_category`：粗分错误类型，例如 `network`、`rate_limit`、`empty`、`unknown`。

事件类型：

- `job_started`
- `stage_started`
- `batch_started`
- `symbol_started`
- `symbol_completed`
- `symbol_failed`
- `symbol_retry`
- `batch_completed`
- `job_completed`
- `job_failed`

## 源状态结构

任务快照可以携带 `source_rate_states`，用于解释为什么页面上的任务 worker 已经调大，但实际请求速度仍受数据源保护策略约束。

```json
[
  {
    "source_key": "eastmoney_kline",
    "configured_max_concurrency": 2,
    "effective_max_concurrency": 1,
    "min_interval_seconds": 0.8,
    "in_flight": 1,
    "backoff_until": "2026-06-03T15:36:20+08:00",
    "circuit_open": false,
    "failure_count": 3,
    "success_count": 128,
    "last_error_message": "Connection closed abruptly"
  }
]
```

字段说明：

- `configured_max_concurrency`：配置中的源级并发上限。
- `effective_max_concurrency`：经过退避、熔断或动态降速后的当前有效并发。
- `in_flight`：当前正在请求该源的 item 数。
- `backoff_until`：源退避结束时间；为空表示未退避。
- `circuit_open`：源熔断是否打开。打开时任务可以跳过该源或进入备用源，不应让多个 worker 同时强打同一源。

## API

### GET `/api/data/scheduler/progress`

读取 Redis 中的任务进度快照、最近事件和等待队列。

查询参数：

- `event_limit`：每个任务返回的最近事件数量，默认 80，最大 200。

响应：

### GET `/api/data/scheduler/jobs`

读取调度器任务定义和每个任务的独立配置。前端任务配置面板必须以单任务为粒度展示和保存，不使用一个全局配置覆盖所有任务。

关键字段：

| 字段 | 说明 |
| --- | --- |
| `job_name` | 任务 ID，例如 `ashare.bars.1d.bootstrap` |
| `title` | 中文任务名称 |
| `description` | 中文任务说明，前端小字可悬停完整展示 |
| `enabled` | 是否启用 |
| `interval_seconds` | 调度频率 |
| `batch_size` | 单批 item 数量，不是任务总量上限 |
| `max_workers` | 任务内部 item worker 数 |
| `limit` | 单次 Provider 记录窗口或诊断上限，不能替代历史 K 线覆盖范围 |
| `rate_policies` | 源级限流策略 |

### PUT `/api/data/scheduler/jobs/{job_name}`

保存单个任务配置。支持热生效的字段包括：

- `enabled`
- `batch_size`
- `max_workers`
- `limit`
- `rate_policy_overrides`

热生效边界：

- `max_workers` 和 `rate_policy_overrides` 在下一只 item 提交前重新读取。
- `batch_size` 在下一批 item 生成时生效。
- 正在进行的外部请求不会被强制中断；如果需要立即停止，使用取消任务接口。

### POST `/api/data/scheduler/jobs/{job_name}/run`

手工执行单个任务。后端必须使用任务级原子锁，避免同一个 `job_name` 同时启动多份采集子进程。

### POST `/api/data/scheduler/jobs/{job_name}/pause`

暂停任务。暂停后 worker 不再提交新的 item，已经发出的外部请求允许自然结束并写入进度。

### POST `/api/data/scheduler/jobs/{job_name}/resume`

继续暂停中的任务。继续后从 Redis 快照和数据库水位恢复待处理 item。

### POST `/api/data/scheduler/jobs/{job_name}/cancel`

取消任务。取消会写入运行态状态、通知采集进程停止，并清理任务锁。后端需要同时处理父进程和子进程，避免页面看不到任务但锁仍提示 PID 运行中。

### POST `/api/data/scheduler/jobs/{job_name}/rerun-failed`

把失败 item 移交到后台队列重跑。重跑应遵守原任务的 SourceGate、失败冷却和 ProviderChain，不允许前端直接并发打满失败项。

## 前端展示

新增 Tab：`任务监控`。

- 左侧任务列表：全部、运行中、等待中、已完成、失败筛选。
- 右侧任务详情：核心指标、整体进度、阶段进度、实时日志、源状态、运行指标。
- 配置面板：每个任务单独展示 `batch_size`、`max_workers`、`limit` 和源限频配置，支持保存、保存并执行。
- 操作入口：运行中任务展示暂停、继续、取消；已失败或含失败 item 的任务展示失败项重跑。
- 悬停说明：任务描述、错误摘要、源状态小字和日志省略文本都应通过浏览器原生 `title` 或弹窗展示完整内容。
- 状态颜色：运行中使用蓝色，已完成使用绿色，等待中使用灰色，失败使用红色；列表和详情必须读取同一份快照状态，避免详情完成但列表仍显示运行中。
- 轮询频率：2 秒。
- 当 Redis 没有任务快照时，使用 scheduler config 展示等待队列。

## 实时行情连续验收

`scripts/integration/probe_realtime_quote_monitor.py` 是只读压力探针。它复用 HTTP 长连接按持仓 1 秒、重点池 5 秒采样，不写 PostgreSQL 业务事实；分钟 K 完整率由内存样本计算，全市场间隔只读 `data_snapshots`。

盘后 5 分钟结构冒烟：

```powershell
.venv\Scripts\python.exe scripts/integration/probe_realtime_quote_monitor.py --duration-minutes 5 --held-symbols 601222 601330 --radar-symbols 600405 002349
```

盘后结果必须为 `after_hours_snapshot`，验收状态为 `not_applicable`，不能冒充交易时段通过。交易日上午连续 120 分钟报告只有同时满足以下条件才返回 `passed`：持仓延迟 P95 不超过 1 秒、重点池延迟 P95 不超过 5 秒、服务端新鲜度 P99 不超过 3 秒、HTTP 丢失率低于 0.1%、返回覆盖率至少 99.9%、无时钟倒退、闭合 1 分钟 K 完整率至少 99.9%、全市场快照最大间隔不超过 300 秒。

2026-09-04 盘后 5 分钟结构冒烟记录：held 请求 285 次、radar 请求 60 次，两通道 HTTP 成功率和返回覆盖率均为 100%；held/radar 端到端延迟 P95 分别为 0.686 秒和 0.087 秒，重连数和时钟倒退均为 0。服务端质量状态为 `after_hours_snapshot`，验收正确返回 `not_applicable`。该结果只证明探针结构和盘后语义，不能替代交易日上午 120 分钟正式验收。
