# A 股停跑恢复补跑设计

- 日期：2026-08-23
- 状态：已批准，待编写实现计划
- 适用项目：`finance-agent`

## 1. 背景

项目已经具备交易日历、数据同步水位、事实表缺口筛选、Provider 降级、源级限频、Redis 进度、PostgreSQL 持久任务队列、调度依赖和失败项重跑能力，但这些能力目前仍是分散的：

- `DataBackfillPlanner` 能把健康检查结果转换为表级补采任务，但不能描述一次停跑恢复批次的冻结范围、步骤依赖和最终验收。
- `BaseDataScheduler` 能运行任务并恢复过期租约，但不知道一个停跑恢复批次是否真正补齐了事实数据。
- `collect_base_data.py` 能根据事实覆盖、水位和失败冷却筛选待采项，但不负责跨数据域编排。
- Redis 进度适合展示当前运行状态，不适合作为进程重启后的批次事实来源。
- 现有失败项重跑面向某次任务中的失败项，不等同于系统停跑若干交易日后的多数据域恢复。

因此需要新增一个批次级补跑能力：项目恢复启动后自动检测缺口，生成可审阅计划，经用户确认后，按依赖补齐 A 股生产数据，并在事实验收通过后恢复派生分析与推荐。

## 2. 已确认决策

1. 第一期只覆盖 A 股完整恢复链路，不扩展到基金和 Crypto。
2. 资产范围使用当前生产配置中的可交易资产池。
3. 项目启动后自动检测缺口，但必须由用户确认后才执行补跑。
4. 每个批次冻结到最近一个已完整收盘的 A 股交易日，不包含当前未闭合交易日。
5. K 线逐交易日补齐；其他数据按各自时间语义恢复，不复制、插值或伪造数据。
6. 补跑期间采用分层门控：实时行情和事件采集继续，重复目标合并去重，派生分析与推荐等待核心质量闸门。
7. 完成标准为“核心数据完整、例外有证据且可解释”，不能仅以任务没有报错作为完成依据。
8. 补跑完成后只重建冻结截止日对应的最新派生截面，不逐日回放停跑期间的历史推荐。

## 3. 目标与非目标

### 3.1 目标

- 自动发现停跑后 A 股生产资产池的数据缺口。
- 生成带范围、数量、风险和预计请求量的补跑计划。
- 支持用户确认、暂停、继续、取消和重启后续跑。
- 复用现有采集器、水位、限频、Provider 降级和持久任务队列。
- 根据数据域语义补齐交易日历、日 K、基本面、估值、资金流、新闻公告和风险情绪数据。
- 对无法追溯的数据形成带证据的例外清单。
- 在核心事实通过质量验收后，仅运行一次最新派生链路。
- 保证计划确认、任务提交、进程恢复和事实写入均具备幂等性。

### 3.2 非目标

- 不在第一期补跑基金、Crypto 现货、Crypto 合约或衍生品数据。
- 不构建历史推荐逐日回放或历史决策重演系统。
- 不复制前一日快照、不插值 K 线、不用零值填补事实缺口。
- 不重写现有采集脚本、Provider 链、任务队列或调度器。
- 不保证补回上游源已经删除且没有替代证据的历史数据；这类情况必须形成例外。
- 不把 Redis 作为补跑批次的持久事实来源。

## 4. 方案选择

### 4.1 采用方案：独立补跑批次编排模块

在缺口检测与现有调度器之间增加一个深模块 `DataRecoveryModule`。模块通过较小接口隐藏数据域规则、依赖图、任务分区、恢复状态、质量验收和门控逻辑。

该方案复用现有执行能力，同时提供批次级审计、断点续跑和完成判定。

### 4.2 未采用方案

#### 动态生成临时调度任务

仅扩展 `DataBackfillPlanner` 并把临时任务合入调度 JSON，改动较少，但状态会分散在 JSON、Redis、事件日志和任务表中，无法稳定回答“这一批是否已补完”。

#### 回放停跑期间所有调度时刻

按停机窗口机械回放原调度任务会产生大量重复请求，而且基本面、新闻、风险等数据不适合逐日回放，无法正确表达不可追溯缺口。

## 5. 总体架构

### 5.1 外部接口

`DataRecoveryModule` 对调用者只暴露以下接口：

```python
preview(request) -> RecoveryPlan
approve(plan_id, plan_hash) -> RecoveryRun
control(run_id, action) -> RecoveryRun
get(run_id) -> RecoveryRunStatus
```

接口约束：

- `preview` 只生成或复用草稿，不写入业务事实表。
- `preview` 可以只读调用现有 Provider 获取新鲜元数据，但只把规范化快照写入补跑草稿，不提前更新业务表。
- `approve` 必须携带用户看到的 `plan_hash`，并且幂等。
- `control` 的 `action` 只允许 `pause`、`resume` 和 `cancel`。
- `get` 返回 PostgreSQL 中的稳定状态，并可叠加 Redis 中的实时进度。
- 调用者不需要了解数据域任务名、Provider、水位或调度依赖。

### 5.2 内部职责

模块内部包含以下实现职责，均不直接暴露给控制台、CLI 或 MCP：

1. `GapDetector`：依据交易日历、生产资产池、资产生命周期、事实表和水位识别缺口。
2. `PlanBuilder`：生成冻结范围、步骤依赖、目标区间、预计请求量和计划哈希。
3. `RecoveryExecutor`：把补跑步骤转换为现有调度任务，并提交给持久任务队列。
4. `RecoveryVerifier`：任务结束后重新读取事实表，验证目标是否真正完成。
5. `RecoveryGate`：控制普通调度任务在补跑期间是否允许执行。
6. `RecoveryRepository`：持久化批次、步骤和目标区间。

### 5.3 与现有模块的 seam

- `collect_base_data.py` 继续负责单项采集、Provider 降级、源级限频、水位和事实 upsert。
- `PersistentTaskQueue` 继续负责调度任务租约、领取、续租、完成、失败和过期恢复。
- `DataBackfillPlanner` 保留表到数据域任务的映射，作为 `PlanBuilder` 的内部规则来源之一。
- `DataSyncControlService` 只适配补跑模块接口，不承载补跑规则。
- `BaseDataScheduler` 只负责执行和门控检查，不负责计算缺口。
- 前端只展示计划、发出确认和控制命令，不自行推断完成状态。

## 6. 时间与范围语义

### 6.1 冻结截止日

所有 A 股日期判断使用 `Asia/Shanghai`。

`cutoff_date` 必须是 `market_calendars` 中最近一个满足以下条件的日期：

- `market='ashare'`；
- `is_trading_day=true`；
- 当日 `close_at` 已早于当前时间；
- 日历记录状态有效。

当前交易日尚未收盘时，不得进入补跑范围。批次创建后 `cutoff_date` 不再移动；运行期间产生的新日期由正常调度或下一补跑批次处理。

若数据库交易日历没有覆盖当前日期，或日历新鲜度不达标，`preview` 必须通过现有交易日历 Provider 做只读获取，以该规范化结果计算 `cutoff_date`。只读获取失败时，计划标记为不可执行，不能退化成按工作日猜测交易日。

### 6.2 资产范围

计划使用当前生产配置选定的 A 股可交易资产池快照，并保存 `universe_id`、快照时间和快照哈希。

若数据库资产池快照过期，`preview` 通过现有 Universe Provider 做只读获取并应用既有可交易资格规则。计划保存规范化后的资产标识集合及其哈希；第一执行阶段再使用现有 Repository 幂等写入该快照。

若确认时资产池或交易日历版本已变化，`approve` 返回 `stale_plan`，生成新计划并要求重新确认，不允许静默扩大用户已确认的范围。

### 6.3 缺口起点

缺口起点不直接采用调度器最后心跳时间。每个数据域根据真实事实覆盖和业务新鲜度独立计算：

- K 线按资产有效期内的缺失交易日计算。
- 基本面按冻结截止日依法应有的报告期计算。
- 估值按最新有效截面及历史源能力计算。
- 资金流、新闻公告和风险情绪按可查询窗口、水位和事实覆盖计算。

调度器停机时间只作为诊断信息展示，不作为补数真实性依据。

## 7. 补跑数据流

```text
冻结批次并启用 RecoveryGate
  -> 校验交易日历和生产资产池版本
  -> 物化资产级或数据域级缺口区间
  -> 补齐核心日 K
  -> 并行恢复相关事实数据
  -> 重新检测残余缺口并有限重试
  -> 执行数据质量与推荐就绪度验收
  -> 重建最新派生截面
  -> 解除 RecoveryGate
```

### 7.1 步骤依赖

| 阶段 | 步骤 | 依赖 | 是否可并行 |
| --- | --- | --- | --- |
| P0 | 冻结批次、设置门控 | 无 | 否 |
| P1 | 校验并持久化计划中冻结的交易日历与生产资产池快照 | P0 | 两者可并行 |
| P2 | 缺口目标物化 | P1 | 按数据域并行 |
| P3 | 闭合日 K 补跑 | P2 | 按资产分区并行 |
| P4 | 基本面、估值、资金流、新闻公告、风险情绪 | P2；需要日期解释的目标依赖 P3 | 数据域之间并行 |
| P5 | 残余缺口复检与有限重试 | P3、P4 | 按数据域并行 |
| P6 | 数据质量和推荐就绪度验收 | P5 | 否 |
| P7 | 最新派生截面重建 | P6 通过 | 按现有依赖图执行 |
| P8 | 最终验收、生成例外报告、解除门控 | P7 | 否 |

### 7.2 最新派生截面

P7 只针对 `cutoff_date` 运行一次最新链路：

```text
data_quality_refresh
  -> technical_screening_refresh / structural_methodology_refresh
  -> universe_merge / universe_avoid_pool_rebuild
  -> recommendation_pipeline
  -> trigger_evaluation（按现有策略决定是否执行）
```

指标和因子继续复用现有推荐链路的计算与写库规则。第一期不生成停跑期间每天的历史推荐。

## 8. 各数据域恢复规则

| 数据域 | 目标选择 | 成功判定 | 允许的例外 |
| --- | --- | --- | --- |
| 交易日历 | 补到 `cutoff_date` | 日期范围完整且交易日标识有效 | 上游日历不可用时不得继续 K 线完成判定 |
| 生产资产池 | 当前生产配置中的可交易资产 | 快照完整并保存版本哈希 | 明确被资格规则排除的资产 |
| 闭合日 K | 资产有效期内缺失交易日 | 事实表存在闭合、可用 K 线 | 上市前、退市后、休市日、经证据确认的停牌 |
| 基本面 | 截止日依法应有的报告期 | 报告期达到要求 | 尚未到法定披露截止日、源端终态不可用 |
| 估值 | 最新有效截面和源端可用历史窗口 | 最新截面达到质量策略 | 停牌、亏损或源端不提供 PE/PB，不写零值 |
| 资金流 | 停跑窗口内源端支持的范围 | 事实覆盖达到该源窗口要求 | 已超出源端历史保留期 |
| 新闻公告 | 停跑窗口内列表和待补正文 | 列表已查询，正文状态终结 | 源端已删除或无法追溯，必须保留 URL/错误证据 |
| 风险情绪 | 各风险子源支持的历史窗口 | 子源水位和事实状态达到策略 | 源端无历史接口或已确认空结果 |

空响应不能直接解释为停牌或无事件。对于核心 K 线，必须由资产生命周期、停复牌事实或第二 Provider 提供证据。

## 9. 持久化模型

### 9.1 `data_recovery_runs`

保存批次级事实，主要字段包括：

- `run_id`
- `market`
- `universe_id`
- `universe_snapshot_at`
- `universe_snapshot_hash`
- `gap_start_date`
- `cutoff_date`
- `plan_hash`
- `status`
- `gate_status`
- `requested_by`
- `approved_by`
- `summary`
- `quality_result`
- `created_at`、`approved_at`、`started_at`、`finished_at`、`updated_at`

### 9.2 `data_recovery_steps`

保存逻辑阶段和依赖，主要字段包括：

- `step_id`
- `run_id`
- `phase`
- `data_domain`
- `status`
- `depends_on`
- `target_count`
- `completed_count`
- `retryable_count`
- `exception_count`
- `task_params`
- `attempt_round`
- `started_at`、`finished_at`、`updated_at`

一个步骤可以提交多个现有 `scheduler_task_runs`。关联信息放入任务 payload：`recovery_run_id`、`recovery_step_id` 和 `partition_hash`，不复制任务租约状态。

### 9.3 `data_recovery_targets`

使用区间压缩保存缺口，不为每个资产和每个日期机械创建一行。主要字段包括：

- `target_id`
- `run_id`
- `step_id`
- `data_domain`
- `asset_id`，市场级来源允许为空
- `gap_start_at`
- `gap_end_at`
- `granularity`
- `expected_count`
- `status`
- `exception_code`
- `exception_evidence`
- `last_error`
- `next_retry_at`
- `updated_at`

目标唯一约束覆盖批次、数据域、资产、时间区间和粒度。

### 9.4 状态机

```text
draft
  -> approved
  -> running
  -> verifying
  -> completed / completed_with_exceptions

running <-> paused
running / verifying -> attention_required -> running
任意非终态 -> cancelled
```

- `completed`：所有适用目标均经事实验证完成。
- `completed_with_exceptions`：仅剩不可重试、有证据且符合策略的例外。
- `attention_required`：仍有可重试核心缺口、未知缺口或数据冲突。
- `cancelled`：停止剩余工作，但不回滚已经写入的事实数据。

## 10. 幂等与并发

### 10.1 批次幂等

计划指纹由市场、资产池快照、冻结截止日、缺口集合和恢复策略版本计算。相同指纹存在草稿或活动批次时，返回原批次。

同一时间只允许一个 A 股活动补跑批次。互斥范围为 `data_recovery:ashare`。

### 10.2 任务幂等

补跑任务幂等键格式：

```text
recovery:{run_id}:{step_id}:{partition_hash}
```

重复确认、调度器重启或 worker 租约恢复不得产生新的逻辑任务。

### 10.3 事实幂等

继续使用现有事实表唯一约束和 upsert 规则。暂停、取消或进程异常不会回滚已经成功写入的数据；再次执行时通过事实覆盖和水位跳过已完成目标。

### 10.4 与正常任务去重

调度任务增加补跑策略分类：

- `always`：实时行情、事件列表等允许始终运行。
- `merge`：与补跑相同的数据域和目标使用幂等键或互斥键合并。
- `requires_open`：质量、指标、因子、筛选、候选池、推荐等任务要求 `RecoveryGate=open`。

## 11. 错误与例外处理

### 11.1 异常分类

| 分类 | 含义 | 处理 |
| --- | --- | --- |
| `transient` | 超时、限流、临时断连、服务端短暂失败 | 沿用水位冷却和指数退避 |
| `source_unavailable` | Provider 不再提供目标历史窗口 | 保存来源、窗口、响应和替代源证据 |
| `not_applicable` | 上市前、退市后、休市日、已确认停牌 | 从应补分母中排除 |
| `data_conflict` | 多源日期、价格、闭合状态冲突 | 停止自动放行，进入人工关注 |
| `unknown_gap` | 无法解释的事实缺失 | 作为核心阻塞项，不允许完成 |

### 11.2 重试规则

- 单次 Provider 失败继续使用现有水位 `next_retry_at` 和 SourceRateLimiter。
- 补跑模块只在冷却到期后发起下一轮，不进行紧密循环。
- 每轮结束后重新检测事实缺口，只对剩余目标创建新分区。
- 达到批次重试轮数后，`transient` 核心目标进入 `attention_required`，不自动转成例外。

### 11.3 任务成功不等于目标完成

采集任务返回成功后，`RecoveryVerifier` 必须重新查询事实表。Provider 返回成功、空结果或已处理数量均不能替代事实覆盖验证。

## 12. RecoveryGate

### 12.1 门控状态

- `recovering`：补跑正在执行；允许元数据、实时和补跑采集，阻止派生链路。
- `degraded`：草稿等待确认、批次暂停、取消或需要人工处理；影响可执行性的核心缺口仍存在。
- `open`：质量和推荐就绪度验收通过，允许派生任务执行。

### 12.2 放行依据

门控不另造一套推荐质量标准。`RecoveryVerifier` 复用现有健康检查和 `recommendation_readiness.executable`：

- 核心缺口导致 `executable=false` 时保持门控。
- 非阻塞缺口可以进入 `completed_with_exceptions`，并随最新派生结果保留警告。
- 被门控的普通任务返回 `blocked_by_recovery`，不记为失败，不消耗任务重试次数。

### 12.3 取消语义

取消批次只停止未领取的分区任务，并请求现有控制逻辑安全结束正在运行的任务。若核心缺口仍存在，门控保持 `degraded`；必须由新的补跑批次通过验收后解除。

## 13. 启动检测与控制入口

### 13.1 启动顺序

```text
恢复过期持久任务租约
  -> 执行只读缺口扫描
  -> 创建或复用 draft
  -> 设置 RecoveryGate
  -> 计算普通调度任务
```

扫描结果：

- 存在影响 `recommendation_readiness.executable` 的缺口：创建草稿并将门控设为 `degraded`。
- 仅存在非阻塞缺口：创建提醒草稿，但不阻止派生任务。
- 不存在缺口：不创建补跑批次，调度器正常启动。

### 13.2 HTTP 入口

建议提供以下入口，具体路由命名可在实现计划中按现有 FastAPI 风格校准：

- 预览补跑计划。
- 确认计划并启动。
- 查询批次列表和单批状态。
- 暂停、继续或取消批次。
- 查询异常与例外明细。

所有入口调用同一个 `DataRecoveryModule` 接口，不复制业务规则。

### 13.3 CLI 与 MCP

CLI 建议命令：

```text
finance-agent data recovery preview
finance-agent data recovery approve
finance-agent data recovery status
finance-agent data recovery pause
finance-agent data recovery resume
finance-agent data recovery cancel
```

MCP 复用同一应用接口，只提供参数解析和结果序列化。

### 13.4 控制台

在现有数据同步控制页面增加“停跑恢复”区域，展示：

- 缺口起始日、冻结截止日、资产池和资产数量。
- 各数据域目标数、预计请求量、阻塞项和不可追溯风险。
- 计划哈希、生成时间和过期状态。
- 批次阶段、完成率、当前分区、重试冷却和最近错误。
- 例外分类、证据和质量验收结论。
- 确认、重新检测、暂停、继续和取消操作。

## 14. 可观测性

### 14.1 批次摘要

每个批次至少输出：

- 总目标区间数和预计事实数。
- 各数据域完成、待重试、例外和阻塞数量。
- 当前门控状态和阻塞原因。
- 已提交、运行中、完成和失败的持久任务数。
- 吞吐量、Provider 限流状态和下一重试时间。
- 最终 `recommendation_readiness` 结果。

### 14.2 事件

建议增加以下结构化事件：

- `recovery_plan_created`
- `recovery_plan_stale`
- `recovery_run_approved`
- `recovery_step_started`
- `recovery_step_verified`
- `recovery_attention_required`
- `recovery_run_completed`
- `recovery_run_completed_with_exceptions`
- `recovery_run_paused`
- `recovery_run_resumed`
- `recovery_run_cancelled`
- `recovery_gate_changed`

事件不得包含数据库密码、Cookie、API key 或 Provider 私密响应正文。

## 15. 验收标准

补跑批次只有同时满足以下条件才可放行：

1. `cutoff_date` 不包含当前未闭合交易日。
2. 资产有效期内的适用闭合日 K 已补齐，或已形成有证据的允许例外。
3. 不存在 `transient`、`unknown_gap` 或 `data_conflict` 类型的未解决核心目标。
4. 现有 `recommendation_readiness.executable=true`。
5. 门控解除后只提交一次冻结截止日对应的最新派生链路。
6. 重复确认、重复启动和进程重启不产生重复逻辑任务。
7. Redis 数据清空后，批次状态仍可由 PostgreSQL、任务表和水位重建。
8. 所有不可补目标均带数据域、资产或逻辑来源、窗口、分类和证据。

## 16. 测试策略

### 16.1 规则测试

- 交易日、休市日、当前未收盘交易日判断。
- 上市前、退市后和停牌日期排除。
- 基本面应有报告期和估值最新截面判断。
- 资金流、事件和风险源历史窗口判断。
- 缺口区间压缩、计划哈希和过期计划拒绝。

### 16.2 状态机测试

- 正常状态路径。
- 暂停、继续、取消和人工关注恢复。
- 非法状态跳转拒绝。
- 取消后核心缺口仍存在时保持 `degraded`。

### 16.3 调度集成测试

- 活动补跑期间派生任务返回 `blocked_by_recovery`。
- 实时行情和事件任务继续运行。
- 相同补跑分区重复提交只生成一个持久任务。
- 正常任务与补跑任务命中相同目标时按策略合并。
- 租约过期后新进程恢复同一批次和同一任务。

### 16.4 事实验证测试

- Provider 返回成功但事实表仍缺数据时，目标不能完成。
- 空 K 线只有得到生命周期、停牌或第二 Provider 证据后才能转为例外。
- 多源冲突进入 `attention_required`。
- 已经通过事实验证的目标在重启后不再采集。

### 16.5 端到端恢复测试

构造生产资产池停跑多个交易日的数据库状态，验证：

1. 启动扫描自动生成草稿。
2. 用户确认后按依赖执行。
3. 执行部分任务后强制结束调度进程。
4. 新进程从原 `run_id` 和剩余缺口继续。
5. 最终通过质量闸门并只生成一次最新推荐截面。

### 16.6 回归与规模测试

- 覆盖当前生产资产规模和至少一年交易日窗口。
- 缺口检测使用集合查询，不允许逐资产 N+1 查询。
- 回归现有 K 线生命周期、水位、Provider 降级、持久队列、调度依赖、质量闸门、控制入口和前端状态展示测试。

## 17. 风险与约束

- 上游源的历史保留能力不同，补跑不承诺零例外。
- 当前事实模型可能无法直接证明历史停牌日期，需要风险源或第二 Provider 提供证据。
- 大范围缺口必须按资产和来源分区，并受现有 SourceRateLimiter 约束，不能因补跑绕过限频。
- 补跑门控若错误释放，会使过期数据进入推荐链路，因此放行必须以事实验证和现有 readiness 为准。
- 工作区当前存在多项未提交修改，后续实现必须避开无关变更，并在编辑任何符号前完成 GitNexus 上游影响分析。

## 18. 实施前置条件

项目 GitNexus 索引已确认与当前提交一致，但当前会话未暴露 GitNexus MCP，且本机 GitNexus CLI 与索引存储版本不兼容。开始实现前必须先恢复可用的 GitNexus MCP 或匹配版本 CLI，并对所有拟修改函数、类和方法运行上游影响分析；若返回 HIGH 或 CRITICAL 风险，必须先向用户报告影响范围。提交代码前必须运行 `detect_changes` 校验实际影响流程。
