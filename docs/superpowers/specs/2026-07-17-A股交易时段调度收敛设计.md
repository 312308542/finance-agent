# A 股交易时段调度收敛设计

## 背景

当前 `interval` 任务只按“本轮完成时间 + interval_seconds”计算下一次执行时间，
不会应用 `trading_day_policy`，也没有交易时段窗口。因此 A 股实时行情、资金流、
风险情绪和盘中触发评估会在收盘后以及夜间持续运行。

2026-07-16 的运行日志显示，15:00 至 24:00 期间实时行情启动 82 次、风险情绪
启动 81 次、资金流启动 16 次、盘中触发评估启动 34 次；收盘最终日 K 则按
15:50 和 17:30 准确执行两次。此次调整只收敛前述盘中任务，不改变最终日 K、
新闻公告、基本面和凌晨修正任务。

## 目标

- A 股盘中任务只在北京时间 09:30-11:30、13:00-15:00 按既有间隔运行。
- 实时行情、资金流和风险情绪在收盘后仅于 15:10、17:30 各补跑一次。
- 盘中触发评估在收盘后不再执行，日级触发继续由最终日 K 成功后唤醒。
- `ashare.bars.1d.close_final` 保持 15:50、17:30 两次执行。
- `ashare.events` 保持 `any_day` interval，避免漏掉盘后新闻和公告。
- 调度器重启、午休跨越、周末和配置热重载都能计算出正确的下一执行时间。

## 非目标

- 本次不改变实时行情、资金流和风险情绪的采集实现或数据结构。
- 本次不修改新闻公告、基本面、基金或数字货币任务。
- 本次沿用现有 `trading_day_policy` 的工作日判断，不新增数据库交易日历依赖；
  法定休市日识别作为独立改进处理。
- 本次不改变 interval 任务“完成后再等待一个间隔”的既有语义。

## 方案比较

### 方案一：只改成固定时间任务

把相关任务改成 `daily_time`，枚举盘中和收盘后的所有时间点。

优点是仅需修改配置；缺点是时间点数量大、难以维护，且无法自然表达“窗口内每
5 分钟/30 分钟执行”。不采用。

### 方案二：实现真正的 `trading_session` 语义

为任务增加 `session_windows`，窗口内按 `interval_seconds` 运行；复用 `run_at`
表达窗口外的固定补跑时间。调度器统一计算盘中、午休、收盘补跑和下一工作日。

优点是与现有设计文档一致，配置清晰，并能复用现有调度、热重载和任务监控链路；
缺点是需要修改调度模型、配置导出、控制接口和测试。采用此方案。

### 方案三：完全按数据变化触发

采集源发现版本或时间戳变化后再发布事件，后续任务由事件驱动。

优点是无无效轮询；缺点是各数据源缺少统一版本能力，改动会扩散到采集器、存储和
事件系统，超出本次问题范围。不采用。

## 调度模型

`BaseDataSchedulerJob` 新增：

```json
{
  "schedule_type": "trading_session",
  "interval_seconds": 300,
  "session_windows": ["09:30-11:30", "13:00-15:00"],
  "run_at": ["15:10", "17:30"],
  "timezone": "Asia/Shanghai",
  "trading_day_policy": "trading_day_only"
}
```

- `session_windows`：交易时段窗口，格式为 `HH:MM-HH:MM` 或
  `HH:MM:SS-HH:MM:SS`；开始时间必须早于结束时间，窗口不可重叠。
- `interval_seconds`：窗口内仍按“上次完成后等待固定间隔”运行。
- `run_at`：`trading_session` 下表示窗口外的固定补跑时间，可为空。
- `timezone`：窗口和固定时间都按该时区解释。
- `trading_day_policy`：窗口和固定补跑时间都必须通过日期策略。

`daily_time` 的 `run_at` 含义保持不变。普通 `interval` 和数字货币任务的行为保持
不变。

## 下一执行时间计算

### 初始启动或热重载

- 当前位于交易窗口内：立即到期，保持调度器重启后能恢复盘中采集。
- 当前早于首个窗口：安排到首个窗口开始时间。
- 当前位于午休：安排到下午窗口开始时间。
- 当前已收盘：选择当天尚未经过的最早 `run_at`。
- 当天窗口和补跑时间都已结束：安排到下一个允许日期的首个窗口。

### 一轮完成后

1. 先计算 `completed_at + interval_seconds`。
2. 若候选时间仍在当前窗口内，直接使用候选时间。
3. 若候选时间跨过窗口结束，安排到下一窗口开始时间。
4. 若交易窗口全部结束，安排到当天尚未经过的最早 `run_at`。
5. 当天无剩余补跑时间，安排到下一个允许日期的首个窗口。

窗口结束时刻包含在窗口内；例如 15:00 可以启动一次，完成后进入 15:10 补跑。
调度器仍依赖现有 `running`/`queued` 状态避免同一任务重入。

## 配置、接口与界面

- `DataSyncTaskPreview`、调度配置导出和解析支持 `session_windows`。
- 任务配置查询和更新接口读写 `session_windows`，保存前执行格式校验。
- 任务监控页展示并允许编辑交易时段窗口；非 `trading_session` 任务保留该字段但不参与调度。
- 内置默认配置和运行时生成配置使用同一字段，避免重建配置后恢复旧频率。
- 当前 `runtime/base_data_scheduler/base_data_scheduler.json` 被 Git 忽略；业务代码验证完成后
  通过现有配置生成/控制服务刷新，并重启调度进程使新代码生效。

## 下游行为

- 风险情绪成功后仍触发回避池重建，但只会随受限后的风险情绪任务运行。
- 盘中触发成功后仍触发 Agent 消费和高风险复核，但收盘后不会再由盘中链路唤醒。
- 最终日 K 的质量检查、技术筛选、结构分析和日级触发仍按 15:50、17:30 两轮执行。

## 错误处理

- 缺失或非法 `session_windows` 时拒绝加载 `trading_session` 任务，并给出任务名和字段错误。
- 无效时区、时间格式、倒置窗口或重叠窗口均在配置解析阶段失败。
- 热重载遇到非法配置时保留旧配置，沿用现有告警和下一轮重试行为。
- 单轮采集失败仍使用现有重试、熔断和下一执行时间计算，不额外制造快速重试。

## 测试与验收

### 单元测试

- 解析合法窗口，拒绝空窗口、倒置窗口和重叠窗口。
- 启动时间覆盖盘前、盘中、午休、收盘后补跑之间以及最后补跑之后。
- 完成时间覆盖仍在窗口内、跨午休、跨收盘、两次补跑之间和最后补跑之后。
- 周末顺延到下一个工作日。
- 普通 `interval`、`daily_time`、`manual` 和 `after_success` 行为不回归。

### 配置测试

- 四个目标任务导出正确的 `trading_session`、窗口和补跑时间。
- 最终日 K 和新闻公告配置保持不变。
- 控制接口和任务监控页能往返保存、展示 `session_windows`。

### 运行验收

- 15:00 后盘中触发评估不再启动。
- 实时行情、资金流和风险情绪在收盘后最多分别于 15:10、17:30 启动两次。
- 17:30 补跑完成后，下一执行时间落在下一个允许日期 09:30。
- 最终日 K 仍只在 15:50、17:30 启动。
