# 可交易资产池与观察链路重构设计

## 1. 背景

当前系统已经打通了基础数据采集、A 股主板 10 年日 K 初始化、基金历史行情/净值初始化、日常行情维护、数据质量、因子计算、推荐流水线、观察池和事件新闻抓取。但在产品语义上，`推荐观察池`、`活跃观察池`、`重点资产池` 被混在了一条简单链路里：

```text
推荐结果 -> 推荐观察池 -> active 观察项 -> 新闻重点资产
```

这条链路在 MVP 早期可以跑通闭环，但对真实金融产品不够清晰：

- 推荐结果不等于用户真正关注。
- 观察池不等于事件新闻优先级。
- `status=active` 只能表示观察项有效，不能表示高优先级。
- 用户实际可交易范围是主板股票和基金，但当前推荐、观察、新闻重点池仍可能混入不可交易标的。
- 历史行情初始化是一次性补齐能力，不应被理解成资产池本身；A 股主板个股、ETF/LOF 和开放式基金应拆成不同初始化任务。

本设计目标是将“资产准入、历史初始化、日常维护、技术初筛、推荐候选、研究跟踪、用户观察、事件重点”拆成职责明确且可实现的链路。

## 2. 设计目标

1. 明确 `可交易资产池` 是所有推荐和逐股高频任务的准入名单。
2. 明确历史初始化是多条一次性跑批能力：A 股主板个股 10 年日 K、ETF/LOF 历史日 K、开放式基金历史净值分别维护。
3. 将系统自动推荐与用户主动观察分离，避免推荐结果无脑塞进用户观察池。
4. 将新闻/公告/风险任务的 `事件重点池` 设计成动态优先级队列，而不是直接复用所有 active 观察项。
5. 优先复用现有表结构，降低改动成本。
6. 保留后续扩展到基金、持仓、量化实验室和更完整交易决策链路的空间。

## 3. 非目标

本阶段不实现真实下单。

本阶段不重建完整交易账户系统，只预留持仓优先级入口。

本阶段不大规模拆表。除非现有 `watchlists` / `watchlist_items` / `asset_recommendations` 无法表达核心语义，否则优先通过 `purpose`、`source_type`、`payload`、查询服务和调度规则完成。

本阶段不把指数、行业、概念作为可买资产。它们仍可作为市场上下文、因子背景和新闻归因来源。

## 4. 核心概念

### 4.1 可交易资产池

可交易资产池是系统允许进入推荐、研究跟踪、用户观察和逐股新闻优先抓取的资产集合。

当前产品范围：

- A 股主板股票。
- 可交易基金，例如 ETF、LOF、开放式基金。基金细分以现有基金数据链路成熟度为准逐步接入。

明确排除：

- 创业板、科创板、北交所股票，如果用户当前不能交易。
- 指数、行业、概念本身。
- 非标准股票代码、测试代码、占位资产。

可交易资产池不是任务，也不是 K 线表。它是准入名单，后续任务围绕它运行。

### 4.2 历史初始化任务边界

历史初始化是对可交易资产池内标的进行历史行情补齐的一次性能力，但不能设计成一个混合所有资产类型的大任务。当前应拆成三类：

| 初始化任务 | 资产范围 | 数据形态 | 结果表 | 说明 |
| --- | --- | --- | --- | --- |
| `ashare.bars.1d.bootstrap` | A 股主板个股 | 10 年日 OHLCV | `market_bars` | 只处理用户当前可交易的主板股票，支持断点续跑和覆盖足够跳过 |
| `fund.etf.bars.1d.bootstrap` / `fund.lof.bars.1d.bootstrap` | 场内 ETF / LOF | 历史日 OHLCV | `market_bars` | 与股票同为交易所成交行情，但应使用基金资产池和基金数据源 |
| `fund.open.nav.bootstrap` | 开放式基金 | 历史净值 | `fund_nav_snapshots` | 开放式基金不是标准 K 线，不应写入股票 OHLCV 语义 |

触发条件：

- 新资产首次进入可交易资产池。
- 标的历史行情覆盖不足目标窗口，例如主板股票 10 年日 K、ETF/LOF 10 年日 K、开放式基金可用历史净值。
- 数据清理后需要重建历史行情。
- 用户手动重跑失败标的。

执行规则：

- 支持断点续跑。
- 已满足覆盖要求的标的直接跳过。
- 失败记录到水位和失败明细，不在该任务内无限重试。
- 批次大小和 worker 数从任务配置读取，长任务运行期间应支持热加载。

这些初始化任务不应作为每小时或每天全量定时任务运行；完成后由日常维护任务按较小窗口补齐新增交易日和修正数据。

### 4.3 日常行情维护

初始化完成后，行情由生命周期任务维护。A 股主板个股、场内基金和开放式基金的维护节奏不同，不应混在同一个任务里。

| 任务 | 定位 | 建议范围 |
| --- | --- | --- |
| `ashare.bars.1d.midday_partial` | 午盘后同步当天未闭合日 K | A 股主板个股 |
| `ashare.bars.1d.close_final` | 收盘后同步当天最终日 K | A 股主板个股 |
| `ashare.bars.1d.revision` | 凌晨修正、补漏、复权变化校准 | A 股主板个股，短窗口 |
| `fund.bars.1d.close_final` | 场内基金收盘后同步最终日 K | ETF / LOF |
| `fund.open.nav.daily` | 开放式基金每日净值维护 | 开放式基金 |

盘中实时看盘不由日 K 生命周期任务承担，应走实时行情快照或后续分钟线/盘口接口。

### 4.4 技术初筛池

技术初筛池是历史行情初始化完成后的第一层粗筛结果，用于在基本面、资金流、新闻和风险因子尚未完全补齐前，先把走势结构较好的标的筛出来。它不是买入建议，也不等价于综合推荐。

建议短期复用现有 `screening_results` / `screening_result_items` 表，或者使用独立 `watchlists.purpose="technical_screening_pool"` 表达临时跟踪池。入池来源应标记为 `technical_screening`。

入池规则应保持轻量、可解释、可快速跑完：

- 标的属于可交易资产池，且历史行情覆盖达到最低窗口，例如最近 250 个交易日完整。
- 趋势条件：收盘价位于 MA60 或 MA120 上方，均线斜率向上或短中期均线形成多头排列。
- 动量条件：20 日、60 日收益为正，且相对回撤不过大。
- 风险条件：ATR、波动率、最大回撤未超过阈值，近期没有连续破位。
- 流动性条件：成交额或换手率达到最低要求，避免低流动性标的。

技术初筛池的有效期应短于系统研究跟踪池，例如 1 到 3 个交易日。它的输出进入后续数据质量、因子、风险、新闻补齐流程，满足综合条件后再进入推荐候选池或系统研究跟踪池。

### 4.5 推荐候选池

推荐候选池来自推荐流水线，落在 `recommendation_runs` 和 `asset_recommendations`。

它表示系统在某一轮策略下的候选判断，不表示用户已经关注，也不表示可以立即买入。

进入推荐候选池的前置条件：

- 属于可交易资产池。
- 数据质量达到最低要求。
- 日 K、因子、风险、事件等关键数据满足最低覆盖。
- 通过市场、品种和交易权限过滤。

候选结果允许包含 `watch`、`buy_candidate`、`avoid`、`reject` 等动作，其中 `avoid` 和 `reject` 不进入研究跟踪池。

### 4.6 系统研究跟踪池

系统研究跟踪池用于承接自动推荐结果，表示系统认为值得继续跟踪，但尚未被用户明确加入自选或观察。

建议使用现有 `watchlists` 表创建独立池：

```text
watchlist:default-owner:ashare:research
name: A 股系统研究跟踪池
purpose: system_research_pool
```

入池规则：

- 标的属于可交易资产池。
- 推荐动作不是 `avoid` / `reject`。
- 分数、置信度和数据质量达到阈值。
- 风险未触发硬过滤。
- 设置有效期，例如 3 到 7 天。

到期或条件失效后，条目状态应从 `active` 转为 `expired` 或 `removed`，并记录原因。

### 4.7 用户观察池

用户观察池表达用户明确关注的资产，不应被推荐任务直接无脑写入。

来源：

- 用户手动加入。
- 用户从系统研究跟踪池一键加入。
- 持仓自动加入。
- Agent 建议后由用户确认加入。

建议使用现有 `watchlists` 表表达：

```text
purpose: manual_watchlist / portfolio_watchlist / fund_watchlist
```

用户观察池的 `active` 表示用户仍在关注该标的，不等价于新闻最高优先级，也不等价于买入信号。

### 4.8 事件重点池

事件重点池是新闻、公告、风险任务运行时计算的动态优先级队列，不建议作为长期业务表持久化。

优先级来源：

1. 持仓资产。
2. 用户观察池资产。
3. 系统研究跟踪池中的高分资产。
4. 最近推荐候选中的高置信资产。
5. 近期风险、异动或数据质量异常资产。

输出用于 `ashare.events` 的逐股新闻抓取名单，例如 Top 200。列表可写入 Redis，TTL 与任务频率或下一次任务开始时间同步。

公告类全市场接口仍可保留全市场口径，不需要逐股拆到事件重点池。

## 5. 调整后的完整链路

```text
低频资产池刷新
  -> 生成可交易资产池
  -> 主板个股 / ETF-LOF / 开放式基金分别触发一次性历史初始化
  -> 午盘 partial / 收盘 final / 凌晨 revision / 基金净值日更维护行情
  -> 数据质量刷新
  -> 技术指标计算
  -> 技术初筛池
  -> 基本面 / 资金流 / 事件 / 风险等因子补齐
  -> 推荐候选池
  -> 系统研究跟踪池
  -> 用户确认后进入用户观察池
  -> 事件重点池动态计算
  -> 新闻、公告、风险、正文补抓
```

这条链路把数据层、推荐层、用户关注层和事件感知层拆开，避免一个 `active` 状态承担过多含义。

## 6. 现有系统映射

| 当前对象 | 当前含义 | 新设计中的定位 |
| --- | --- | --- |
| `assets` | 资产主表 | 全部资产基础资料，不等于可交易资产池 |
| `asset_universes` / `asset_universe_members` | 资产池与成员 | 可用于表达可交易资产池、市场上下文池 |
| `market_bars` | 日 K 数据 | 历史初始化和日常维护的结果表 |
| `fund_nav_snapshots` | 开放式基金净值 | 开放式基金历史初始化和每日净值维护的结果表 |
| `screening_results` / `screening_result_items` | 初筛结果 | 可承载技术初筛池的一次运行和成员 |
| `recommendation_runs` | 推荐运行 | 推荐候选池的一次运行 |
| `asset_recommendations` | 个股推荐结果 | 推荐候选池成员 |
| `watchlists` | 观察池定义 | 用户观察池、系统研究跟踪池等不同 purpose |
| `watchlist_items` | 观察池成员 | 用户关注或系统研究跟踪的成员 |
| `event_records` | 新闻、公告、事件记录 | 事件结果，不承担资产池职责 |
| Redis 任务进度 | 临时运行态 | 可承载事件重点池快照和任务进度 |

## 7. 数据模型建议

### 7.1 低成本字段策略

优先复用现有字段：

- `watchlists.purpose`：区分 `technical_screening_pool`、`system_research_pool`、`manual_watchlist`、`portfolio_watchlist`、`fund_watchlist`。
- `watchlist_items.source_type`：区分 `technical_screening`、`recommendation`、`manual`、`portfolio`、`agent_confirmed`。
- `watchlist_items.payload`：存放 `priority_score`、`expires_at`、`promotion_status`、`eligibility_snapshot`。
- `watchlist_item_events.event_type`：记录 `technical_screening_intake`、`research_intake`、`user_promoted`、`expired`、`removed_by_rule` 等状态变化。

### 7.2 可交易资产池表达

短期可以使用配置化规则和现有 universe：

```text
universe:tradeable:ashare:main_board
universe:tradeable:fund:default
```

规则包括：

- A 股代码必须是标准 6 位。
- A 股必须通过主板过滤。
- 基金必须通过基金类型过滤。
- 停牌、退市、异常资产可在推荐阶段二次过滤。

中期可以增加更明确的资产资格快照，例如 `asset_eligibility_snapshots`，但本阶段不强制。

## 8. 服务边界

### 8.1 Asset Eligibility Service

职责：

- 判断资产是否属于可交易资产池。
- 提供可交易资产列表。
- 提供过滤原因，供页面和日志展示。

建议先实现为轻量函数或服务，避免散落在各任务中重复过滤。

### 8.2 Market Data Lifecycle

职责：

- 根据可交易资产池分别执行 A 股主板个股 10 年日 K、ETF/LOF 历史日 K、开放式基金历史净值初始化。
- 根据资产类型执行日常行情生命周期维护。
- 结合水位表跳过已完成或冷却中的标的。

### 8.3 Technical Screening Service

职责：

- 在历史行情初始化或日常行情更新后，基于 OHLCV 和基础流动性指标执行粗筛。
- 生成技术初筛池，记录入池规则、技术得分、有效期和跳过原因。
- 将技术初筛结果提供给数据质量、因子补齐、事件重点池和推荐流水线，不直接生成买入建议。

### 8.4 Recommendation Intake

职责：

- 推荐结果只写推荐候选池。
- 自动同步时进入系统研究跟踪池，而不是用户观察池。
- `avoid` / `reject` 不入研究跟踪池。

### 8.5 Research Pool Service

职责：

- 管理系统研究跟踪池。
- 处理有效期、过期、降级和提升。
- 支持用户将研究项提升到用户观察池。

### 8.6 Event Priority Resolver

职责：

- 动态计算事件重点池。
- 按持仓、用户观察、研究跟踪、推荐候选、风险异动打分。
- 输出新闻逐股抓取名单。
- 将本轮结果写入 Redis 或任务进度，便于页面解释为什么抓这些标的。

## 9. 调度任务影响

### 9.1 历史初始化任务

历史初始化应拆成多条手工或后台一次性任务，而不是一个混合资产类型的大任务。

| 任务 | 范围 | 执行策略 |
| --- | --- | --- |
| `ashare.bars.1d.bootstrap` | A 股主板个股 | 10 年日 K；支持断点续跑、覆盖足够跳过、失败等待手动重跑 |
| `fund.etf.bars.1d.bootstrap` | ETF | 10 年或可用历史日 K；使用基金数据源和基金资产池 |
| `fund.lof.bars.1d.bootstrap` | LOF | 10 年或可用历史日 K；若上游不稳定，保留失败水位和手动重跑入口 |
| `fund.open.nav.bootstrap` | 开放式基金 | 可用历史净值；写入 `fund_nav_snapshots` |

共同规则：

- 输入资产范围改为可交易资产池。
- 已满足目标覆盖的资产跳过。
- 新资产进入可交易资产池后可加入待初始化队列。
- 失败不无限重试，只记录失败并等待手动重跑。

### 9.2 日常行情维护

`midday_partial`、`close_final`、`revision` 应使用 A 股主板个股范围。基金应使用独立日常维护任务，例如 `fund.bars.1d.close_final` 和 `fund.open.nav.daily`。

场内基金可复用 K 线生命周期概念，开放式基金应按净值生命周期维护。

### 9.3 技术初筛任务

历史初始化完成后，可以先执行一轮粗略技术分析入池。建议新增或明确以下任务：

```text
analytics.technical_screening.ashare.main_board
analytics.technical_screening.fund.exchange_traded
```

执行策略：

- 输入来自可交易资产池和已完成历史行情覆盖的标的。
- 只依赖 OHLCV、成交额、波动率、均线、动量和回撤等轻量指标。
- 结果写入 `screening_results` / `screening_result_items`，或同步到 `technical_screening_pool`。
- 有效期 1 到 3 个交易日；过期后重新计算，不长期沉淀为用户观察。
- 输出可驱动下一步数据质量、因子补齐、事件重点池和推荐候选计算。

### 9.4 推荐任务

`analytics.recommendations.ashare.all_a` 的输入应从全 A 或普通资产池调整为可交易资产池。

自动同步不再写入 `A 股推荐观察池`，而是写入 `A 股系统研究跟踪池`。

### 9.5 事件任务

`ashare.events` 不再直接读取所有 active 观察项作为重点名单。

新逻辑：

```text
EventPriorityResolver.resolve(market="ashare", limit=200)
```

输出 Top N 逐股新闻名单。公告列表仍使用全市场接口。

## 10. 前端产品表现

页面不应再把所有池子混叫为观察池。

建议展示：

- 可交易资产池：资产准入、覆盖率、历史 K 初始化状态。
- 技术初筛池：本轮技术粗筛入池、技术得分、规则命中、有效期。
- 推荐候选：本轮策略候选、动作、分数、风险、数据质量。
- 系统研究跟踪：系统自动跟踪项、有效期、来源推荐、提升按钮。
- 我的观察池：用户确认关注项、提醒条件、复核时间。
- 事件重点：本轮新闻抓取名单、优先级来源、抓取状态。

用户应能从系统研究跟踪池执行：

- 加入我的观察池。
- 忽略。
- 延长跟踪。
- 查看推荐证据和事件新闻。

## 11. 迁移策略

1. 保留当前 `watchlist:default-owner:ashare:recommendations`，但停止作为长期产品概念继续扩展。
2. 新建 `watchlist:default-owner:ashare:research`，作为系统研究跟踪池。
3. 后续推荐自动入池写入 research pool。
4. 当前推荐观察池中的 active 项可以迁移到 research pool，并保留来源事件。
5. `resolve_ashare_priority_news_symbols` 替换为事件重点解析器后，旧池子不再直接驱动新闻逐股抓取。

## 12. 验收标准

功能验收：

- 主板股票和基金准入规则集中化，不再散落在多个任务中。

## 14. 风险与取舍

短期复用 `watchlists` 表会让 `purpose` 和 `payload` 承担更多业务含义，但这是低成本推进 MVP 的合理取舍。

事件重点池不持久化会降低查询历史的能力，但它本质是任务运行态。需要历史审计时，可以记录每轮解析摘要到任务日志或 Redis 事件，不必先建业务表。

基金链路尚未完全成熟时，基金可以先进入可交易资产池定义，但具体日 K、因子和推荐链路按能力逐步启用，避免为了概念完整而引入不可用数据。

## 15. 下一步

用户确认本设计后，进入实现计划阶段。实现计划应先改最底层的资产准入，再调整 K 线任务范围，最后拆推荐入池和事件重点池，避免上层逻辑先行导致数据范围继续混乱。
