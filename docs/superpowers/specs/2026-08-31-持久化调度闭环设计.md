# 持久化调度闭环设计

- 日期：2026-08-31
- 状态：已确认方案，待用户审查书面规格
- 适用项目：`finance-agent`
- 替代范围：调度运行态、恢复门控、持久任务消费、进度展示和实时行情覆盖语义

## 1. 背景与现场结论

当前调度器虽然配置了 33 个任务、29 个启用任务，但实际长期只有 1～2 个任务运行。现场证据表明这不是单一并发参数问题，而是以下问题叠加：

1. Docker scheduler 没有传入运行时配置文件，实际使用代码内置配置：全局并发为 4，`realtime`、`analytics` 等资源池多数只有 1 个槽位；Web 读取的运行时配置却显示全局并发 10、资源池 3 个槽位。
2. 调度状态由进程内 `ScheduledJobState` 决定，PostgreSQL `scheduler_task_runs` 只在进程准备执行某个到期任务时才被动写入和领取，因此数据库队列不是唯一事实来源。
3. `after_success` 的触发代次仅保存在内存中。进程重启后，下游触发关系会丢失，数据库中租约过期并恢复为 pending 的任务也可能因本地任务不再到期而长期无人领取。
4. 恢复草稿被算作活动批次，`draft + degraded` 会立即阻止全部 `analytics.*`。当前恢复草稿未批准、没有补跑任务执行，但推荐、质量检查和触发链路已经从 2026-08-26 起停止刷新。
5. Web 的 waiting 列表只是“当前没有运行的任务目录”，包含未到期任务和手工任务，不是实际等待队列。
6. `ashare.realtime_quotes` 配置 `limit=200`，执行器却读取另一个不存在于采集参数模型中的 `realtime_quote_limit`，最终回退到 100。
7. 高频 interval 使用“执行完成时间 + interval”计算下一次运行。任务耗时会直接累加到采集周期，无法表达交易时段固定节拍和时效目标。

本规格采用已确认的方案 2：保留 Python、PostgreSQL、Redis 和 Docker Compose 技术栈，将计划、准入、排队、领取、执行、恢复与展示收敛成一个持久化闭环。

## 2. 目标与非目标

### 2.1 目标

- 运行时配置只有一个权威来源，API、Web 和 scheduler 能检测并展示配置版本是否一致。
- 所有计划执行先形成 PostgreSQL 任务事实，再经过准入、排队和 worker 领取。
- scheduler 重启、Redis 清空和 worker 租约过期后，未完成任务仍能继续执行。
- `after_success`、`all_of`、`any_of` 和 `barrier` 依赖跨进程重启保持正确。
- mutex、资源池、恢复门控、优先级和交易时段统一输出明确的准入决定。
- 恢复草稿不会冻结生产链路；恢复运行时只阻止真实依赖未恢复数据域的消费者。
- Web 准确区分计划、阻塞、排队、运行、完成、失败和取消状态。
- 实时行情配置与执行覆盖一致，并能报告目标数、实际覆盖数、覆盖率和最大滞后。
- 高频 A 股任务按交易时段固定节拍运行，耗时不会静默延长下一次计划时间。
- 全部行为具备自动化测试、容器重启测试和真实运行态验收证据。

### 2.2 非目标

- 不引入 Celery、Temporal、Kafka 或新的基础设施。
- 不把 scheduler 拆成独立部署的多种微服务；第一版仍使用一个 scheduler 容器和容器内线程池。
- 不绕过 Provider 限频、熔断、数据质量和推荐就绪度规则。
- 不保证上游 Provider 不存在的历史数据可以被补造；不可获得的数据必须形成证据化例外。
- 不把“同时运行任务越多”作为成功标准；成功标准是任务准入正确、吞吐满足时效目标且数据水位可证明。

## 3. 设计原则

1. **PostgreSQL 是调度事实来源。** Redis 只保存高频进度和短期指标，JSON 状态文件只保存进程健康和当前配置身份。
2. **先计划，后准入，再领取。** 任何任务都不能绕过持久化计划直接进入线程池。
3. **阻塞是状态，不是日志。** 被依赖、mutex、资源池、交易时段或恢复门控拦截的任务必须保存原因和重新评估条件，不能每 5 秒重复打印同一日志。
4. **配置身份可证明。** scheduler 必须报告加载文件的绝对路径、内容摘要和加载时间；API 不得用另一份配置推断运行中的并发额度。
5. **门控按依赖数据域决定。** 不使用任务名前缀代替真实依赖。
6. **任务状态与工作项进度分离。** PostgreSQL 保存调度状态，Redis 保存任务内部 symbol/batch 进度；两者不能互相伪装。

## 4. 模块设计

### 4.1 `SchedulerPlanner`

接口：

```python
reconcile(*, now: datetime, config: SchedulerConfig) -> PlanningSummary
```

职责：

- 根据 `daily_time`、`trading_session`、`fixed_interval`、`manual` 和 `after_success` 计算应存在的逻辑运行。
- 为每个逻辑运行生成稳定 `idempotency_key`，幂等写入 `scheduler_task_runs`。
- 对错过的高频 fixed interval tick 执行合并，只保留一个最新待执行 tick，并记录 `coalesced_count`。
- 读取持久化依赖代次，为 `after_success` 任务创建一次且仅一次的下游运行。
- 不领取任务、不执行 Provider、不直接修改 Redis 进度。

### 4.2 `SchedulerAdmissionController`

接口：

```python
evaluate(task: ScheduledTask, snapshot: AdmissionSnapshot) -> AdmissionDecision
```

`AdmissionDecision` 包含：

- `allowed`
- `reason_code`
- `reason_detail`
- `recheck_at`
- `required_data_domains`
- `blocking_task_ids`

职责：

- 校验交易时段、显式依赖、恢复数据域、mutex 和资源池额度。
- 把任务从 `scheduled` 转成 `blocked` 或 `pending`。
- 只有准入输入发生变化、关联任务完成或到达 `recheck_at` 时才重新评估。
- 相同 `task_id + reason_code + blockers` 不重复写日志，只更新心跳指标。

### 4.3 `PersistentSchedulerWorker`

接口：

```python
claim(*, worker_id: str, free_slots: int) -> list[TaskClaim]
execute(claim: TaskClaim) -> TaskResult
```

职责：

- 直接从 PostgreSQL 领取所有已到期 pending 任务，不依赖进程内 due state。
- 使用 `FOR UPDATE SKIP LOCKED` 和租约 token 保证同一任务只有一个执行者。
- 领取时再次校验资源池和 mutex 占用，避免多个 worker 的并发竞态。
- 成功、失败、取消或租约过期均在独立事务中落盘。
- 启动时恢复全部过期 running 任务；达到 `next_retry_at` 后自动重新进入 pending。

### 4.4 `SchedulerRuntimeReporter`

接口：

```python
snapshot(*, now: datetime) -> SchedulerRuntimeSnapshot
```

职责：

- 汇总 PostgreSQL 任务状态、worker 租约和资源池占用。
- 叠加 Redis 中的任务内部进度，不改变 PostgreSQL 状态语义。
- 输出实际加载配置的路径、摘要、版本和漂移状态。
- 为 API、Web 和健康检查提供同一个快照模型。

### 4.5 与现有代码的 seam

- `BaseDataScheduler` 保留兼容入口，内部委托上述模块，不再维护权威内存队列。
- `PersistentTaskQueue` 扩展状态查询与按准入条件领取能力，继续复用现有租约和幂等逻辑。
- `DataRecoveryModule` 继续负责缺口计划、执行和事实验证；`RecoveryGate` 只提供数据域状态，不直接按任务名前缀过滤调度列表。
- `collect_base_data.py` 继续负责单次采集和 Provider 质量控制。
- `DataSyncControlService` 负责配置编辑和 runtime snapshot 适配，不自行构造伪队列。

## 5. 配置唯一来源

### 5.1 Compose 启动约束

scheduler 命令必须显式传入：

```text
--config /app/runtime/base_data_scheduler/base_data_scheduler.json
```

配置文件不存在、JSON 非法、任务名重复、依赖不存在、资源池不存在或参数不合法时，scheduler 启动失败并写入明确健康错误，禁止静默回退内置配置。

内置默认配置只允许用于以下场景：

- `--dump-default-config`
- 明确的测试夹具
- 首次初始化运行时配置文件

常驻 loop 不允许在未传 `--config` 时启动。

### 5.2 配置身份

每次加载配置计算 SHA-256 摘要，并在状态快照中保存：

- `config_path`
- `config_digest`
- `config_loaded_at`
- `config_mtime_ns`
- `config_version`

API 读取配置文件得到的摘要与 scheduler 报告不一致时，返回 `config_drift=true`，Web 显示错误状态而不是继续展示推断并发。

热重载成功后更新身份；热重载失败时继续使用上一版本，同时保存 `config_reload_error`，不得把未生效配置展示为运行配置。

## 6. 持久化状态模型

### 6.1 `scheduler_task_runs` 扩展

保留现有主键、幂等键、payload、尝试次数和租约字段，新增：

- `schedule_type`
- `scheduled_for`
- `priority`
- `resource_pool`
- `mutex_key`
- `dependency_generation`
- `required_data_domains`（JSONB）
- `blocked_reason`
- `blocked_detail`（JSONB）
- `blocked_until`
- `config_digest`
- `coalesced_count`
- `cancel_requested_at`

状态集合调整为：

```text
scheduled -> blocked -> pending -> running -> completed
                   \-> cancelled
pending/running -> failed -> pending（可重试）
scheduled/blocked/pending/running -> cancelled
```

语义：

- `scheduled`：逻辑运行已经持久化，尚未完成准入判断。
- `blocked`：存在明确阻塞条件；必须包含 `blocked_reason`。
- `pending`：已通过准入，可由 worker 领取。
- `running`：持有有效租约并正在执行。
- `completed`：业务执行和持久任务完成回写成功。
- `failed`：当前尝试失败且没有立即可领取的重试。
- `cancelled`：不会再执行；保留审计记录。

迁移必须兼容已有 `pending/running/completed/failed` 行，不删除历史数据。

### 6.2 依赖代次

每个上游 completed 任务形成稳定完成代次：

```text
completion_generation = upstream.task_id
```

下游 `after_success` 幂等键包含下游任务名、依赖模式和所消费的上游完成代次集合。

- `all_of`：所有依赖均存在尚未消费的新完成代次时创建下游。
- `any_of`：任一依赖出现尚未消费的新完成代次时创建下游。
- `barrier`：所有依赖达到同一业务时间窗口后创建下游。

下游任务记录已消费代次，scheduler 重启后继续从数据库计算，不依赖内存计数器。

### 6.3 blocked 重新评估

阻塞原因码至少包括：

- `dependency_not_satisfied`
- `recovery_domain_blocked`
- `outside_trading_session`
- `mutex_busy`
- `resource_pool_full`
- `retry_backoff`
- `scheduler_paused`
- `config_disabled`

依赖完成、恢复门控变化、mutex 释放和资源池释放通过 PostgreSQL 状态变化触发下一轮评估；交易时段和退避使用 `blocked_until`。没有状态变化时不重复产生相同日志事件。

## 7. 恢复门控修正

### 7.1 状态语义

- `draft`：只表示存在待确认计划，不影响普通生产任务，门控视为 open。
- `approved`、`running`、`verifying`：根据未解决目标的数据域返回 recovering 状态。
- `paused`、`attention_required`：根据未解决目标的数据域返回 degraded 状态。
- `completed`、`completed_with_exceptions`、`cancelled`：不作为活动执行批次；取消记录不永久冻结后续生产任务。

草稿和取消批次的缺口仍通过数据质量与 readiness 阻止不安全推荐，但不能用一个全局 RecoveryGate 停止所有派生任务。

### 7.2 数据域依赖

调度任务显式声明 `requires_data_domains`。第一版映射至少满足：

- 实时行情：无历史恢复依赖，始终允许。
- 新闻列表和正文：无历史恢复依赖，始终允许。
- 风险情绪采集：无历史恢复依赖，始终允许。
- 盘中触发：依赖 `realtime_quotes` 和当日 `risk_sentiment`，不依赖历史基本面补跑。
- 数据质量：只阻止正在恢复的对应数据域检查，不阻止其他数据域检查。
- 技术筛选：依赖闭合 `market_bars`。
- 推荐：按策略显式依赖 `market_bars`、`fundamentals`、`valuation`、`capital_flow`、`events` 和 `risk_sentiment` 的子集。
- 回测：依赖其回测窗口的闭合行情与策略所需数据域。

准入控制器只在任务所需数据域存在阻塞目标时返回 `recovery_domain_blocked`，并把具体 run、step 和 domain 写入 `blocked_detail`。

### 7.3 readiness 保底

RecoveryGate 放行不等于推荐一定可执行。推荐入口继续执行场景化 freshness 和 readiness 校验：

- 盘中强度使用分钟级实时行情新鲜度。
- 日内/短线推荐使用当日行情、最近闭合日 K 和对应因子水位。
- 组合风险允许使用独立风险数据水位。

任何场景的必需数据不新鲜时，推荐必须 fail closed，并明确返回缺失数据域。

## 8. 调度时间语义

### 8.1 schedule type

支持并规范以下类型：

- `daily_time`：按本地固定时刻运行。
- `trading_session`：只在配置交易窗口内按固定节拍运行，可配置收盘补跑时刻。
- `fixed_interval`：以计划时间为锚点计算下一 tick，不把任务耗时累加到周期。
- `manual`：只由显式操作创建运行。
- `after_success`：由持久化依赖代次创建运行。

旧 `interval` 兼容解析为 `fixed_interval`，配置保存时规范化成新名称。

### 8.2 高频 A 股任务

以下任务必须改为 `trading_session`：

- `ashare.realtime_quotes`
- `ashare.risk_sentiment`
- `analytics.triggers.evaluate.intraday`

默认交易窗口使用 `Asia/Shanghai`：

```text
09:25-11:35
12:55-15:10
```

交易日判断必须使用项目交易日历；日历不可用时 fail closed，不按工作日猜测。

资金流是否盘中执行由数据源语义决定；若保留盘中刷新，同样使用 `trading_session`。新闻事件任务可以保持 any-day fixed interval。

### 8.3 tick 合并

同一任务前一 tick 尚未完成时，不并发创建无限积压：

- 保存最新一个待执行 tick。
- 旧 tick 合并到最新任务并增加 `coalesced_count`。
- 完成后按原计划时间轴计算下一 tick。
- Web 展示计划周期、实际启动延迟、执行耗时和被合并次数。

## 9. 实时行情覆盖

### 9.1 参数统一

`limit` 是单次任务允许处理的最大目标标的数。执行器不得再读取未声明的 `realtime_quote_limit`。

任务参数必须显式区分：

- `scope=priority`：持仓、观察池、近期推荐、待处理触发标的优先。
- `scope=market_sweep`：目标交易池滚动覆盖。
- `limit`：本次最大标的数；`null` 表示由分区器覆盖完整目标池，0 非法。
- `batch_size`：单个 Provider 请求或 worker 分区大小。

### 9.2 双层刷新

保留一个高频 priority 任务，并增加一个 market sweep 任务：

- priority 任务按交易时段高频执行，默认覆盖最多 200 个重点标的。
- market sweep 以稳定分区遍历目标交易池，分区游标持久化到任务 payload；scheduler 重启后从未完成分区继续。
- 同一标的在同一计划窗口由幂等键合并，避免 priority 与 sweep 重复请求。
- gotdx 和 AKShare 的实际返回分别记录来源覆盖、错误和冲突；部分可用不能伪装成完整覆盖。

### 9.3 可验收时效

在本机 Compose 生产配置下，交易时段容量验收目标为：

- priority 标的 p95 最大写入滞后不超过 120 秒。
- 目标交易池完整 sweep 最大写入滞后不超过 10 分钟。
- 每轮输出 `target_count`、`requested_count`、`written_count`、`fresh_count`、`coverage_ratio`、`max_lag_seconds` 和分来源状态。

若实际 Provider 能力无法达到目标，scheduler 必须把对应任务和数据水位标记为 degraded，不能只显示 job success。

## 10. 资源池、mutex 与并发

### 10.1 配额来源

全局并发和资源池额度只取 scheduler 已加载配置。Web 不再用配置文件推断运行额度。

资源池快照至少包括：

- `limit`
- `running`
- `pending`
- `blocked`
- `oldest_pending_age_seconds`
- `saturation_ratio`

### 10.2 领取规则

worker 每次领取按以下顺序筛选：

1. `status=pending` 且 `next_retry_at <= now`。
2. 资源池存在空闲额度。
3. mutex 没有被有效 running 租约占用。
4. 按 priority 降序、scheduled_for 升序、created_at 升序选择。

领取和额度判断位于同一数据库事务。第一版只有一个 scheduler 容器，但实现必须允许未来多个 worker 使用相同规则而不重复执行。

### 10.3 长任务分区

新闻、全市场行情、K 线和恢复补跑等长任务必须把可独立重试的工作拆成稳定分区：

- 分区任务具备自己的幂等键、租约和结果。
- 父任务聚合分区状态，不占用一个虚假的长期执行槽。
- 单个分区失败不要求重跑全部标的。
- 分区大小受 Provider 限频和数据库写入批量约束。

## 11. API 与 Web 状态语义

### 11.1 scheduler status

健康状态返回：

- 进程存活与心跳年龄。
- 实际配置身份和 `config_drift`。
- planner、admission、worker 最近成功时间和最近错误。
- 各持久任务状态计数。
- 实际资源池占用。
- 最老 pending/blocked 任务及原因。
- 各核心数据域最新水位、覆盖率和最大滞后。

### 11.2 progress

进度接口按 PostgreSQL 任务状态生成目录：

- `scheduled`
- `blocked`
- `pending`
- `running`
- `recent_completed`
- `recent_failed`

Redis 只为 running 任务补充 batch/symbol 进度。未到期任务进入 `next_runs`，手工任务进入 `manual_jobs`，两者不得计入 waiting 或 pending。

### 11.3 控制操作

- pause/resume 更新配置控制区，并由 planner/admission 形成持久状态变化。
- cancel 对 scheduled/blocked/pending 任务立即转 cancelled；running 任务写入 `cancel_requested_at`，由执行器在安全检查点退出。
- 手工 run 直接创建带 `trigger_source=manual` 的 scheduled 记录，仍经过相同准入和 worker 领取。
- API 操作返回持久 `task_id`，不返回无法追踪的后台线程标识。

## 12. 错误处理与可观测性

### 12.1 错误边界

- 配置错误：启动失败或热重载保持旧版本，并显示配置错误。
- planner 错误：不影响已 pending/running 任务被 worker 继续处理。
- admission 错误：任务保持 scheduled，记录错误并退避，不能默认放行。
- worker 执行错误：按任务重试策略转 failed 或 pending。
- Redis 错误：内部进度降级，但 PostgreSQL 调度状态仍可用。
- PostgreSQL 错误：scheduler 停止创建和领取新任务，健康状态 fail closed。

### 12.2 结构化事件

至少记录：

- `scheduler_config_loaded`
- `scheduler_config_drift`
- `scheduler_task_planned`
- `scheduler_task_blocked`
- `scheduler_task_unblocked`
- `scheduler_task_claimed`
- `scheduler_task_completed`
- `scheduler_task_failed`
- `scheduler_task_cancelled`
- `scheduler_tick_coalesced`
- `scheduler_lease_recovered`
- `scheduler_data_watermark_degraded`

事件按状态变化写入，不按 5 秒轮询重复写入同一原因。

## 13. 数据迁移与兼容

1. 新迁移扩展 `scheduler_task_runs` 约束和字段，不删除历史行。
2. 历史 pending/running/completed/failed 行保持原状态；缺少的新字段从 payload 和 job 配置读取，无法恢复时使用显式 `legacy` 标记。
3. 启动时先恢复过期租约，再由 worker 直接领取所有可执行 legacy pending 任务。
4. 旧 interval 配置在读取时兼容，在下一次保存时规范化为 fixed interval 或 trading session。
5. API 在一个版本周期内保留现有响应字段，并增加新的状态集合；前端切换完成后再删除错误的 waiting 推断逻辑。
6. 回滚代码时新字段可以保留；旧代码不依赖新字段，但回滚前必须停止新 scheduler，避免新状态被旧约束误处理。

## 14. 测试策略

### 14.1 单元测试

- 配置路径、摘要、热重载和漂移检测。
- 各 schedule type 的下一计划时间、交易日和交易窗口边界。
- tick 合并与固定时间轴。
- 依赖代次的 all_of、any_of、barrier 和重启恢复。
- 每种 admission reason 的阻塞与解除。
- draft/cancelled 不门控、活动恢复按数据域门控。
- 实时行情 limit、priority 顺序、market sweep 分区和覆盖指标。
- API 状态分类不混入未到期和手工任务。

### 14.2 PostgreSQL 集成测试

- 幂等计划写入。
- `FOR UPDATE SKIP LOCKED` 并发领取。
- 资源池和 mutex 事务竞争。
- 租约过期恢复并由不同 worker 领取。
- legacy pending 任务在没有内存 due state 时仍能执行。
- scheduler 重启后 after_success 只触发一次。
- blocked 条件变化后转 pending。

### 14.3 Redis 集成测试

- Redis 正常时叠加内部进度。
- Redis 清空或不可用时 PostgreSQL 状态不丢失。
- 旧 active progress 不得把已 completed 的数据库任务误标成 running。

### 14.4 Compose 与进程测试

- `docker compose config` 验证 scheduler 必须携带 `--config`。
- 配置文件不存在和非法时容器健康失败且错误明确。
- 修改并保存配置后 scheduler 热重载，API 摘要与实际摘要一致。
- 运行任务时强制重启 scheduler，确认租约恢复、pending 继续和 after_success 不重复。
- 同时验证 API、scheduler、PostgreSQL、Redis 和 Web 容器健康。

### 14.5 真实运行态验收

- 在交易时段观察至少一个完整 priority 周期和一个完整 market sweep 周期。
- 统计峰值并发、各资源池饱和度、任务启动延迟和执行耗时。
- 查询数据库验证实时行情覆盖率与最大滞后。
- 验证推荐、数据质量和盘中触发水位恢复更新。
- 创建未批准恢复草稿，确认安全任务和不依赖缺口域的派生任务继续运行。
- 启动受控恢复，确认只有依赖受影响数据域的任务 blocked。
- 重启 scheduler 后重复读取状态，确认配置摘要、任务状态和依赖代次连续。

## 15. 验收标准

实施只有同时满足以下条件才算完成：

1. scheduler 容器实际加载运行时配置，状态与 API 报告的 `config_digest` 一致。
2. 全局并发和所有资源池 limit 在配置、scheduler 状态、API 和 Web 中完全一致。
3. PostgreSQL 中不存在达到执行时间却因没有本地 due state 而长期无人领取的 pending 任务。
4. scheduler 重启后租约任务继续执行，after_success 不丢失、不重复。
5. 未批准 draft 和 cancelled 恢复批次不再全局冻结 analytics。
6. 活动恢复只阻止显式依赖未恢复数据域的任务，阻塞详情可查询。
7. 相同阻塞原因不再每 5 秒重复写日志。
8. Web waiting、pending、blocked、running 数量与 PostgreSQL 查询一致。
9. 实时行情配置 limit 与执行目标数一致，priority 与 market sweep 均输出覆盖指标。
10. 交易时段 priority p95 滞后不超过 120 秒，目标交易池 sweep 最大滞后不超过 10 分钟；未达标时状态明确 degraded。
11. 推荐、质量检查和盘中触发使用各自场景新鲜度，陈旧数据不能通过 readiness。
12. 单元、PostgreSQL/Redis 集成、API、Compose、重启恢复和真实运行态测试全部通过。
13. GitNexus `detect_changes` 只报告预期调度、恢复、采集和进度流程影响；HIGH/CRITICAL 风险在编辑前得到明确处理。
14. 不覆盖或回滚工作区内与本任务无关的用户修改。
