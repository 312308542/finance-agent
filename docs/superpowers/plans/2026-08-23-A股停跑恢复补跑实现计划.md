# A 股停跑恢复补跑实现计划

## 目标

按《A 股停跑恢复补跑设计》（docs/superpowers/specs/2026-08-23-A股停跑恢复补跑设计.md）新增批次级补跑能力：系统启动后只读扫描生产资产池数据缺口并生成草稿计划，经用户确认后按 P0～P8 依赖补齐日 K、基本面、估值、资金流、新闻公告和风险情绪事实，事实验收通过后仅重建一次最新派生截面并解除 RecoveryGate。全程支持幂等、暂停/继续/取消、进程重启续跑和带证据的可解释例外。

## 现状与风险

- GitNexus 能力已恢复（WSL CLI 1.6.8，索引已重建至 8da192f），`query`/`context`/`impact`/`detect_changes` 全部可用。
- 影响评估：`BaseDataScheduler`（7 上游，LOW）、`PersistentTaskQueue`（7，LOW）、`DataBackfillPlanner`（15，LOW）、`DataSyncControlService`（3，LOW）。无 HIGH/CRITICAL。
- 工作区存在与本需求无关的未提交修改（前端面板、触发器等）。本计划只做追加式修改：新增 `src/finance_agent/data_recovery/` 包、一个 Alembic 迁移和对应测试；对既有文件仅在明确 seam 追加最小代码，不回退、不重排他人修改。
- `PersistentTaskQueue.enqueue` 已支持幂等键去重，任务级幂等直接复用；Redis 不作为批次事实来源。

## 实施步骤

1. **REC-007 持久化模型**：迁移 `20260823_0026_create_data_recovery_tables.py` 创建 `data_recovery_runs`、`data_recovery_steps`、`data_recovery_targets`（字段与约束按规格第 9 节；目标表唯一约束覆盖批次+数据域+资产+区间+粒度）；`storage/orm.py` 追加三个 ORM；新增 `data_recovery/repository.py` 提供 `RecoveryRepository`（批次互斥 `data_recovery:ashare`、草稿复用按 `plan_hash`、步骤/目标幂等 upsert）。
2. **REC-008 检测与验收**：`data_recovery/gap_detector.py` 用集合查询识别各数据域缺口（cutoff_date 取最近已收盘交易日；日历或资产池过期时经现有 Provider 只读刷新，失败则计划不可执行）；`plan_builder.py` 冻结范围、生成 P0～P8 步骤依赖、目标区间压缩、预计请求量与 `plan_hash`（市场+资产池快照+cutoff+缺口集合+策略版本）；`verifier.py` 任务完成后重读事实表判定完成，例外分类 `transient/source_unavailable/not_applicable/data_conflict/unknown_gap`，放行依据复用现有健康检查与 readiness。
3. **REC-009 执行与门控**：`executor.py` 将步骤分区提交到 `PersistentTaskQueue`（幂等键 `recovery:{run_id}:{step_id}:{partition_hash}`，payload 带 `recovery_run_id`/`recovery_step_id`/`partition_hash`），P7 仅在 P6 通过后对 cutoff_date 提交一次最新派生链路；`gate.py` 维护 `recovering/degraded/open` 三态并把 `always/merge/requires_open` 分类暴露给调度器；`BaseDataScheduler.run_loop` 领取前检查门控，被拦截的派生任务返回 `blocked_by_recovery` 且不计失败；启动顺序接入「恢复租约→只读扫描→创建/复用 draft→设门控」；`service.py` 组合为 `DataRecoveryModule` 门面（preview/approve/control/get）。
4. **REC-010 控制入口**：API 新增预览/确认/列表/详情/暂停/继续/取消/例外明细路由，全部委托 `DataRecoveryModule`；CLI 增加 `data recovery preview|approve|status|pause|resume|cancel`；MCP 注册同名工具；控制台数据同步页增加「停跑恢复」区域（计划摘要、阶段进度、例外与证据、操作按钮）；`DataSyncControlService` 只适配转发。
5. **测试**：新增规则测试（交易日/cutoff/报告期/窗口/区间压缩/哈希过期）、状态机测试（正常路径、暂停继续取消、非法跳转、取消后保持 degraded）、调度集成测试（blocked_by_recovery、实时任务放行、重复分区单任务、合并策略、租约恢复续跑）、事实验证测试（成功≠完成、空 K 线需证据、冲突进 attention、重启不再采已完成目标）；最后全量回归。
6. **收尾**：运行 `gitnexus detect-changes` 校验实际影响面，更新规格进度表并输出实施报告。

## 验收标准

- 对应规格第 15 节全部 8 条：cutoff 不含未收盘交易日；适用闭合日 K 补齐或有证据例外；无未解决 transient/unknown_gap/data_conflict 核心目标；readiness 可执行；派生链路仅一次；重复确认/重启无重复逻辑任务；清空 Redis 后状态可由 PostgreSQL 重建；所有不可补目标带域、来源、窗口、分类和证据。
- 现有测试全量通过；新增模块测试覆盖上述四类场景。


## 附：实施中发现并顺带修复的既有问题（用户授权）

以下两个问题在补跑实施过程中发现，经用户确认后顺带修复（2026-08-23）：

### 1. heartbeat 事件类型错误

- 位置：src/finance_agent/storage/repositories.py 的 SchedulerTaskRepository.heartbeat。
- 现象：租约续约成功时错误发出 scheduler.task.completed 事件（payload status=completed），事件流中出现心跳即完成的假事件，误导事件消费者与审计。
- 修复：改为发出 scheduler.task.heartbeat，payload 为 status=running 且 lease_extended=true；幂等键随事件类型自然区分。
- 影响面：仅事件观测语义；complete/fail/租约判断逻辑不变。GitNexus 影响评估：类级 CRITICAL（72 个受影响点，因该类被广泛引用），但本次为单点行为修正且纯事件载荷变化。
- 测试：tests/test_persistent_task_queue.py::test_heartbeat_emits_running_event_not_completed。

### 2. 持久队列缺查询/取消 API

- 现象：scheduler_task_runs 没有按负载引用查询与取消任务的仓储方法；补跑取消只能内联拼 UPDATE 绕过仓储层，事件缺失、口径分散。
- 修复：
  - SchedulerTaskRepository.list_tasks(job_name/statuses/payload_key/payload_value/limit)：任务观测查询 API；
  - SchedulerTaskRepository.cancel_tasks(task_ids/reason/now)：只取消 pending 任务（规格 12.3：不回滚已写事实），逐条追加 scheduler.task.cancelled Outbox 事件并返回实际取消数；
  - PersistentTaskQueue.list_tasks/cancel_tasks 同名透传；
  - DataRecoveryModule._cancel_pending_tasks 改走仓储 API，删除内联 SQL。
- 测试：test_list_tasks_filters_by_status_and_payload_key、test_cancel_tasks_only_cancels_pending_and_emits_events、test_cancel_tasks_empty_ids_is_noop。
