# 方案 12：基础数据调度资源池与优先级改造

> 优先级：P1 ｜ 依赖：基础数据调度器、任务监控页、数据同步配置中心已可用
> 前置阅读：`docs/基础数据调度器.md`、`docs/数据同步任务队列通用化优化方案.md`

## 1. 背景

本次改造前，基础数据调度器已经有三层并发：

| 层级 | 当前字段 | 含义 |
| --- | --- | --- |
| 调度器全局并发 | `max_concurrent_jobs` | 同时运行多少个调度任务 |
| 单任务 worker | `job.params.max_workers` | 一个任务内部同时处理多少个标的或 item |
| 数据源有效并发 | `rate_policies.<source>.max_concurrency` | 同一个外部数据源允许多少个并发请求 |

这三层都不能互相替代。`max_concurrent_jobs` 是系统总闸门，不能直接去掉；但当前它只有一个总数限制，缺少任务优先级和资源隔离。盘中高频轻任务、收盘分析任务、新闻正文补抓、Agent 消费、回测等任务混在同一个全局队列里，容易出现两类问题：

1. 长任务占满全局并发，导致盘中实时行情、触发器、风险情绪延迟。
2. 多个同类重任务同时启动，数据库、Redis、外部数据源和模型调用被一起打满。

本方案目标是保留全局并发，同时把调度器升级为“全局总闸门 + 资源池 + 任务优先级 + 互斥键”的执行模型。

## 2. 目标

1. 保留 `max_concurrent_jobs`，作为调度器层面的硬上限。
2. 新增 `resource_pool`，限制不同类型任务各自的并发额度。
3. 新增 `priority`，让同一轮到期任务按业务重要性排队。
4. 保留 `mutex_key`，继续解决新闻/正文补抓、同资源写入冲突等互斥问题。
5. 前端任务监控页清晰展示四类并发：全局任务并发、资源池占用、当前任务 worker、源有效并发。
6. 全部改动保持配置可导出、可编辑、可测试，不依赖本地 `runtime/` 文件。

## 3. 非目标

1. 不删除 `max_concurrent_jobs`。
2. 不把所有任务都改成无限并发。
3. 不把外部数据源限频交给调度器全局并发处理，源级限频仍由 `rate_policies` 控制。
4. 不改变事实数据表结构。
5. 不新增长期任务日志表；运行态仍以 Redis/进度快照为主。

## 4. 总体设计

调度器选任务时按以下顺序处理：

```text
读取所有 enabled job
  -> 找到到期任务 due_states
  -> 过滤同市场资产池阻塞
  -> 过滤 mutex_key 互斥任务
  -> 按 priority 排序
  -> 检查全局 max_concurrent_jobs
  -> 检查 resource_pool 剩余额度
  -> 提交到 ThreadPoolExecutor
  -> 完成后按 schedule_type 计算下一次运行
  -> after_success 任务按依赖触发
```

### 4.1 新增调度字段

在 `BaseDataSchedulerJob` 中新增：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `priority` | `int` | `100` | 数值越大优先级越高。只影响同一轮已到期任务的排队顺序。 |
| `resource_pool` | `str` | `"default"` | 任务占用的资源池名称。 |

在 `BaseDataSchedulerConfig` 中新增：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `resource_pools` | `dict[str, dict]` | 见 4.2 | 每个资源池的最大并发、说明和默认优先级范围。 |

### 4.2 默认资源池

| 资源池 | 默认并发 | 适用任务 | 设计理由 |
| --- | ---: | --- | --- |
| `realtime` | 1 | 实时行情、盘中触发器、风险情绪轻量刷新 | 保证盘中观察优先，不被长任务挤掉。 |
| `collection_heavy` | 2 | K 线、基本面、资金流、新闻列表、风险采集 | 外部数据源和数据库写入压力较大，需要限额。 |
| `article_enrichment` | 1 | 新闻正文二次抓取 | 慢任务，且容易触发站点限流，独立低并发。 |
| `analytics` | 1 | 技术初筛、推荐合并、推荐计算、数据质量 | CPU/数据库读写较重，避免和采集任务互相抢资源。 |
| `agent` | 1 | Agent 消费、高风险复核 | 可能调用模型或复杂工作流，避免并发放大成本。 |
| `maintenance` | 1 | 回测、到期复盘、低频维护 | 低优先级后台任务。 |
| `default` | 1 | 未显式分类任务 | 兼容旧配置。 |

全局 `max_concurrent_jobs` 仍然生效。例如全局为 4，即使所有资源池额度相加大于 4，实际同时运行任务也不能超过 4。

| 优先级 | 任务类型 | 示例 |
| ---: | --- | --- |
| 900 | 手动任务、用户点击立即执行 | 页面单次执行、失败重跑 |

| 700 | 风险与情绪 | `ashare.risk_sentiment` |

| 600 | 资金流、新闻列表 | `ashare.capital_flow`、`ashare.events` |
| 550 | 技术初筛、推荐合并、推荐计算 | `analytics.technical_screening.*`、`analytics.recommendations.*` |
| 500 | 基本面、估值 | `ashare.fundamentals` |
| 400 | 新闻正文补抓 | `ashare.news_articles` |
| 300 | 资产池、凌晨修正、低频风控事件 | `ashare.universe.all`、`ashare.bars.1d.revision` |
| 100 | 回测、复盘 sweep、维护任务 | `analytics.backtest.weekly`、`analytics.reviews.due` |

手动任务在 `run_scheduler_job` 的单任务配置里仍保持 `max_concurrent_jobs=1`，避免页面重复启动造成同一任务多份采集。

- 在 due job 过滤市场资产池和 `mutex_key` 后，对 runnable due states 做稳定排序：

```python

    due_states,
    key=lambda state: state.job.priority,

)
```

**目标**：在配置解析阶段对两类易错配置输出告警，不阻断调度。

**实现**：

- 在 `base_data_scheduler.py` 新增 `warn_on_resource_pool_misconfiguration()`，在 `parse_scheduler_config()` 解析完资源池和任务后调用：

  2. **额度之和超全局（INFO）**：各资源池 `max_concurrent_jobs` 之和超过全局 `max_concurrent_jobs` 时提示，全局闸门仍会压住实际并发，但部分资源池无法同时达到各自声明额度。
- 两者都只记录日志、不抛异常，保持旧配置和健壮兜底行为不变。

**验证**：

- 真实配置触发验证：用 `build_preset_config('ashare-comprehensive')` 导出后篡改（全局并发改 1、任务引用 `typo_pool`），`parse_scheduler_config` 成功解析并输出两条告警（WARNING 未声明资源池、INFO 额度之和 11 超全局 1）。

## 7. 风险与回滚

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 资源池配置过小 | 某些任务长时间排队 | 前端展示排队原因，允许配置调整。 |
| 优先级配置错误 | 低优先级任务抢跑 | 预设测试锁定关键任务优先级。 |
| 队首阻塞 | 队首资源池满，其他可跑任务也被挡住 | `fill_worker_slots()` 需要扫描队列，选择可运行任务。 |
| 旧配置不兼容 | 本地 runtime json 缺新字段 | 所有新增字段必须有默认值。 |
| 页面误解并发含义 | 用户把 worker 当全局并发 | 前端用中文明确区分四层并发。 |
| 资源池名拼写错误 | 任务引用不存在的资源池，实际额度与预期不符 | T7 在配置解析时 WARNING 提示未声明资源池。 |
| 各池额度之和超全局 | 部分资源池无法同时达到各自声明额度 | T7 在配置解析时 INFO 提示额度之和超标，运行期全局闸门仍兜底。 |

回滚方式：

1. 保留字段解析但不启用资源池检查，把所有任务放入 `default` 池，池额度等于 `max_concurrent_jobs`。
2. 优先级排序可回退为配置顺序，但不删除字段，避免配置兼容性震荡。
