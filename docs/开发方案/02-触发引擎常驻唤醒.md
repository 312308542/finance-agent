# 方案 02：触发引擎常驻唤醒（O2 收尾）

> 优先级：P0 ｜ 批次 1 ｜ 依赖：无
> 前置阅读：`00-总体规划与执行约定.md`

## 1. 背景与现状

已有资产：

- `src/finance_agent/triggers/service.py`：`TriggerService` 支持 6 类触发（持仓回撤 `position_drawdown`、信号转弱 `signal_flip`、观察池条件 `watchlist_condition_hit`、推荐运行 `recommendation_run_ready`、风险事件 `risk_event_detected`、数据质量 `data_quality_degraded`），带 `dedup_key` 去重和 `cooldown_until` 冷却，写入 `assistant_trigger_events` 并可派发到 Agent 唤醒队列。
- `src/finance_agent/agents/loop/runner.py`：`InternalFinanceAgentLoopRunner` 可消费 `dispatched + agent_task_id` 的触发事件，经真实模型 Planner 按需调用 Domain Workflow，回写 `agent_loop_status` / `workflow_run_id`。
- CLI：`finance-agent agent run-once / run-task / run-loop`（`src/finance_agent/cli/main.py:223` 起）。
- `BaseDataScheduler`（`src/finance_agent/scheduler/base_data_scheduler.py`）：`--loop` 常驻、状态文件、JSONL 事件日志、失败重试、`after_success` 依赖触发、交易日历调度（`next_calendar_run_at`、`trading_day_policy`）均已生产可用。
- 盘中数据基础：`realtime_quote_snapshots` 表、`market_bars_intraday` 表（迁移 0015）已存在。

**缺口**：三件事没接起来——

1. 触发评估没有常驻入口：`TriggerService` 只能被 CLI/MCP 手动调用，数据刷新后没有人自动评估触发。
2. Agent Loop 没有常驻消费：`agent run-loop` 需要手工启动，没有纳入调度体系。
3. 盘中波动规则缺失：现有 6 类触发都基于日级数据，没有利用 `realtime_quote_snapshots` / `market_bars_intraday` 的盘中急跌、放量异动规则。

## 2. 目标与非目标

**目标**

1. 调度器常驻运行时，触发评估与 Agent 消费自动进行，全程无需手动 CLI。
2. 新增盘中波动触发规则（快速下跌、放量异动），仅在 A 股交易时段运行。
3. 全链路可观测：触发评估和 Agent 消费作为调度任务出现在任务监控页（自动复用既有进度体系）。

**非目标**

- 不改 Workflow 内部逻辑（归方案 04）。
- 不做复核回写（归方案 03）。
- 不引入新的常驻进程形态——复用 `BaseDataScheduler --loop`，不另起 daemon 框架。

## 3. 技术方案

### 3.1 架构决策：触发评估与 Agent 消费做成两个调度任务

不新建独立 daemon。在 `BaseDataScheduler` 中新增两类 `sync_task_type`：

```text
analytics.triggers.evaluate   -> 调 TriggerService 评估并派发
agent.loop.consume            -> 调 InternalFinanceAgentLoopRunner 消费已派发事件
```

理由：调度器已具备常驻、状态文件、事件日志、失败重试、暂停/恢复控制和前端监控；让触发与消费成为普通任务即可零成本获得全部运维能力。这与既有 `analytics.recommendations.*`、`analytics.technical_screening.*` 任务的接入方式一致（参考 `run_technical_screening_refresh` 在 `base_data_scheduler.py` 中的接法）。

### 3.2 任务一：`analytics.triggers.evaluate`

**sync_config 侧**（`src/finance_agent/data/sync_config.py`）：

- 新增 `build_trigger_scheduler_jobs(config)`，导出任务：
  - `analytics.triggers.evaluate.daily`：每日收盘后（依赖 `ashare.bars.1d.close_final` 的 `after_success`），评估全部 6 类既有触发。
  - `analytics.triggers.evaluate.intraday`：交易时段内固定间隔（默认 15 分钟，`trading_day_policy="ashare"` 只在交易日），只评估盘中规则（见 3.4）和持仓相关触发。
- 任务参数：`owner_id`（默认 default-owner）、`trigger_groups`（list，控制评估哪些规则组）、`dispatch`（bool，是否立即派发）、`max_events_per_run`。

**scheduler 侧**（`src/finance_agent/scheduler/base_data_scheduler.py`）：

- 仿照 `run_technical_screening_refresh` 增加 `run_trigger_evaluation(**kwargs)`：开 session → 构造 `TriggerService` → 评估 → 派发 → 把 `created_count / dispatched / skipped / cooldown` 计数写入任务 payload（任务监控页自动可见）。

### 3.3 任务二：`agent.loop.consume`

- 同样模式接 `InternalFinanceAgentLoopRunner`：每次运行消费至多 `limit`（默认 10）个已派发事件。
- 调度策略：`analytics.triggers.evaluate.*` 任务的 `after_success` 依赖项，即"评估完→立刻消费"；另加一个低频兜底（每 30 分钟）扫漏。
- 关键参数透传：`owner_id`、`limit`、`use_model_planner`（默认 true，模型不可用时 Runner 已有确定性 fallback）。
- payload 写入：`consumed / succeeded / failed / fallback_used` 计数与每个事件的 `workflow_run_id`。

### 3.4 盘中波动触发规则（TriggerService 扩展）

在 `triggers/service.py` 新增规则组 `intraday_volatility`，两条规则：

1. **快速下跌 `intraday_sharp_drop`**：对持仓和用户观察池资产，取 `realtime_quote_snapshots` 最近两个快照，跌幅超过阈值（默认 -4%/30 分钟，可配）→ 生成触发，建议 workflow `portfolio_monitoring`（持仓）或 `asset_deep_analysis`（观察池）。
2. **放量异动 `intraday_volume_surge`**：当前快照成交量相对近 20 个同时段快照均量 > 阈值（默认 3 倍）且价格变动超过 ±2% → 生成触发。

**数据源事实（实现前必读）**：

- `ashare.realtime_quotes`（`realtime_quote_refresh`，默认 5 分钟间隔）采集任务**已存在**于 sync_config，盘中规则以 `realtime_quote_snapshots` 为主数据源。
- `market_bars_intraday` 表（迁移 0015）目前是**孤儿表**——只有 ORM 定义，没有任何写入方。盘中规则第一版**不要**依赖它；分钟 K 线采集任务的取舍归方案 06 的 D1 决策项。

实现约束：

- 数据不足（快照缺失、间隔过大）时静默跳过该资产并在结果里计数 `skipped_no_data`，**不报错**——实时快照任务可能未开启。
- 复用既有 `dedup_key` + 冷却机制，盘中规则默认冷却 120 分钟，避免同一标的反复唤醒。
- 阈值放进任务 `params`，不硬编码（前端任务配置编辑器可直接改）。

### 3.5 runtime 配置与部署

- 更新 `runtime/base_data_scheduler/base_data_scheduler.json`：加入上述任务（intraday 任务默认 `enabled: false`，待盘中数据链路验证后再开；daily 任务默认开启）。
- `data config init/export` 的预设（`personal-comprehensive`）包含新任务，保证新环境可一键生成。

```powershell

.\.venv\Scripts\python.exe scripts\data\run_base_data_scheduler.py --config runtime\base_data_scheduler\base_data_scheduler.json --run-once --only analytics.triggers.evaluate.daily
.\.venv\Scripts\python.exe -m pytest -q
```

> 当前脚本差异：`scripts/data/run_base_data_scheduler.py` 暂不支持 `--only` 参数。T7 冒烟按代码现状使用 `runtime/base_data_scheduler/manual_runs/trigger_daily_smoke.json`（本地忽略文件，只包含 `analytics.triggers.evaluate.daily`）执行单任务 dry-run 与真实 run。

验收标准：

- 常驻 `--loop` 模式下，收盘任务成功后自动出现触发评估与 Agent 消费记录，无人工介入。
- 同一触发源在冷却期内不重复唤醒（查 `assistant_trigger_events.dedup_key`）。
- 模型不可用时 Agent 消费走 fallback，任务状态仍为成功并标记 `fallback_used`。

## 6. 风险与注意事项

- **改 `base_data_scheduler.py` 风险高**（它刚经历大重构且被 4000+ 行测试覆盖）：新增执行入口必须只增不改，复用既有任务执行骨架；动到公共路径前先看 `tests/test_base_data_scheduler_analytics.py` 里相关测试名。
- Agent 消费会真实调用模型 Planner：测试与冒烟一律注入 fake planner 或确认 `use_model_planner=false` 路径；真实模型联调单独一步并记录成本。
- 盘中规则依赖 `ashare.realtime_quotes` 任务的实际开启情况——这是 intraday 触发任务默认 `enabled: false` 的原因。启用顺序：先确认实时快照任务在运行并有数据，再开触发任务；分钟 K 线采集是否补建归方案 06 的 D1 决策。
