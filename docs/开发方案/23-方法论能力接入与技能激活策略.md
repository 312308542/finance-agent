## 4. 推荐的系统接入策略

### 4.1 A1 修复：结构证据进推荐 payload（选定方案与理由）

**决策：推荐流水线写 payload，不新建前端 API。** 理由：① 前端已按 `payload.structure.structure_frames` 形状实现解析（T10），走 payload 是零前端改动的最短路径；② 圆桌 workflow 已有同形状组装逻辑可复用；③ payload 自包含利于审计（推荐当时看到的结构证据被冻结在推荐记录里，符合"评分可复现"的既有原则）。

**规格**：
- `RecommendationService` 构建单标的推荐时，从 `indicator_frames` 读取该资产最新四类 structural-lite v2 帧（`library="structural-lite"`），组装为 `payload.structure = {"library": "structural-lite", "structure_frames": [...]}`。
- **精简契约**（控制 payload 体积）：每帧只保留 `horizon(schema_version)`、`status`、`confidence`、`evidence_id`、`as_of`，外加**每引擎至多 3 条**关键条目摘要（SMC 取最近结构事件名+方向+break_level；谐波取形态名+方向+bars_since_d；Elliott 取 pattern+signal_hint；swings 取最近段方向）。完整数据凭 `evidence_id` 回 `indicator_frames` 查——payload 是索引+摘要，不是全量复制。
- 无结构数据/全 insufficient 时写 `payload.structure = {"status": "no_structure_evidence"}`，前端如实显示"暂无结构证据"（宁缺毋假）。
- 红线不变：structure 只进 payload 展示层，`decide_action`/评分路径零引用（既有行为级隔离测试继续锁死，并补"payload 含 structure 时动作不变"断言）。

### 4.2 A2+A3 修复：capability-gated 技能激活（本方案核心机制）

新增**引擎能力注册表**（`skills/loader.py` 或独立 `skills/capabilities.py`）：

```text
ENGINE_CAPABILITIES: dict[str, EngineCapability]
  "structural_lite_smc"      → available=True  (structural-lite v2 生产中)
  "structural_lite_harmonic" → available=True
  "structural_lite_elliott"  → available=True
  "structural_lite_swings"   → available=True
  "talib_cdl"                → available=True  (M2 指标体系)
  "chanlun"                  → available=False (fail-closed，待 czsc 批准)
  "ichimoku"                 → available=True  (日级调度产出 ichimoku_v1)
  "correlation"/"pair_trading"/"seasonal" → available=False (接口预留，见 §4.4)
```

- **标识对齐（A8）**：elliott-wave/harmonic/smc 三个 SKILL.md 的 `requires_engine` 改为 `structural_lite_elliott`/`structural_lite_harmonic`/`structural_lite_smc`（一次性 frontmatter 修订，禁令段不动）。
- **门控规则**：`load_active_methodology_skills()`（新的默认入口，替换名不副实的 `load_all_...`，旧名保留为别名+弃用注释）加载逻辑 = `P1 ∪ 已启用扩展层` 中，`requires_engine is None`（纯知识）**或** `ENGINE_CAPABILITIES[requires_engine].available == True` 的技能。
- **立即效果**：smc/harmonic/elliott-wave 三技能（含 T9 知识）自动进入 technical_analyst 注入集；chanlun-interpret 因引擎 unavailable 继续被挡——**未来 czsc 批准、引擎上线后，翻一个 capability 位即自动激活，无需再改加载逻辑**。这就是把 A3 的巧合安全变成机制安全。
- 注册表首版为静态声明（人工维护，随引擎上线翻位）；是否升级为运行时探测（查 indicator_frames 有无该 schema 数据）留作阶段三选项，首版不做——静态声明可测试、可审计、无运行时开销。

**A7 体量预算**：`prompt_excerpt()` 增加预算约束——每技能注入摘要≤上限（建议 1200 字符，超长技能取"解读口径+失效条件"节而非全文）；每角色技能总注入≤上限（建议 6000 字符）；超限时按 P1>L1>L2 优先级截断并在 prompt 尾注明"另有 N 个技能未注入"。防回归测试锁死预算。

### 4.4 A4 孤儿引擎处置（决策落档）

**决策：ichimoku 接入，其余三个显式标注"接口预留"。** 理由：ichimoku 是技术分析师日常口径、计算轻（纯 pandas）、可直接挂进既有 `analytics.structural.ashare.daily` 任务顺带计算（同一批 K 线输入，边际成本≈0）；correlation/pair-trading 的消费场景在组合层（方案 19/16 的持仓分析），seasonal 信息量待 T11 验证——三者接入动力不足，强行接入违反"没有消费方不建生产线"原则。
- ichimoku：`StructuralMethodologyRefreshService` 增加 ichimoku 帧计算入库（`ichimoku_v1` horizon），capability 翻位激活 ichimoku 技能。
- 其余三个：SKILL.md 增加一行"引擎已实现未接入，等待消费场景（方案 16/19/T11）"；capability 保持 False；本方案进度表记录决策，不再是含混状态。

## 5. 引擎 / skill / 圆桌 / 前端边界设计（固化为架构约定）

```text
确定性引擎层   只算结构，输出带 evidence_id/confidence/caveats 的帧 → indicator_frames
                不知道 skill 存在，不知道谁消费
能力注册表     引擎→可用性 的唯一事实源；skill 激活的唯一依据
skill 层       只解读，声明 requires_engine；无引擎能力则不被加载（机制保证，非清单巧合）
圆桌层         role-scoped 上下文（structure 仅 technical_analyst）+ role 对应技能注入
                模型只见"已算好的证据 + 解读口径"，红线三层防护不变
推荐 payload   结构证据的精简摘要+evidence_id 索引（展示与审计），不进 decide_action/评分
前端层         只渲染 payload 摘要；完整证据凭 evidence_id 可追溯；无数据如实空态
```

跨层禁令（防回归测试各一条锁死）：skill 不产生新事实；结构不进评分/动作；risk_rebuttal 不接收结构（直至 T11 解禁 T14）；无 capability 技能不注入；前端不造假数据。
