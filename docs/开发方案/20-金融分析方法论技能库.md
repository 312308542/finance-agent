### 1.2 决策：选范围 3（全做，含确定性引擎）

总负责人定调"**我需要的是准确性**"。这个要求本身决定了范围：方法论若只给 LLM 一个知识 skill、让它从原始 K 线自己"数浪、找中枢"，**是最不准的做法**（模型会幻觉结构）。要准确 = 结构必须由**确定性引擎**算出，skill 只负责"拿到算好的结构后怎么解读"。

> **关键印证（Vibe-Trading 缠论 skill）**：它用成熟库 `czsc`（waditu/czsc）自动算分型/笔/中枢/买卖点，skill 只定义买卖点语义——不是让 LLM 算。这正是本项目 §7"成熟库计算、本项目适配编排"原则，也是红线的正确落法。

## 2. 核心架构原则（准确性的根本保证）

> **计算归确定性引擎，解读归 skill，LLM 永不自己算结构。**

技能分两类，处理方式不同：

| 类型 | 例 | 处理 |
| --- | --- | --- |
| **A 纯知识型** | 行为金融偏差、板块轮动判别框架、估值方法、K 线形态含义 | 只写 SKILL.md，指导圆桌分析师**解读口径**，不产生新数字。轻，合红线。 |
| **B 计算型** | 缠论（笔/中枢）、艾略特波浪（浪型计数）、harmonic（XABCD）、ichimoku（五线） | **先建确定性引擎**（优先成熟库：缠论→`czsc`、harmonic→`pyharmonics`、基础指标→已有 ta-lib），写入 `indicator_frames`/`signal_snapshots`；skill **只解读引擎输出**。重，但唯一准确且合红线的做法。 |

**红线（写进每个 skill 的禁令段 + 防回归测试）**：

- skill 不得让模型自己计算笔/中枢/浪型/形态——只能引用引擎输出。
- skill 不得引用引擎输出/入库数据之外的事实。
- skill 不得给目标价、不得改确定性分数/信号方向/风险标记。
- 计算型方法论无对应确定性引擎时，该 skill **不得上线**（宁缺毋假）。

## 3. 仓库内 SKILL.md 格式（适配确定性模型）

每个 skill 一个目录 `src/finance_agent/skills/<name>/SKILL.md`，结构：

```markdown
---
name: chanlun_interpret
category: technical            # technical/factor/flow/event/risk/portfolio/behavioral
markets: [ashare, crypto]
requires_engine: chanlun       # B 型必填：依赖的确定性引擎；A 型为 null
roundtable_role: technical_analyst   # 被哪个圆桌角色加载
---
## 适用场景
## 输入（只读：引擎输出 + 工具层事实）
## 解读口径（怎么读已算好的结构）
## 禁令（不得自己计算/不得引用库外数据/不得给目标价/不得改分数）
```

skill 不是给 Hermes 的对话 skill，而是**圆桌分析师角色的解读指南**：方案 18/04 的分析师节点按 `roundtable_role` 加载对应 skill，注入 prompt 指导解读。借鉴 Vibe-Trading 的 SKILL.md 思想，但适配我们"确定性事实 + 只解读"的模型。

## 9. 风险与注意事项

- **准确性的红线**：B 型方法论无确定性引擎时该 skill 禁止上线——宁可缺这个方法论，也不让 LLM 假装会算。
- 成熟库许可与稳定性：czsc/pyharmonics 等装依赖前确认许可证（§13 纪律）和维护状态；优先成熟库不手写（§7）。
- 范围 3 是大工程：P1 便宜先做，P2 缠论试点验证模式，P3 每个引擎独立排期，避免一次性铺开 79 个技能失控。
- skill 是圆桌角色的解读指南，**不是** Hermes 对话 skill（那是方案 01/16），两者不要混。
