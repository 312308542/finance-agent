# 方案 08：人工确认与操作闭环（O9）

> 优先级：P2 ｜ 批次 4（最后）｜ 依赖：方案 07（前端确认入口）、方案 03/04（needs_human 复核态与反馈 API）
> 前置阅读：`00-总体规划与执行约定.md`

## 1. 背景与现状

这是"私人金融助手"区别于一次性荐股工具的最后一环：**建议 → 用户确认 → 订单草案 → 外部执行登记 → 复盘比较 → 记忆反写**。

已有资产：

- `decision_logs`：建议、用户确认与反馈记录表（已迁移并冒烟），`MemoryService.record_user_feedback` 已实现 accepted/rejected/modified 反馈写入与源记忆置信度调整。
- `review_tasks` + `MemoryService.complete_review_task`：复盘任务与复盘结论反写已实现。
- 方案 03 产出 `pending_user_confirmation` 决策状态；方案 04 产出反馈 API；方案 07 产出待确认列表与反馈 UI。
- `OrderDraft` 在 `docs/领域协议.md` 中已有协议定义，但无表、无代码。

**缺口**：确认后没有下文——没有订单草案实体、没有执行登记、复盘不比较"建议 vs 实际执行 vs 后续表现"。

**红线（重申，凌驾本方案一切设计）**：系统永不真实下单。本方案终点是"草案 + 用户自行执行后的登记"，不接任何券商/交易所写接口。

## 2. 目标与非目标

**目标**

1. 用户确认接受某建议后，可生成结构化订单草案（仅文档性质）。
2. 用户在外部完成交易后可登记执行结果（价格、数量、时间、备注）。
3. 执行登记自动更新持仓、生成复盘任务；复盘比较建议价/执行价/后续表现并反写 Finance Memory。
4. 全链路审计：建议 → 确认 → 草案 → 执行 → 复盘五个节点串在 `decision_logs` 引用链上。

**非目标**

- 不做订单状态机（无"已报/部分成交"概念——草案没有生命周期，只有"已生成/已作废"）。
- 不做自动持仓同步（券商接口）；持仓更新仅来自用户登记。
- 不做绩效归因分析（quantstats 接入属量化研究 TODO）。

## 3. 技术方案

### 3.1 数据模型（迁移 `20260613_0018_create_action_loop_tables.py`）

**`order_drafts`**

| 列 | 说明 |
| --- | --- |
| order_draft_id (PK) | `draft:{owner}:{asset}:{ts}` |
| owner_id / portfolio_id / asset_id / market | 归属 |
| decision_log_id (FK 语义) | 来源决策，必填——草案必须可追溯到建议 |
| action | buy / sell / add / reduce（枚举与推荐动作映射） |
| suggested_price_range (JSONB) | 建议价区间 + 依据（如"评分时点收盘价 ±2%"） |
| suggested_position_ratio | 建议仓位比例（来自组合经理观点，可空） |
| constraints (JSONB) | 风险约束快照（止损参考、集中度提醒、复核结论） |
| status | drafted / superseded / cancelled |
| disclaimer | 固定免责声明文本，非空 |
| created_at / updated_at | |

**`execution_records`**

| 列 | 说明 |
| --- | --- |
| execution_id (PK) | |
| owner_id / portfolio_id / asset_id / market | |
| order_draft_id（可空） | 允许登记无草案的自主操作（用户自己买的也要能记账） |
| decision_log_id（可空） | |
| action / executed_price / executed_quantity / executed_at | 用户填报 |
| fee / note | 可选 |
| source | `user_reported`（唯一合法值，为未来留枚举位） |
| created_at | |

设计要点：两表均为 PostgreSQL 普通表；不动既有 `positions` 表结构——持仓更新走服务层逻辑。

### 3.2 服务层 `src/finance_agent/application/action_loop_service.py`

```text
class ActionLoopService:
    confirm_decision(decision_log_id, feedback, modified_action=None)
        # 包装既有 record_user_feedback；feedback=accepted 且动作可执行时返回"可生成草案"标记
    create_order_draft(decision_log_id) -> OrderDraft
        # 校验：决策状态为 accepted；高风险动作必须复核状态为 approve 或 needs_human 已确认
        # 同一决策再次生成时旧草案置 superseded
    record_execution(payload) -> ExecutionRecord
        # 写 execution_records；调持仓更新；生成复盘任务（review_tasks，due 默认 T+20 交易日）
        # 写 decision_logs 执行关联事件 + assistant_memories（type=execution_note）
    update_position_from_execution(execution)
        # buy/add: 加权平均成本更新或新建 position；sell/reduce: 减数量，清仓置 closed
        # 数量/方向校验：卖出数量不得超过当前持仓，违规直接报错不静默修正
    compare_execution_outcome(review_task)
        # 复盘时点计算：建议价 vs 执行价滑差、执行至今收益、同期市场基准（候选池均值）对比
        # 产出结构化 outcome 喂给 complete_review_task（既有反写链）
```

高风险闸门：`create_order_draft` 对 sell/swap/大仓位动作检查方案 03 的复核结论——`reject` 状态决策**不能**生成草案，返回明确错误与复核理由。

### 3.3 API 与前端

API（延续方案 07 模式）：

- `POST /api/decisions/{id}/confirm`（包装 confirm_decision，区别于纯反馈：会推进闭环状态）
- `POST /api/decisions/{id}/order-draft`
- `GET /api/order-drafts?owner_id&status`
- `POST /api/executions` / `GET /api/executions?owner_id&limit`
- `GET /api/reviews/upcoming?owner_id`（待复盘任务）

前端（在方案 07 页面上增量）：

- recommendation/portfolio 页：建议行增加「确认」入口 → 确认后出现「生成订单草案」→ 草案卡片（显著免责声明 + "请在您的交易软件中自行操作"）。
- 新增 portfolio 页子区「执行登记」表单与历史列表。
- risk/提醒中心：待复盘任务到期提醒。
- 草案卡片**没有**任何形似"提交订单"的按钮——只有「我已在外部执行，去登记」链接。

### 3.4 复盘闭环

- 复盘任务到期由方案 02 的调度体系驱动（新增 `analytics.reviews.due` 任务：扫描到期 review_tasks → 调 `compare_execution_outcome` → `complete_review_task` 反写记忆）。
- 复盘结论结构：`{建议动作, 用户实际动作, 滑差, 持有收益, 基准对比, 教训文本}`；教训文本第一版规则生成，方案 04 骨架就绪后可升级为模型生成（标 fallback 模式，复用圆桌降级协议）。

验收标准：

- 一条建议的完整生命周期五节点全部可在审计链查到，且每个节点引用前一节点 ID。
- 复核被驳回的卖出建议无法生成草案（API 返回明确拒绝理由）。
- 复盘反写后，`memory.recall_asset_memories` 能召回该资产的执行教训。
- 全仓库搜索不存在任何对外下单调用；草案 UI 无"下单/提交订单"字样。

## 6. 风险与注意事项

- **持仓更新是本方案唯一的"写真实资产状态"操作**，`update_position_from_execution` 必须事务完整 + 幂等（同一 execution_id 重复提交不得重复加仓）；写前跑 gitnexus_impact 确认 positions 的全部读方。
- 免责声明文本与"非投资建议"边界检查进单测（断言草案与 UI 文案包含声明），防止后续无意删除。
- 复盘的"后续表现"依赖行情数据新鲜度：数据缺口时复盘结论必须标注 `partial`，不得用过期价格得出"建议错误"的结论。
- 本方案完成即 V2.0 闭环达成，完成后把 `docs/优化版本进度跟踪表.md` 总体路线表 V2.0 置为已完成，并通知总负责人做整体验收。
