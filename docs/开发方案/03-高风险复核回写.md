# 方案 03：高风险复核回写（O3 收尾）

> 优先级：P0 ｜ 批次 2 ｜ 依赖：方案 02（复核批处理走调度任务入口）
> 前置阅读：`00-总体规划与执行约定.md`

## 1. 背景与现状

已有资产：

- `src/finance_agent/agents/runtime/policies.py`：`HighRiskReviewPolicy`——判断哪些裁决需要高风险复核（卖出、换股、大仓位调整、强冲突信号、数据缺口）。
- `src/finance_agent/agents/runtime/model_router.py`：`ModelRoutingPolicy`——常规分析路由 `deepseek-v4-pro`，高风险复核路由 `gpt-5.5-pro`；路由结果已作为 `model_route` 审计事件写入 `agent_workflow_events`。
- 6 个 Workflow 在需要复核时会生成**复核协议**（复核输入、路由目标）并写 `model_review` 审计事件，但**到此为止**——没有任何代码真正调用复核模型，也没有结果回写。
- `src/finance_agent/agents/runtime/model_client.py`：OpenAI-compatible 客户端，刚加固了瞬时网络错误重试（`_post_chat_completion_with_retry`）。
- 模型配置中心：`model_providers` / `model_instances` / `model_routing_rules` 表 + `finance-agent models` CLI 已可用。
- 报告模板（`agents/reports/templates.py` `build_chinese_decision_report`）已有"复核状态"section，当前永远是"待复核"。

**缺口**：复核是整个安全设计的最后一道闸，现在是"已声明、未执行"。卖出/换股建议带着"待复核"标记直接进了报告。

## 2. 目标与非目标

**目标**

1. 待复核事件能被批量取出、真实调用复核模型、解析结构化结论并回写审计链路。
2. 复核结论反映到决策日志与中文报告（复核通过 / 驳回 / 需人工 / 复核不可用四态）。
3. 模型不可用时不阻塞：标记 `review_unavailable` 并下调结论置信度，等待下轮重试。
4. 提供 CLI 与调度任务两个入口。

**非目标**

- 不改变 `HighRiskReviewPolicy` 的触发条件（哪些动作算高风险维持现状）。
- 不做人工确认 UI（归方案 07/08，本方案只产出 `needs_human` 状态供其消费）。
- 聊天摘要抽取移到本方案"二期"，不阻塞主线。

## 3. 技术方案

### 3.1 新增 `HighRiskReviewService`

新文件 `src/finance_agent/agents/runtime/high_risk_review_service.py`：

```text
list_pending_reviews(owner_id, limit)        # 从 agent_workflow_events 取 event_type="model_review"
                                             # 且 payload.review_status 为 pending/unavailable 的事件
execute_review(review_event) -> ReviewResult # 组装 prompt -> 调模型 -> 解析 -> 回写
run_pending_reviews(owner_id, limit) -> dict # 批量入口，返回计数摘要
```

**复核输入组装**：从复核协议 payload 取 workflow 裁决、动作、评分、信号、风险反驳、数据质量与证据 ID；通过 `FinanceToolRuntime` 补取该资产当前事实上下文（防止复核用的是过期快照——复核时点的事实优先）。

**Prompt 设计**：系统提示固化复核员角色——"你是高风险动作复核员，只能输出 JSON，职责是否决或放行，不是重新分析"。要求输出：

```json
{
  "verdict": "approve | reject | needs_human",
  "confidence": 0.0,
  "reasons": ["..."],
  "blocking_risks": ["..."],
  "data_gaps": ["..."]
}
```

**解析与校验**：严格 JSON 解析 + pydantic 模型校验；解析失败重试一次（重发并附"上次输出不合法"提示）；再失败按 `review_unavailable` 处理。**禁止**把自由文本当成结论。

**回写**（同一事务内完成）：

1. 新增 `model_review_result` 审计事件（payload 含 verdict、reasons、模型 ID、耗时、token 用量如可得）。
2. 更新源 `model_review` 事件 payload 的 `review_status`。
3. 更新对应 `decision_logs` 记录：`reject` → 决策状态置为 `rejected_by_review` 并要求 Workflow 输出降级为 watch/hold；`needs_human` → 置 `pending_user_confirmation`。
4. 报告：复核完成后在 `agent_workflow_events` 写 `report_review_appended` 事件，payload 带可渲染的复核结论 Markdown 片段（报告本体已落库不可变，前端渲染时拼接，见方案 07）。

### 3.2 路由与降级

- 模型选择走 `ModelRoutingPolicy` 既有高风险路由，不在 Service 里写死模型名。
- 复核模型未配置 / 调用失败（重试耗尽）→ `review_unavailable`：写审计、保持 pending 队列里可重试、决策置信度乘以惩罚系数（默认 0.7，常量集中定义）。
- 安全缺省：`reject` 与 `needs_human` 的处理是收紧，`review_unavailable` 时**绝不**默认放行——报告中持续显示"复核未完成"。

### 3.3 入口

1. **CLI**：`finance-agent agent review-pending --owner-id ... --limit 10 [--dry-run]`，dry-run 只列队列不调模型。
2. **调度任务**：`sync_task_type = analytics.high_risk_reviews`，按方案 02 的模式接入 `BaseDataScheduler`，挂在 `agent.loop.consume` 的 `after_success`（Agent 跑完 Workflow 后立刻复核），另加低频兜底。

### 3.4 二期（主线完成后）：聊天摘要抽取

- `assistant_chat_sessions` 超过 N 轮后由常规模型生成会话摘要，写入 `assistant_memories`（type=`chat_summary`），供后续会话和 Workflow 引用。复用本方案的模型调用与 JSON 校验骨架。任务拆解里单列，可顺延。

- 复核模型断网时全链路无异常，事件保持可重试状态。

## 6. 风险与注意事项

- **不要在 Workflow 执行路径里同步等复核**：复核模型慢且贵，主链路写完协议即返回，复核永远异步。这是现有架构的设计意图，保持它。
- 复核 prompt 与解析 schema 集中放在一个模块（建议 `agents/runtime/review_protocol.py`），别散进 Service——方案 04 的圆桌节点要复用同一套 JSON 校验骨架。
- 真实联调用的 API key 走 `models` CLI 配置进数据库，不进代码、不进 `.env` 提交。

## 8. 附录

### 8.1 T1 现状盘点：复核协议与决策日志结构

**`model_review` 事件来源**

- `src/finance_agent/agents/workflows/langgraph_graphs.py` 的 `build_high_risk_review_items` 会先为每个决策构造复核项：`asset_id`、`decision_type`、`trade_action`、`requires_review`、`reason`。
- `src/finance_agent/agents/runtime/model_router.py` 的 `ModelRoutingPolicy.build_review_result` 再补出 `model_review` 协议。
- `src/finance_agent/agents/personal_assistant.py` 的 `build_workflow_node_events` 会把 `high_risk_reviews` 拆成两类审计事件：
  - `high_risk_review:{index}`：payload.output 为完整复核项，包含 `model_review`。
  - `model_review:{index}`：payload.output 只保存 `model_review` 协议。
- `src/finance_agent/agents/runtime/langgraph_adapter.py` 的 `classify_workflow_event_type` 将 `model_review:*` 归类为 `event_type="model_review"`，最终由 `WorkflowAuditRepository.insert_event` 写入 `agent_workflow_events`。

**当前 `model_review` payload 结构**

当前代码状态与本方案草稿存在一个命名差异：现有待执行状态不是 `pending`，而是 `requires_model_review`。

```json
{
  "engine": "langgraph",
  "node": 7,
  "output_keys": ["review_input", "review_model", "review_status", "route", "summary"],
  "output": {
    "review_status": "requires_model_review",
    "review_model": "gpt-5.5-pro",
    "route": {
      "task": "high_risk_review",
      "model_key": "gpt-5.5-pro",
      "model_name": "GPT-5.5 Pro",
      "provider": "openai",
      "role": "high_risk_reviewer",
      "reason": "卖出、换股/换币、强风险、数据缺口或信号冲突需要 GPT-5.5 Pro 复核。",
      "workflow_type": "recommendation_decision",
      "asset_id": "ashare:600519",
      "decision_type": "recommendation_sell"
    },
    "summary": "该决策已触发高风险复核，等待上层模型客户端执行。",
    "review_input": {
      "asset_id": "ashare:600519",
      "decision_type": "recommendation_sell",
      "trade_action": "sell",
      "decision_summary": "示例摘要",
      "risk_context": {
        "decision_type": "recommendation_sell",
        "suggested_action": "sell",
        "severity": "high",
        "confidence": 0.7,
        "data_quality_status": "available",
        "risk_severities": ["high"],
        "has_conflicting_signal": false
      }
    }
  }
}
```

未触发复核时，`output.review_status="not_required"`、`review_model=null`、`route=null`、`review_input={}`。因此后续服务的待处理查询应按代码现状筛选：

- 当前待复核：`agent_workflow_events.event_type="model_review"` 且 `payload.output.review_status="requires_model_review"`。
- 后续可重试失败：T3 实现后新增 `review_unavailable`，也纳入待处理队列。
- `agent_workflow_events` 本身没有 `owner_id` 和 `workflow_type`，需要通过 `workflow_run_id` 关联 `agent_workflow_runs` 后再按 `owner_id` 过滤。

**`decision_logs` 可更新字段**

`decision_logs` 当前 ORM 字段为：

- 主键和归属：`decision_id`、`owner_id`、`portfolio_id`、`asset_id`。
- 来源引用：`source_recommendation_id`、`source_alert_id`、`workflow_run_id`。
- 决策主体：`decision_type`、`suggested_action`、`user_action`、`summary`。
- 证据引用：`reason_ids`、`risk_ids`、`evidence_ids`。
- 审计扩展：`created_at`、`payload`。

当前没有独立 `status` 或 `confidence` 列；现有 Workflow 写入时 `user_action` 统一为 `unknown`，业务上下文放在 `payload`。因此 T2/T3 的实现口径为：

- 复核通过：保持 `suggested_action` 和 `user_action` 不强行改写，在 `payload.review_status="approved_by_review"`、`payload.review_result` 中记录模型结论。
- 复核驳回：在 `payload.review_status="rejected_by_review"` 记录驳回原因；如需要面向后续人工闭环显式过滤，可同时把 `user_action` 更新为 `rejected_by_review`。
- 需人工确认：在 `payload.review_status="pending_user_confirmation"` 记录待确认状态；如需要面向前端列表查询，可同时把 `user_action` 更新为 `pending_user_confirmation`。
- 模型不可用：在源 `model_review` 事件 payload 中写 `review_status="review_unavailable"`，并在关联 `decision_logs.payload.review_status` 记录 `review_unavailable` 和置信度惩罚，不默认放行。

`DecisionLogRepository` 当前只有 `insert_decision_log` 与 `list_recent_decisions`，没有按 `decision_id` 局部更新 payload/user_action 的方法。T3 需要新增仓储更新方法，避免通过整条 upsert 覆盖原始决策字段。
