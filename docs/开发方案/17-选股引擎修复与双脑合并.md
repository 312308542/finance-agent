# 方案 17：选股引擎修复与双脑合并

> 优先级：P0 ｜ 批次 6 ｜ 依赖：方案 15（真实数据，校准前提）、方案 16（画像）、方案 18（新因子，需同步）、方案 10（模型联调）
> 前置阅读：`14-选股能力与顾问层升级总纲.md`

## 1. 背景与现状

这是直接修"垃圾答案"的方案，对应总纲 §1.1 的 4 个病灶（均有代码证据）：

1. **评分标度与动作阈值量纲不匹配**（`recommendations/service.py:434`）：buy 要求 `total_score>=75`，但评分是"偏离中位数"的加权平均（`scoring/service.py:185`），中庸股≈50，最高分 62 → 永远 watch。
2. **缺失数据双重扣分**（`scoring/service.py:187-193`）：缺失同时砸 `total_score` 和 `confidence`，真实残缺数据必然被压成 watch。
3. **聊天与 Workflow 双脑割裂**（`chat.py:148-153`）：`_answer_model_chat` 无 `run_workflow`，圆桌/风险反驳/证据链（方案 04）在聊天里没被触达。
4. **Agent 取数复述、非目标导向**：聊天循环只 `get_latest → 复述`，不重排、不深挖、不把 watch 翻译成"还差什么"。

## 2. 目标与非目标

**目标**

1. 评分→动作改为**候选池内相对分位制 + 绝对安全地板**，按画像调阈值，让系统第一次真会说"买入"。
2. 缺失惩罚从 `total_score` 拆出，改为独立 `data_confidence` 维度，真实残缺数据不再被一票否决。
3. 聊天选股/分析意图**真正调用 Workflow**（合并双脑），复用方案 04 圆桌+风险反驳+证据链。
4. Agent 改为**目标导向**：产出可执行买入短名单，而非复述数据表。
5. 选股前置**数据真实性闸门**（消费方案 15 的就绪度报告）。

**非目标**

- 不改因子计算本身（那是方案 18）。
- 不动 Workflow 的节点编排、DTO、落库链路（只改裁决和接入）。
- 不让画像或模型篡改确定性分数（红线）。

## 3. 技术方案

### 3.1 评分→动作改为相对分位制（治病灶一+二）

改 `recommendations/service.py` 的 `decide_action`/`decide_conviction`（改前跑 `gitnexus_impact`）：

- 入参增加该标的在候选池内的**分位** `rank/total` 和**画像** profile：
  - 头部分位（阈值按画像：进取者前 20%、稳健者前 8%）+ 无 critical/high 风险 + 过绝对地板 → `buy_candidate`。
  - 中部 → `watch`，尾部/bearish → `avoid`。
- **绝对安全地板**：`base_score < 45`（地板值由方案 15 真实分布定）即使排第一也不给 buy，防"矮子拔将军"。
- 缺失惩罚从总分拆出（改 `scoring/service.py`）：`total_score` 只反映可用维度的真实水平，缺失体现为独立 `data_confidence`，在报告里作为"证据完整度"提示，不再二次绞杀。
- **校准依据**：分位线和地板值必须参照方案 15 的真实分数分布定，不拍脑袋；写进 `docs/选股数据覆盖基线.md` 的校准记录。

### 3.2 聊天真正调用 Workflow（治病灶三，架构关键）

改 `chat.py`：`recommendation_lookup` 和单标的分析意图，从"浅层读工具循环"改为"调 Workflow + 模型叙述"：

- `recommendation_lookup` → `interface.run_workflow("recommendation_decision", profile=...)` → 取回圆桌观点/风险反驳/evidence → 聊天模型基于**这份深度结果**作答。
- 单标的追问 → `asset_deep_analysis`。
- 聊天模型的角色从"自己查数总结"变成"把 Workflow 的结构化输出翻译成对话"——方案 04 的全部投资（圆桌真实模型、风险反驳、evidence 白名单）立刻被复用。
- 保留浅层只读工具作为补充追问（如用户问某个具体字段），但选股结论必须来自 Workflow。

### 3.3 Agent 目标导向（治病灶四）

- 为"适合买入"类意图定义**成功标准 = 产出可执行买入候选短名单**（总纲 §1 的"好答案规格"），写进 system prompt 硬约束："你的任务是回答用户诉求并给出可行动建议，不是复述数据表。"
- 编排：取最新推荐 → 按买入适配度（含画像）重排筛 Top N → 对 Top N 调 `asset_deep_analysis` 深挖 → 输出"排序 + 每只为什么 + 还差什么才升级 + 风险反驳 + 确认边界"。
- 修复字段缺失：取数补全名称/评分（垃圾答案里 Top 3-5 是 `—` 的 bug）。

### 3.4 数据真实性闸门（治沙箱数据问题）

- 回答选股前调方案 15 的 `recommendation_readiness`：
  - 数据过期/未来时间戳/沙箱标记 → **开头就明确拒绝当作可执行清单**，主动提议触发新真实推荐运行，而非把沙箱数据列成表最后小字提示。
  - 数据就绪 → 正常出短名单。

## 6. 风险与注意事项

- `scoring/service.py` 和 `decide_action` 是推荐链路核心，被多处引用：**改前必跑 gitnexus_impact**，且保证"未指定画像/分位时逐字节兼容旧行为"。
- **校准必须在真实数据上做**（依赖方案 15）——这是 T3 不能提前于方案 15 的硬约束。
- 双脑合并后聊天会真实调模型 + Workflow，延迟和成本上升：用方案 04 的 `roundtable_model_roles` 收缩控制，测试用 fake client。
- 红线：相对分位制只是改"动作裁决"，不改 `total_score` 本身；画像只调阈值不改分数。
