# 数据库设计

本文档定义 Hermes 私人金融助手与 AI 标的推荐引擎的数据库表设计。第一版同时覆盖 A 股和数字货币，但二者是两条独立推荐链路，不能混排或合并成一个推荐榜。两条链路共用基础设施和协议形态，分别运行推荐子链路：

```text
候选池
 -> 数据采集
 -> 因子计算
 -> 初筛规则
 -> 多维评分
 -> Agent 分析
 -> 风险反驳
 -> 推荐排序
 -> 中文解释报告
```

AKShare A 股数据能力与推荐链路映射见：`docs/AKShare能力矩阵.md`。

数据库目标：

- 支撑 A 股和数字货币共用一套基础设施，但推荐运行、初筛、评分、排序和报告按市场独立执行。
- 支撑私人金融助手的持仓监控、私人观察池、触发提醒、决策日志、长期记忆和复盘。
- 区分 `asset_universes` 与私人观察池：前者是上游推荐输入范围，后者是主 Agent 长期维护的潜力标的清单。
- 全环境统一使用 PostgreSQL + TimescaleDB：业务实体用普通 PostgreSQL 表，行情和衍生品时间序列用 TimescaleDB hypertable。
- 保留原始数据，方便追溯和审计。
- 结构化字段用于查询、筛选、排序和索引。
- 复杂协议全文保存到 `payload JSON`，方便协议升级。
- 不把 Agent 的自然语言输出当作唯一事实来源，所有推荐必须能追到因子、信号、风险和证据。
- 不把长期记忆当作事实数据库；本项目的 Finance Memory 只能保存偏好、历史建议、用户反馈、关注理由和复盘结论，事实仍以行情、财务、风险、推荐和证据表为准。Hermes-agent 自带的通用记忆不进入金融事实表，只作为上层 Agent 的辅助上下文。

## 1. 设计原则

### 1.1 存储选型

统一方案：

- PostgreSQL：保存资产、候选池、因子、评分、推荐、证据、回测等业务数据。
- TimescaleDB：保存 K 线、资金费率、未平仓量、多空比等时间序列数据。

环境要求：

- 开发、测试、演示和生产都使用 PostgreSQL + TimescaleDB，保持 schema、约束、hypertable 行为一致。
- 不为主链路提供 SQLite 或普通 PostgreSQL 降级模式，避免开发环境绕过 TimescaleDB 的唯一约束、时间分区和压缩策略。
- SQLite 只能用于完全脱离推荐主链路的一次性脚本实验，不能作为应用运行环境或测试环境。

需要使用 TimescaleDB hypertable 的表：

- `market_bars`
- `crypto_derivative_snapshots`

后续数据量变大时，也可以评估把这些表迁移或同步到 ClickHouse / Parquet 做离线研究，但系统主库仍以 PostgreSQL + TimescaleDB 为准。

### 1.2 共用表优先，运行链路独立

A 股和数字货币都属于 `assets`。市场差异通过 `market`、`exchange`、`asset_type`、`payload` 和专属快照表表达。

共用表不代表共用同一次推荐运行。`ashare`、`crypto_spot`、`crypto_future` 必须分别构建候选池、分别初筛、分别评分、分别排序。`recommendation_runs.market` 不使用 `mixed`，业务服务和仓储写入都需要拒绝混合市场候选池。

共用表：

- `market_bars`
- `crypto_derivative_snapshots`
- `market_calendars`

- `screening_results`
- `screening_result_items`
- `asset_scores`
- `signal_snapshots`
- `risk_findings`
- `recommendation_runs`
- `recommendation_run_universes`
- `asset_recommendations`
- `agent_analysis_runs`
- `agent_analysis_items`
- `evidence`
- `portfolios`
- `positions`
- `watchlists`
- `watchlist_items`
- `asset_theses`
- `monitoring_alerts`
- `decision_logs`
- `assistant_memories`
- `assistant_chat_sessions`
- `assistant_chat_messages`
- `review_tasks`
- `agent_workflow_runs`

专属表：

- A 股：`fundamental_snapshots`、`capital_flow_snapshots`
- 数字货币：`crypto_derivative_snapshots`

### 1.3 字段和 payload 的边界

需要高频查询、筛选、排序的字段单独建列。

例如：

- `asset_id`
- `symbol`
- `market`
- `timeframe`
- `as_of`
- `status`
- `total_score`
- `rank`
- `action`

变化快、字段多、不同市场差异大的内容放入 `payload JSON`。

例如：

- AKShare 原始响应。
- Binance 原始响应。
- 因子分组明细。
- Agent 分析摘要。
- 推荐理由和风险反驳。
- 回测参数和图表数据。

### 1.4 原始数据、计算结果和实时缓存的边界

数据库不是把所有实时计算过程都长期落库。第一版按下面规则设计：

- `market_bars`、`fundamental_snapshots`、`capital_flow_snapshots`、`crypto_derivative_snapshots`、`event_records` 是原始或标准化基础数据，长期保存，用于回放、复算、审计和回测。
- `indicator_frames`、`factor_frames`、`signal_snapshots`、`asset_scores` 是推荐链路里的计算结果快照，按推荐运行、分析运行、每日刷新或固定周期刷新保存。
- 技术指标不是为每根 K 线、每个参数组合持续落库的实时流水。第一版只保存推荐解释、排序和复盘需要的关键指标值、输入窗口和计算版本。
- 因子、信号和评分不是事实源，事实源仍然是行情、财务、资金流、衍生品和事件数据。它们落库的原因是保证一次推荐可以复盘，而不是替代实时计算引擎。
- 盘中实时计算可以使用内存、Redis 或任务运行上下文承载；只有进入推荐候选、评分、风险反驳或报告证据链的结果才写入业务表。

因此，查询推荐结果时优先读取 `asset_scores`、`signal_snapshots`、`risk_findings` 和 `asset_recommendations`；需要重新计算或做更长周期研究时，再回到 `market_bars` 等基础数据。

Redis 作为缓存层使用，但不改变数据库事实源边界：

- PostgreSQL + TimescaleDB 是 Source of Truth，保存所有可审计、可回放、可复算的数据。
- Redis 保存热数据、Agent 输入上下文、任务锁和 Provider 熔断状态，数据可以过期或丢失。
- Agent 上下文缓存只能保存数据库可重建的数据包，不能作为推荐结果或证据链的唯一来源。
- `raw_records`、`event_records`、`evidence`、`asset_recommendations`、`agent_analysis_runs`、`agent_analysis_items` 永远需要落库。

推荐的 Agent 读取路径：

```text
基础数据表
 -> AgentContextBuilder
 -> Redis 短 TTL 上下文缓存
 -> Agent 分析
 -> 推荐、风险、证据引用和 Agent 输出落库
```

### 1.5 时间字段

统一使用带时区时间。

- `as_of`：数据本身对应的市场时间。
- `collected_at`：系统采集时间。
- `created_at`：系统生成记录时间。
- `updated_at`：系统最后更新时间。

### 1.6 状态字段

所有核心数据表都应有 `status`。

```text
available    完整可用
partial      部分可用
unavailable  不可用
stale        过期
error        获取或计算失败
```

### 1.7 ID 规范

建议 ID 使用可读字符串，方便调试和跨表追溯。

```text
asset_id:             ashare:600519 / crypto_spot:BTCUSDT
universe_id:          universe:hs300:20260511
raw_record_id:        raw:akshare:stock_zh_a_hist:600519:20260511
indicator_frame_id:  ind:BTCUSDT:1d:20260511
factor_frame_id:      factor:600519:swing:20260511
screening_item_id:    screening_item:hs300:600519:20260511
score_id:             score:BTCUSDT:swing:20260511
recommendation_id:    asset_rec:600519:swing:20260511
agent_analysis_id:    agent:technical:BTCUSDT:20260511
evidence_id:          ev:binance:kline:BTCUSDT:20260511
```

### 1.8 TimescaleDB 分区原则

`market_bars` 和 `crypto_derivative_snapshots` 按时间列创建 hypertable：

- `market_bars` 使用 `timestamp` 作为时间列。
- `crypto_derivative_snapshots` 使用 `as_of` 作为时间列。

TimescaleDB 约束规则必须在表结构里体现：

- hypertable 的主键或唯一约束必须包含时间列。
- `market_bars` 不使用单列 `id` 作为主键，使用 `asset_id, timeframe, timestamp, source, adjustment` 作为复合主键或唯一约束。
- `crypto_derivative_snapshots` 不使用单列 `snapshot_id` 作为主键，使用 `asset_id, as_of, source` 作为复合主键或唯一约束。
- 涉及唯一约束的文本字段不能为 `NULL`，例如 `adjustment` 默认使用空字符串。

建议按市场和周期设置不同 chunk 粒度：

| 数据 | 推荐 chunk 粒度 |
| --- | --- |
| A 股日线 | 6 个月 |
| A 股分钟线 | 7 天到 1 个月 |
| 数字货币 1d / 4h / 1h | 1 个月 |
| 数字货币 1m / 5m | 1 天到 7 天 |
| 衍生品快照 | 7 天到 1 个月 |

M0 可以先统一使用 1 个月 chunk，后续根据数据量调整。

建议开启压缩策略：

- 高频 K 线：30 天后压缩。
- 日线和低频数据：180 天后压缩。
- 衍生品快照：30 天后压缩。

保留策略先不自动删除，避免影响回测和审计。后续如数据量过大，再对 1m/5m 高频数据设置归档到 Parquet。

## 3. 资产与候选池

### 3.1 assets

资产主数据表。A 股、数字货币现货、数字货币合约都在这里登记。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | string | 主键，例如 `ashare:600519`、`crypto_spot:BTCUSDT` |
| `symbol` | string | 交易代码 |
| `name` | string | 展示名称 |
| `market` | string | `ashare`、`crypto_spot`、`crypto_future` |
| `asset_type` | string | `stock`、`crypto`、`cash` 等 |
| `exchange` | string | SSE、SZSE、Binance 等 |
| `currency` | string | CNY、USDT、USD |
| `sector` | string | A 股行业或数字货币分类，可为空 |
| `base_asset` | string | 数字货币基础资产，例如 BTC |
| `quote_asset` | string | 数字货币计价资产，例如 USDT |
| `tradable` | bool | 当前是否可交易 |
| `status` | string | 数据状态 |
| `payload` | JSON | 市场专属扩展字段 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

主键：

- `asset_id`

索引：

- `idx_assets_market_symbol`：`market, symbol`

- `idx_assets_sector`：`sector`
- `idx_assets_status`：`status`

- `market, symbol`

### 4.2 market_bars

标准 OHLCV 行情表，A 股和数字货币共用。全环境使用 TimescaleDB hypertable。

| 字段 | 类型 | 说明 |
| --- | --- | --- |

- `market_bars` 是 TimescaleDB hypertable，不使用单列 `id` 作为主键。
- `adjustment` 必须使用非空字符串，数字货币统一为空字符串，避免唯一约束中 `NULL` 导致重复写入。
- A 股推荐默认使用已收盘日线；数字货币可以使用 1h/4h/1d，但 `is_closed=false` 的最新 K 线只能作为弱证据。

索引：

- `idx_market_bars_asset_tf_time`：`asset_id, timeframe, timestamp`
- `idx_market_bars_market_symbol`：`market, symbol`
- `idx_market_bars_timestamp`：`timestamp`
- `idx_market_bars_closed`：`asset_id, timeframe, is_closed, timestamp`

TimescaleDB 设置：

```sql
SELECT create_hypertable('market_bars', 'timestamp', if_not_exists => TRUE);
```

推荐压缩设置：

```sql
ALTER TABLE market_bars SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'asset_id,timeframe',
  timescaledb.compress_orderby = 'timestamp DESC'
);
```

建议查询模式：

```sql
-- 单标的最近 N 根 K 线
SELECT *
FROM market_bars
WHERE asset_id = :asset_id
  AND timeframe = :timeframe
ORDER BY timestamp DESC
LIMIT :limit;

-- 候选池批量取时间窗口
SELECT b.*
FROM market_bars b
JOIN asset_universe_members m ON m.asset_id = b.asset_id
WHERE m.universe_id = :universe_id
  AND b.timeframe = :timeframe
  AND b.timestamp >= :start_at
  AND b.timestamp < :end_at;
```

## 7. 因子、筛选、评分和信号

本组表保存的是“推荐时点的计算快照”，不是 Tick 级或逐 K 线实时指标仓库。服务层可以随时从 `market_bars` 重新计算指标和因子，但进入初筛、评分、Agent 分析、风险反驳和中文报告的结果必须落库，保证推荐结果可追溯、可解释、可复算。

建议保存粒度：

| 类型 | 是否长期保存 | 保存粒度 |
| --- | --- | --- |
| 技术指标 | 有限保存 | 候选标的、推荐运行、每日或固定周期刷新 |
| 因子结果 | 保存 | 进入初筛或评分的标的快照 |
| 初筛结果 | 保存 | 每次推荐运行或筛选任务 |
| 多维评分 | 保存 | 每次评分任务，用于推荐排序和复盘 |
| 信号快照 | 保存 | 进入推荐证据链的信号 |

不建议在 M0 把 RSI、MACD、均线、布林带等所有指标按所有资产、所有周期、所有参数组合持续展开成大宽表。如果后续需要做大规模因子研究，可以另建离线特征库或把历史计算结果归档到 Parquet / ClickHouse。

## 10. 私人金融助手、观察池与长期记忆

这些表支撑上层 `PersonalFinanceAgent` 长期运行：持仓监控、私人观察池、触发提醒、决策日志、金融业务记忆和复盘。它们使用普通 PostgreSQL 表，不需要 TimescaleDB hypertable。长期时序事实仍在 `market_bars`、`crypto_derivative_snapshots` 等基础表里。

这里的记忆是 Finance Memory，不是 Hermes-agent 自带通用记忆的替代品：

- Hermes Memory：由 Hermes-agent 管理，保存对话上下文、任务偏好、工具使用习惯和通用长期摘要。
- Finance Memory：由本项目管理，保存投资假设、建议理由、用户是否采纳、复盘结论、观察池变更原因和风险偏好变化。
- 数据库只存 Finance Memory 和审计记录；如果需要引用 Hermes Memory，应通过上层 Agent 上下文注入，不直接把通用记忆写入金融事实表。

Finance Memory 的存储形态采用三层：

1. 结构化事实源：`decision_logs`、`assistant_memories`、`review_tasks`、`asset_theses` 等普通 PostgreSQL 表。
2. 语义召回层：`memory_embeddings`，后续基于 pgvector 或等价能力检索相似历史场景。
3. 知识图谱层：通过 `GraphStore` 配置选择唯一图数据库后端，默认推荐 `neo4j`，也可选择 `apache_age`。

知识图谱后端规则见 `docs/知识图谱后端设计.md`：

- `graph.backend = neo4j`：默认推荐，使用 Neo4j / DozerDB 承载知识图谱、多跳查询、风险传导和后续 GraphRAG。
- `graph.backend = apache_age`：可选部署形态，适合希望减少独立中间件或资源较小的环境。
- 同一环境只能启用一个后端，不自动 fallback，不双写双读。
- 图数据库只保存从 PostgreSQL 事实表投影出的图谱，可被重建；金融事实和审计仍以 PostgreSQL 表为准。

观察池原因记忆不新增业务事实表，继续复用现有结构：`watchlist_items.reason` 保存观察项当前关注理由；`watchlist_item_events` 保存 `candidate_intake_reason`、`daily_watch_reason`、`watchlist_transition` 等可审计事件；`assistant_memories` 保存 `candidate_intake_reason` 和 `watchlist_daily_reason` 两类可召回摘要。GraphSync 会把这些事实投影为 `WatchlistEvent -> Memory` 等图谱关系。

阶段性决策：`financial_memory_edges` 已在 M2/M3 阶段落库并通过冒烟验证，短期保留为历史兼容表；新增知识图谱能力以 `GraphStore` 为准，后续完成图谱同步和查询工具验证后，再迁移旧关系并标记该表 deprecated。

#### watchlist_item_events 事件约定

观察池成员事件表来自 M3 可靠性补强，用于记录观察项从入池、每日复核、升级、剔除到用户确认的轨迹。当前不为入池原因和每日继续关注原因新增独立表，统一写入该表：

这些事件可以通过 `source_decision_id` 关联 `decision_logs`，并由 GraphSync 投影为 `WatchlistEvent -> Memory` 的图谱关系，连接到对应的 `assistant_memories`。

## 11. 模型配置中心与检索配置

本模块参考 Dify 的模型供应商配置思路：模型供应商、模型实例、默认路由和检索配置都保存到数据库。代码中仍保留 JSON/env 入口用于本地调试，但正式运行优先读取数据库配置，便于后续在 CLI、TUI 或前端页面中在线切换模型供应商。

数据库只管理“使用哪个模型、如何连接、在哪个场景路由到哪个模型、RAG 如何检索”。金融决策规则、风险阈值、Agent loop 和 Workflow 编排仍由业务代码和审计协议控制，不能把买卖判断直接写成数据库配置。

### 11.1 model_providers

| `provider_name` | string | 展示名称 |
| `base_url` | text | OpenAI-compatible API 地址 |
| `api_key` | text | API Key；CLI 和 TUI 输出必须脱敏 |
| `timeout_seconds` | int | 默认请求超时 |
| `is_enabled` | bool | 是否启用 |
| `is_default` | bool | 是否默认供应商 |
| `payload` | JSON | 扩展能力描述、限流、组织 ID 等 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

约束和索引：

## 11. 推荐主链路查询

### 12.1 获取最新推荐榜

常用查询条件：

- `market`
- `universe_id`
- `strategy`
- `horizon`
- `run_id`

推荐读取顺序：

```text
recommendation_runs
  -> recommendation_run_universes
  -> asset_recommendations
  -> asset_scores
  -> agent_analysis_items
  -> evidence
```

### 12.2 个股或单币分析页

推荐读取顺序：

```text
assets
  -> market_bars
  -> indicator_frames
  -> factor_frames
  -> asset_scores
  -> signal_snapshots
  -> risk_findings
  -> agent_analysis_items
  -> asset_recommendations
  -> evidence
```

如果是 A 股，补充：

```text
fundamental_snapshots
capital_flow_snapshots
event_records
```

如果是数字货币，补充：

```text
crypto_derivative_snapshots
event_records
```

### 12.3 私人金融助手首页

私人金融助手首页和每日复盘读取顺序：

```text
portfolios
  -> positions
  -> watchlists
  -> watchlist_items
  -> monitoring_alerts
  -> decision_logs
  -> assistant_memories
  -> review_tasks
```

如果需要给出持仓操作或换股建议，再进入：

```text
positions
  -> market_bars
  -> factor_frames
  -> asset_scores
  -> signal_snapshots
  -> risk_findings
  -> asset_recommendations
  -> agent_workflow_runs
  -> evidence
```

读取原则：

- 事实优先读行情、持仓、因子、信号、风险和证据表。
- Finance Memory 只作为用户偏好、历史建议、观察理由和复盘教训的上下文。
- Hermes Memory 只作为通用对话和任务上下文，不能单独支撑金融建议。
- CLI Chat Memory 保存 `finance-agent chat` 的会话流水，用于续聊和历史查看；它是上层交互上下文，不是金融事实源，也不是 Finance Memory。
- 观察池只代表“持续跟踪”，不代表“立即可以买”。

- `market_bars`

- `factor_frames`

- `screening_result_items`
- `asset_scores`
- `signal_snapshots`

- `recommendation_runs`
- `recommendation_run_universes`
- `asset_recommendations`
- `agent_analysis_runs`
- `agent_analysis_items`
- `evidence`

M0 目标：

- 能构建 A 股和数字货币候选池。
- 能写入标准行情。
- 能写入数字货币资金费率、未平仓量和多空比，支撑合约拥挤度分析。
- 能保存推荐时点的指标快照、因子、逐标的筛选、评分、风险反驳和推荐结果。
- 能审计每个 Agent 的输入、输出、状态和单标的分析摘要。
- 能生成 `result.json` 和 `report.md`。

### M1：增强分析质量

第二阶段实现这些表：

- `fundamental_snapshots`
- `capital_flow_snapshots`
- `event_records`
- `backtest_results`
- `performance_reports`

## 14. 后续实现建议

第一版使用 SQLAlchemy 2.x ORM 和 Alembic 迁移。

数据库部署建议：

```text
PostgreSQL 16+
TimescaleDB 2.x
```

Alembic 迁移中需要先启用扩展：

```sql
CREATE EXTENSION IF NOT EXISTS timescaledb;
```

然后再创建普通表和 hypertable。注意：TimescaleDB hypertable 的唯一约束必须包含时间列，因此：

- `market_bars` 的唯一约束使用 `asset_id, timeframe, timestamp, source, adjustment`。
- `crypto_derivative_snapshots` 的唯一约束使用 `asset_id, as_of, source`。
- 不要为 hypertable 设计不包含时间列的单列主键。
- 需要被唯一约束覆盖的可选文本字段使用空字符串默认值，不使用 `NULL`。

建议目录：

```text
src/finance_agent/storage/
  db.py
  orm.py
  repositories.py
  migrations/
```

实现顺序：

1. 先建立 M0 表的 ORM 模型和 Alembic 迁移。
2. 建立 `AssetRepository`、`UniverseRepository`、`MarketDataRepository`。
3. 建立 `IndicatorRepository`、`FactorRepository`、`ScreeningRepository`、`ScoreRepository`。
4. 建立 `RiskRepository`、`AgentAnalysisRepository`、`RecommendationRepository`。
5. 建立 `PortfolioRepository`、`WatchlistRepository`、`DecisionLogRepository`、`MemoryRepository`、`MemoryEmbeddingRepository`、`MemoryEdgeRepository`、`AlertRepository`。
6. 跑通一次 `recommend assets` 的写入、读取、证据追溯和中文报告生成。
7. 跑通一次 `portfolio monitor`：读取持仓、触发提醒、调用 Workflow、写入决策日志和 Finance Memory。
8. 再补 A 股专属快照、事件、回测和绩效表。
